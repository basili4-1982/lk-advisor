# Алгоритм рекомендации

## 1. Воронка

```text
запрос → интент → кандидаты → правила → скоринг → разнообразие → объяснение → ответ
```

LLM не участвует в выборе товара и не считает числа. Он только формулирует причину по готовым данным.

## 1.1. Профиль

Профиль собирается заранее и кэшируется. На запросе он не пересчитывается.

Что даёт:

- сужает кандидатов по категориям и задачам;
- добавляет признаки для скоринга;
- даёт аргументы для объяснения.

Что не делает:

- не выбирает товар;
- не подменяет правила: событие, если есть, только уточняет интент;
- не придумывает потребности без evidence.

Формула вклада профиля:

```text
profile_match = max(
  affinity[category] × 0.6 + affinity[task] × 0.4,
  need[tag] × 0.5
)
```

Пример: клиент с играми получает `games / gaming`, а не `backup`. Клиент с растровым редактором получает `graphics / raster` и соседнюю `vector`.

## 2. Интент

Ядро — профиль: история покупок, активные лицензии, поведение клиента. Событие визита не требуется.

Если `event` передан — берём его. Если нет — выводим по истории:

| Признак | Интент |
|---|---|
| лицензия истекает ≤ 90 дней | `renewal` |
| заказ доставлен ≤ 30 дней | `cross_sell` |
| клиент у лимита мест | `upsell` |
| последняя покупка — расходник | `reorder` |
| товар снят с продажи | `analog` |
| иначе | `none` → fallback |

## 3. Кандидаты

| Интент | Откуда берём |
|---|---|
| `renewal` | та же лицензия на новый срок, апгрейд на старший тариф |
| `cross_sell` | аксессуары, совместимые товары, гарантия, услуги к заказу |
| `upsell` | связи `upgrade`, старший тариф, дополнительные места |
| `reorder` | расходники и подписки к прошлой покупке |
| `analog` | связи `analog` для снятого товара |

Если товар уже куплен — исключаем, кроме апгрейда.

## 4. Правила

Порядок применения:

1. `excludes` и несовместимость — исключить.
2. `export_control` — исключить.
3. `already_owned` — исключить, если это не апгрейд.
4. `out_of_stock` — исключить или пометить.
5. `manager_only` — оставить, добавить `manager_approval`.
6. `max_discount` — ограничить скидку.

Правила применяются **до** скоринга и **до** LLM. Запрещённое не попадает в ответ даже с высоким score.

## 5. Скоринг

Каждый кандидат получает 0–1 по пяти признакам:

| Признак | Вес | Что значит |
|---|---:|---|
| `relevance` | 0.35 | совпадение с интентом: точное — 1.0, смежное — 0.6, общее — 0.2 |
| `urgency` | 0.25 | близость срока: ≤ 7 дней — 1.0, ≤ 30 — 0.7, ≤ 90 — 0.4 |
| `affinity` | 0.20 | совместные покупки, та же категория или вендор, тип связи |
| `margin` | 0.10 | маржинальность товара, нормированная по каталогу |
| `confidence` | 0.10 | уверенность связи и полнота данных |

```text
score = 0.35 × relevance
      + 0.25 × urgency
      + 0.20 × affinity
      + 0.10 × margin
      + 0.10 × confidence
```

Округление до двух знаков. При равном score выше тот, у кого больше `urgency`, затем — меньший `product_id` для детерминизма.

## 6. Разнообразие

- Не больше одной рекомендации одного типа.
- Top-3 после разнообразия.
- Если первая — `renewal`, вторая не может быть `renewal`.
- Дубликаты по `product_id` убираются.

## 7. Объяснение

Шаблон:

```text
{Что предлагаем}. {Почему}: {факт из evidence}. {Что будет, если согласиться}.
```

Примеры:

- «Продлите лицензию на 12 месяцев. Срок истекает 03.12.2026, это через 14 дней. Условия сохранятся.»
- «Добавьте гарантию к заказу. Заказ доставлен 18.11.2026, гарантия действует 12 месяцев.»
- «Перейдите на старший тариф. В текущем тарифе 10 мест, у вас занято 9.»

LLM получает только кандидата, evidence и шаблон. Любое число в ответе проверяется по evidence; если числа нет — фраза переписывается шаблоном.

## 8. Fallback

| Ситуация | Ответ |
|---|---|
| нет кандидатов после правил | популярные товары сегмента, `fallback: true` |
| нет истории у клиента | популярные товары сегмента, `fallback: true` |
| нет популярных | пустой список, `fallback: true` |
| нет каталога | 500, без выдуманных рекомендаций |

## 9. Логирование

На каждый запрос:

- `trace_id`, `client_id`, `event`;
- число кандидатов до и после правил;
- отсеянные правила;
- score и rank;
- выбранная рекомендация;
- latency;
- версия модели и каталога.

Лог нужен для демо и для будущего A/B.

## 10. Что проверяем

- [ ] Один и тот же вход при seed 42 даёт один и тот же ответ.
- [ ] Запрещённый товар не появляется ни в одном сценарии.
- [ ] `manager_only` не скрывает товар, а помечает.
- [ ] Числа в `reason` есть в `evidence`.
- [ ] Fallback не выдаёт запрещённое.
- [ ] Top-3 не содержит двух товаров одного типа.

## 11. Связи товаров

Связи берём из четырёх источников, по приоритету:

1. Явные атрибуты каталога: модель, цоколь, разъём, комплект.
2. Правила категорий и задач.
3. LLM по описаниям.
4. Совместные покупки.

LLM предлагает связь, но не решает, показывать ли её.

### Статусы

| Статус | Показываем |
|---|---|
| `confirmed` | да |
| `llm_suggested` + тип разрешён + confidence ≥ 0.7 + evidence | да |
| `quarantine` | нет |
| `rejected` | нет |

### Что можно в кросс-сейл

```text
accessory | compatibility | adjacent_task | workflow_next_step
```

### Что нельзя

```text
substitute | same_task   — это замена, не допродажа
none | rejected          — никогда
compatibility без явного подтверждения модели/цоколя/разъёма — в карантин
```

`show` из ответа LLM игнорируем. Его считает движок по типу связи, цели и правилам.

Подробности теста и ошибок — `relation-extraction.md`.
