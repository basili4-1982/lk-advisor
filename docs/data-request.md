# Что нужно от данных, чтобы проверить связывание solo

Гипотеза: solo-товар можно связать не по категории, а по цепочке задачи. Например, пакет шифрования → менеджер ключей, backup, аудит, утилита уничтожения файлов.

Пока это предположение. Ниже — минимальный сет, чтобы проверить его на реальных данных, а не на синтетике.

## 1. Товары

Минимум 300–500 карточек, лучше — весь каталог. По уточнению: **120 000 товаров с ценами**; для остальных цена может быть пустой.

| Поле | Обязательно | Зачем |
|---|---|---|
| `id` / `sku` | да | ключ |
| `title` | да | название |
| `description` | да | из описания извлекаем задачу и этап |
| `category` | да | базовая навигация |
| `subcategory` | желательно | точнее, чем категория |
| `vendor` | желательно | экосистема и совместимость |
| `price` | да для 120k | бюджетные альтернативы и наборы; пустая цена = «по запросу» |
| `currency` | да | рубли/другое |
| `term_months` | желательно | подписка/бессрочная |
| `audience` | желательно | `b2b` / `b2c` / `any` |
| `status` | да | активный/снятый |
| `attributes` | желательно | совместимость, API, форматы |
| `source_url` | желательно | проверка и цитирование |

## 2. Совместные покупки

Если есть — самый сильный сигнал.

```text
product_a, product_b, count, period_start, period_end
```

Минимум 100–500 пар. Если данных мало, лучше честно указать «нет», чем прислать случайные пары.

## 3. История одного клиента

```json
{
  "client_id": "...",
  "audience": "b2b",
  "industry": "manufacturing",
  "orders": [
    {
      "order_id": "...",
      "date": "2026-11-01",
      "items": [
        {"product_id": "...", "quantity": 1, "price": 10000}
      ]
    }
  ]
}
```

Нужны именно заказы с несколькими позициями, а не просто список купленных товаров. Иначе нельзя проверить «куплено вместе».

## 4. Существующие связи

Если есть ручные или исторические связи — пришлите:

```text
from_id, to_id, type, confidence, source
```

Они нужны как эталон и как отрицательные примеры: что уже считается связью, а что нет.

## 5. Кейсы и цепочки

Если у вас уже есть описания кейсов или цепочек задач — пришлите:

```text
case_id, title, description, industry, audience
case_id, product_id, role
```

Роль: `anchor`, `complement`, `service`, `alternative`.

## 6. Solo-товары, которые беспокоят

Отдельный список 30–50 товаров, которые сейчас остаются без связей. Это фокус эксперимента.

## Эксперимент на 50 solo

1. Берём 50 solo-товаров из списка.
2. Генерируем кандидатов:
   - co-purchase;
   - та же подкатегория;
   - вендор/экосистема;
   - LLM извлекает задачу и этап из описания;
   - открытые источники: `related`, `works with`, `accessories`.
3. Агент предлагает тип связи, уверенность, причину и evidence.
4. Человек проверяет 50 предложений.
5. Считаем:
   - precision связей;
   - долю solo, которым нашли осмысленную связь;
   - долю «лучше оставить solo»;
   - разницу B2B/B2C.

Порог: если precision ниже 0.7 или больше половины связей «притянуты за уши», гипотеза не проходит и мы оставляем solo + сервис/кейс, без выдуманных товаров.

## Что не делаем

- не связываем все 200k любой ценой;
- не привязываем игры к неигровым товарам;
- не публикуем связи без `confirmed`;
- не строим глобальные совместные покупки по истории одного клиента.

## Что уже готово

- шаблоны типов связей с описанием и примерами;
- агент разметки пары;
- очередь ручной валидации;
- список solo-товаров в админке;
- аналитика показов и пропусков.

Когда сет появится, меняется только загрузчик и набор кандидатов. Промпт и валидация уже есть.
