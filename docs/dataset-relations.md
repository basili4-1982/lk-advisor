## Ключ заказа

В сыром фиде один `order_id` может встречаться в разные недели: **44** таких
заказа, из них **6** пересекают train/test срез.

Поэтому атомарная единица покупки — **инстанс заказа**:

```text
(order_id, order_week)
```

Раньше ключ был `(order_id, item_id)`. Он схлопывал повторные недели, из-за
чего в БД оставался **1** multi-week заказ вместо **44**, а cross-cut — **0**
вместо **6**. Теперь:

- `lk_orders` хранит `PRIMARY KEY (order_id, order_week, item_id)`;
- co-purchase строится по инстансам заказа;
- train/test определяется по неделе строки; cross-cut заказы **не исключаются**,
  потому что разные недели — это разные покупки (ежемесячные подписки).

Проверка после переимпорта: 44 multi-week, 6 cross-cut, 30 514 строк,
27 603 инстанса.

## Приватность публичных ответов

Пороги `k`:

- товар виден в B2B, если у него **≥3** разных покупателя;
- товар виден в B2C, если у него **≥5** разных физлиц.

Правила применяются в `lk_item_privacy` и во всех публичных dataset-ответах:

- `GET /v1/admin/dataset/co-purchases?audience=b2b|b2c`;
- `GET /v1/admin/dataset/candidates?audience=b2b|b2c`;
- создание кандидатов из co-purchase;
- будущий демо-граф связей.

Скрытые товары остаются в БД и видны только агрегированно: общее число,
категории, счётчики. Названия, `item_id` и индивидуальные связи по ним в
публичные ответы не попадают.

На реальном датасете:

| Проверка | Кол-во |
|---|---:|
| Публичные товары | 817 |
| Скрыто (<3 покупателей) | 0 |
| B2C-товары | 66 |
| Скрыто B2C (<5 физлиц) | 0 |
| Публичные B2B-пары (≥3 B2B-покупок) | 412 |
| Публичные B2C-пары (≥5 B2C-покупок) | 3 |
| Co-purchase пары, скрытые по B2B-порогу | 1 781 |
| Co-purchase пары, скрытые по B2C-порогу | 2 190 |

B2C-граф поэтому будет почти пустым: это честно, а не «сломано». У физлиц
почти нет совместных заказов; для B2C работают популярность и use case, а не
co-purchase.

## Как устроено

```text
Sales XLSX
  → lk_items / lk_clients / lk_orders
  → co_purchase_pairs (count, B2B, B2C)
  → конструктор связей: активные шаблоны + LLM
  → lk_relation_candidates (quarantine)
  → ручное подтверждение / отклонение
```

Co-purchase — это **кандидат и evidence**, а не готовый тип связи. Тип выбирает конструктор:

- активные `relation_types`;
- описание, примеры и поведение;
- LLM-классификация;
- fallback по названиям: `upgrade`, `accessory`, `adjacent_task`.

## Что уже видно на реальных данных

- 2 193 пары; 729 пар с count ≥ 2.
- 208 solo-товаров — с ними нужна отдельная стратегия: кейс, сервис, открытые источники.
- Сильные пары — это в основном лицензии/дистрибутивы/тарифы:
  - Google Workspace Business ↔ Starter;
  - КриптоПро дистрибутив ↔ лицензия;
  - МагПро дистрибутив ↔ лицензия.
- Конструктор уже даёт `accessory` для дистрибутив/лицензия и `upgrade` для Starter → Business.

## Ограничения

- Категории товаров определены эвристикой по названию; фид ещё не подключён.
- Нет маппинга `item_id` → `product_id` реального каталога.
- Нет batch-классификации на все 729 пар; сейчас топ-10.
- Co-purchase не работает для B2C (0.8% мультитоварных заказов).
- Solo-товары пока только считаются; стратегия не реализована.
- LLM-классификация идёт последовательно; для сотен пар нужна очередь/воркеры.
