# База по классам ПО из реестра

Первый ощутимый результат внешних источников — не связи, а **классифицированная
база продуктов**. Это уже полезно само по себе.

## Где это уже полезно

1. **Поиск и фильтры.** Можно искать «антивирусы» или «средства бэкапа», а не
   угадывать по названию SKU.
2. **Дедупликация.** Один продукт в разных редакциях и у разных поставщиков
   сводится к одной реестровой записи.
3. **Аналоги.** Внутри класса видно, какие продукты конкурируют: 77 товаров
   антивирусной защиты — это готовый пул альтернатив.
4. **Проверка ошибок.** Если товар из класса «средства просмотра» предлагается
   как «средство защиты», это видно сразу.
5. **Холодный старт.** Для 79 товаров без истории класс даёт хоть какую-то
   идентичность и контекст.
6. **Отчётность.** 157 классов — это язык, на котором можно разговаривать с
   закупщиками и жюри, а не «817 безымянных SKU».

## Чего класс не даёт

- Класс не говорит, что два продукта дополняют друг друга.
- Внутри класса могут быть несовместимые вещи: антивирус и DLP.
- Класс не заменяет страницу состава продукта и матрицу совместимости.

Поэтому связи из одного класса строить нельзя. Но база классов уже полезна для
поиска, альтернатив, проверок и покрытия.

## Следующий шаг

1. Довести матчинг оставшихся 450 товаров до реестра.
2. Показывать класс в карточке товара и в витрине (в системной панели).
3. Для классов с покрытием >10 товаров собрать пул альтернатив и проверить
   вручную 50 пар.
4. Использовать класс как ограничение: не предлагать товар другого класса, если
   гипотеза про конкретную задачу.

## Как посмотреть

Админка → **Данные → Внешние знания**: там теперь видны 32 099 внешних
продуктов, 157 классов и таблица покрытия по классам.

## Проверка на выдаче

Замеры на трёх временных срезах показали: классы и сертификаты пока не
улучшают P@3, потому что serving использует только прямые связи от купленного,
а не классы. Текущая выдача практически равна popular (P@3 1.4–2.2%).
Подробности — `docs/recommendation-evaluation.md`.
