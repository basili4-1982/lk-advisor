# Проверка теории: дают ли внешние источники новое знание

**Гипотеза:** если подключить страницы вендоров и реестры ПО, система сможет
строить связи и проверять совместимость лучше, чем на одних внутренних покупках.

**Короткий вывод:** данные есть, и они закрывают реальный пробел — платформы и
редакции. Но автоматически превратить их в связи без слоя сопоставления
товаров (entity resolution) нельзя: наивный матчинг даёт ложные связи.

## Что собрали

Прототип из двух скриптов:

- `analysis/external_knowledge_probe.py` — скачивает страницы вендоров,
  извлекает факты через LLM, сохраняет URL и структурированные факты;
- `analysis/external_probe_analyze.py` — сопоставляет факты с каталогом,
  считает покрытие и кандидатов, отсекая уже известные связи.

Источники: Astra Linux, Яндекс 360, КриптоПро, VK WorkSpace, 1С-Битрикс,
The Bat!, Dr.Web, Google Workspace.

Сырые страницы не сохраняются. В отчёт попадают только извлечённые факты,
ссылки и публичные названия продуктов.

## Результаты

| Показатель | Значение |
|---|---:|
| Страниц обработано | 7 из 8 |
| Извлечено платформ | 24 |
| Извлечено редакций | 14 |
| Товаров в каталоге с платформой внутри | **0 из 817** |
| Кандидатов по редакциям (после отсечения известных) | 30 |
| Кросс-вендорных кандидатов | 33 |
| Из них высокого качества без доработки | мало |

### Что получилось хорошо

1. **Платформы.** КриптоПро CSP: Windows, macOS, Linux, FreeBSD, Solaris,
   AIX, iOS, Android. Dr.Web: ПК, смартфоны, планшеты, Smart TV, консоли.
   VK WorkSpace: Windows, Linux, веб, мобильные. Внутри каталога этих полей
   нет вообще — внешний источник закрывает пробел на 100% для выборки.

2. **Редакции и тарифы.** Google Workspace: Starter, Standard, Plus,
   Enterprise. VK WorkSpace: Базовый, Расширенный, Индивидуальный.
   1С-Битрикс: Малый бизнес, Бизнес. Это основа для upgrade/alternative.

3. **Интеграции.** КриптоПро: УЦ, ЭЦП, IPsec, EFS, .NET. Google Workspace:
   Gemini, AppSheet, Cloud Identity, Migrate. VK: SSO/OAuth, DLP, SIEM.

### Где теория не подтвердилась

1. **SKU и продукт — разные уровни.** Вендор пишет «Смоленск» и «Воронеж», а в
   каталоге SKU различаются платформой, сроком и числом пользователей.
   Прямого совпадения строк нет.

2. **Наивный матчинг даёт ложные связи.** «Microsoft Office» совпал с
   «Kaspersky Small Office», «Cloud Identity Premium» — с «Kaspersky Premium».
   Один общий токен — не связь.

3. **Для 215 товаров без связей** автоматических кандидатов высокого качества
   в этом прогоне не появилось. Данные есть, но нужен слой сопоставления.

4. **Реестр Минцифры** с демо-стенда напрямую не открылся (таймаут). Нужен
   файл XML/XLS или отдельный импорт, а не запрос со страницы.

## Вывод

Теория подтверждена частично:

- **атрибуты и совместимость** — да, внешние источники дают новое знание;
- **связи автоматически** — нет, без entity resolution получается шум.

Это не повод отказываться. Это указывает, что строить надо не «парсер
страниц», а **слой идентичности товара**:

```text
вендор → продукт → линейка → редакция → SKU
реестровый номер / SKU / алиасы
```

Пока этого нет, LLM будет связывать «Office» с чем угодно.

## Что делать дальше

1. **Entity resolution.** Таблица `vendor_products`: вендор, продукт, линейка,
   редакция, платформа, реестровый номер, алиасы. Сопоставление с `lk_items`.
2. **Источники.**
   - реестр Минцифры: импорт XML/XLS;
   - страницы вендоров: платформа, редакции, совместимость;
   - матрицы совместимости: отдельный адаптер.
3. **Evidence store.** URL, цитата, дата, TTL, тип источника.
4. **Правила кандидатов.**
   - одна линейка + разные редакции → upgrade/variant;
   - одна категория + разные платформы → alternative;
   - явная интеграция из документации → adjacent_task;
   - всё остальное → «требует проверки».
5. **Оценка точности.** Разметить 50 пар: precision внешних кандидатов должна
   быть выше 80%, иначе в прод не пускать.

## Как воспроизвести

```bash
python3 analysis/external_knowledge_probe.py
python3 analysis/external_probe_analyze.py
```

Нужны `DEEPSEEK_API_KEY` и доступ к `DATABASE_URL`. JSON-выгрузки не
коммитятся: в них есть внутренние item_id.

## Слой vendor_products

После проверки добавлен рабочий слой внешних продуктов:

- `vendor_products`: вендор, продукт, линейка, редакция, платформы, реестровый
  номер, URL источника, алиасы;
- `vendor_product_items`: сопоставление внешнего продукта с SKU каталога,
  метод и уверенность;
- импорт CSV и кнопка «Сопоставить с каталогом» в разделе «Данные».

Демо-состояние после импорта и сопоставления:

| Показатель | Значение |
|---|---:|
| Внешних продуктов | 16 |
| Сопоставлено продуктов | 14 |
| Покрыто SKU каталога | 172 |
| Из них товаров без связей | 32 |

То есть внешний слой уже даёт платформы и редакции для 172 SKU, включая
32 «сироты», у которых не было ни одной связи.

Импорт сейчас принимает CSV. Для реестра Минцифры нужен отдельный XML-адаптер:
с демо-стенда сайт реестра не открылся, выгрузку нужно забирать файлом.
