## Разбор функций

### Сильные

- **Реестр связей**: статусы, провенанс, версия, TTL, reject-memory, bulk,
  импорт, сброс.
- **Каталог**: фильтры, уверенность, карточка связи, алиасы, доказательства,
  фильтр по сертификату.
- **Метрики**: официальный протокол, P@3, baseline, bootstrap CI, variant share.
- **Гипотезы**: создание на каталоге, guardrails, решения, база знаний.
- **Serving**: предрасчёт офлайн-модели, 11.67% P@3, popular fallback.
- **Витрина**: чистый клиентский вид, системная информация по кнопке, профиль,
  история, создание клиента, сертификаты.
- **Внешние данные**: Минцифры, ФСТЭК, вендорские страницы, классы, источники.

### Слабые места

1. **`internal/httpapi/admin.go` — монолит** на несколько тысяч строк с HTML/JS.
   Любая правка рискованна.
2. **Предрасчёт рекомендаций вручную.** Нет планировщика; после новых покупок
   таблица устаревает.
3. **Матчинг внешних данных эвристический.** Есть ложные совпадения; precision
   не измерен на большой выборке.
4. **Нет авторизации.** Демо-стенд, не продакшен.
5. **Живой трафик только ручной.** Показы создаются открытием витрины.
6. **Платформенная совместимость** помечается `unverified`, но не фильтруется.
7. **Тесты частичные.** Нет end-to-end на весь сценарий; часть тестов делит БД
   с демо.

### Что добавить для 90+

- Планировщик пересчёта рекомендаций.
- E2E-тест сценария «гипотеза → витрина → решение».
- Проверка платформы по матрицам совместимости.
- Живой обход вендорских страниц с TTL.
- Разбить `admin.go` на модули.

## Что честно говорить на демо

- Показы создаются реальным открытием витрины, а не накруткой.
- Метрика P@3 — офлайн-бэктест, не живые продажи.
- Внешние источники — реестр и страницы вендоров; обход не полностью живой.
- Для регулируемых отраслей сертификация включена политикой, её можно отключить.
- Платформенная совместимость пока помечается, а не фильтруется.
