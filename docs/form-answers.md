# Ответы для формы ИИкузница

## 2. Подход и архитектура

Путь запроса: `POST /v1/recommendations` с `client_id` → профиль клиента (покупки,
активные лицензии и сроки, отрасль, сегмент, история) → кандидаты из графа
связей → отсечение правилами → скоринг → разнообразие → топ-3 → объяснение.

Источники и инструменты: совместные покупки из истории, документация вендоров,
страницы товаров, атрибуты каталога, реестр Минцифры, реестр ФСТЭК. Кандидаты
строятся по связям (апгрейд, дополнение, замена, аксессуар), затем применяются
правила: несовместимость, уже куплено, экспортный контроль, только через
менеджера, нет в наличии.

Где принимает решения модель: LLM **не выбирает товар и не считает score**.
Движок детерминированно считает пять признаков — релевантность ситуации,
срочность, близость покупок, маржу, уверенность связи. LLM делает две вещи:
предлагает тип связи и уверенность при разметке и формулирует человеческую
причину по готовым evidence.

Как проверяется ответ: тип связи валидируется по реестру; уверенность ≥85%
принимается автоматически, 70–85% уходит человеку, ниже 70% — в карантин;
правила применяются до скоринга; ответ проходит guard по числам, PII и утечке
промпта; каждое утверждение привязано к evidence. Обратная связь — показы,
клики, покупки — плавно снижает вес неработающих связей.

## 3. Стек и модели

- **LLM:** DeepSeek V4.1 Flash 1017 (`deepseek-flash`) через API. Используется
  только для объяснений и предложений связей; товар и score не выбирает.
- **Офлайн-модель:** совместные покупки + популярность + пересечение токенов
  названий + связи каталога. Python (pandas/numpy), результат в PostgreSQL.
- **Backend:** Go 1.26, `net/http`, `lib/pq`, планировщик пересчёта.
- **Frontend:** серверный HTML/CSS + ванильный JavaScript.
- **База:** PostgreSQL 16 — каталог, клиенты, заказы, связи, правила, веса,
  события, эксперименты, `client_recommendations`, профильные шарды.
- **Хостинг:** Ubuntu 22.04, Docker Compose; `lk-app` (non-root, read-only),
  `lk-db` (внутренняя сеть), Caddy 2 (TLS Let's Encrypt), домен
  `taskino.online`, сервер `45.8.248.227`.

## 5. Запуск и поставка

Состав: исходники на GitHub, Docker Compose (`lk-app` + `lk-db`), Caddy,
миграции внутри бинарника, дамп демо-базы (817 товаров, 812 связей,
190 110 рекомендаций), OpenAPI, документация, инструкция, расчёт стоимости,
демо-видео.

Среда: Ubuntu 22.04, Docker Compose v2, 4 vCPU / 8 ГБ RAM / 48 ГБ. Переменные:
`DATABASE_URL`, `ADDR=:8080`, `LLM_API_KEY`, `DEMO_ALLOW_REAL_DATA=1`,
`RECOMPUTE_INTERVAL`, `RELATION_SYSTEM_PROMPT`. Запуск:
`docker compose up -d --build`; healthcheck `/healthz`.

Доступ: логин не нужен. Тестовые клиенты — `C05445` (treatment, target в блоке),
`C11191` (финансы, только сертифицированные), `COLD-RETAIL` (холодный старт).
Опасные операции (сброс каталога, импорт, apply агента) закрыты `403`.

Пример запроса:

```bash
curl -X POST https://taskino.online/v1/recommendations \
  -H 'Content-Type: application/json' \
  -d '{"client_id":"C05445","limit":3}'
```

Ожидаемый ответ: `variant: treatment`, три рекомендации; третья —
`GAPPS-STARTER-1USER-1MO-First-Year`, `type: upsell`, причина «Гипотеза: показ
в эксперименте». Полный JSON — в материалах и `docs/api.md`.

## Чего нет

- авторизации и ролей — демо открыто, закрыт только промпт;
- адаптера к реальному ЛК — отдаём API, события из витрины;
- живого трафика: метрики — офлайн-бэктест;
- полного совпадения XLSX и `lk_orders` (31 753 против 30 514 продаж);
- автоматического обхода всех открытых источников и безошибочного матчинга;
- rate limit/WAF, контрактных тестов OpenAPI и полного E2E;
- масштабирования до 120 тыс. товаров и онлайн-обучения.
