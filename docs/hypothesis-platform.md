# Платформа проверки гипотез: вертикальный срез

Одна гипотеза проходит полный цикл:

```text
гипотеза → назначение → exposure → метрики → решение
```

Это не «ещё один A/B», а слой, который связывает рекомендацию с проверяемым
эффектом и решением.

## Создание гипотезы

Гипотеза создаётся в разделе **«Гипотезы»** кнопкой **«Добавить гипотезу»**.
Форма работает на каталоге (`lk_items`), а не на синтетическом `products`.

Поля:

| Поле | Обязательно | По умолчанию |
|---|---|---|
| Источник (`from_id`) | да | — |
| Цель (`to_id`) | да | — |
| Тип связи (`relation_type`) | да | первый активный тип |
| Название | нет | генерируется из товаров, можно изменить |
| Формулировка | нет | генерируется, можно изменить |
| Аудитория | да | `b2b` |
| Отрасль | нет | пусто, то есть все отрасли |
| Primary metric | да | `conversion` |
| Guardrails | нет | `renewal, upsell, fallback` |
| Traffic split | да | 50/50 |

Название и формулировка генерируются из очищенных названий товаров: общие
префиксы вроде «Предоставление доступа к сервисам» отбрасываются, чтобы
заголовок оставался читаемым. После ручной правки автогенерация для этого поля
отключается.

Новая гипотеза стартует в статусе `running` **без событий**: 0 exposure на
оба варианта. Guardrail в этом состоянии рекомендует `extend` («мало данных»),
и кнопка «Внедрить» заблокирована. Это ожидаемое поведение, а не ошибка.

API:

```bash
curl -X POST localhost:8080/v1/admin/experiments \
  -H 'Content-Type: application/json' \
  -d '{
    "from_id":"GAPPS-BUS-STD-1USER-1MO-First-Year",
    "to_id":"GAPPS-STARTER-1USER-1MO-First-Year",
    "relation_type":"upgrade",
    "title":"Показ Starter после Business",
    "hypothesis":"Апгрейд на Starter повышает конверсию в B2B",
    "audience":"b2b",
    "industry":"",
    "metric":"conversion",
    "guardrails":"renewal, upsell, fallback",
    "traffic_split":0.5
  }'
```

Если для пары уже идёт эксперимент, API возвращает его `id` с
`created: false`, дубль не создаётся. Кнопка **«Проверить гипотезой»** в
карточке связи в «Каталоге» создаёт гипотезу тем же API.

## Как это работает

1. Клиент детерминированно попадает в `control` или `treatment` по хэшу
   `experiment_id + client_id`.
2. Каждый запрос рекомендаций пишет `exposed` в `experiment_events`.
3. Если target показан, exposure привязывается к `product_id`.
4. Клик и покупка target копируются в `experiment_events`.
5. Результаты считаются по вариантам, включая:
   - exposures;
   - target shown;
   - clicks;
   - purchases;
   - CTR;
   - overall conversion;
   - target conversion.
6. Считаются guardrails: renewal, upsell, fallback.
7. Человек принимает решение: `promote`, `reject`, `extend`.

## Почему target conversion важнее uplift

Пример синтетического прогона 50 клиентов × 10 сессий (не данные каталога):

| Вариант | Exposure | Target shown | Покупки | Conversion | Target conv |
|---|---:|---:|---:|---:|---:|
| control | 250 | 28 | 5 | 2.0% | **17.9%** |
| treatment | 250 | 228 | 67 | 26.8% | **29.4%** |

Guardrails в том же прогоне:

| Вариант | Renewal | Upsell | Fallback |
|---|---:|---:|---:|
| control | 76.0% | 20.0% | 0.0% |
| treatment | 72.0% | 24.0% | 0.0% |

Renewal слегка падает. Поэтому решение — не `promote`, а `extend`: нужна
вторая волна и проверка, не теряем ли продления.

## Guardrail hard-stop

Перед решением платформа проверяет:

| Guardrail | Порог | Действие |
|---|---|---|
| Renewal | падение ≥ 5 п.п. | блок `promote`, `extend` |
| Renewal | падение ≥ 10 п.п. | `reject` |
| Fallback | рост ≥ 5 п.п. | `reject` |
| Margin на exposure | падение ≥ 20% | `reject` |
| Мало данных | <100 exposure на вариант | `extend` |

Если человек нажимает `promote`, а guardrail сработал, решение автоматически
заменяется на `extend` или `reject`, а причина пишется в заметку.

## Time-to-reject

Плохая гипотеза (CorelDRAW офисному сотруднику) останавливается на
**100 exposure на вариант**, то есть на 200 сессиях при сплите 50/50.

Первый чекпоинт на 50/50 только помечает проблему (`extend`, мало данных),
второй — автоматически переводит эксперимент в `reject`. Подробнее:
`analysis/bad_hypothesis_stop.md`.

## Margin guardrail

В `products` появилось поле `cost`. Пока оно равно 0, маржа считается
недоступной и guardrail не блокирует решение. Когда заказчик даст
себестоимость, платформа начнёт считать:

- revenue по покупкам;
- margin на purchase;
- margin на exposure;
- падение маржи treatment против control.

## База знаний

```text
GET /v1/admin/experiments/knowledge?q=PDF&decision=reject
```

Завершённые эксперименты остаются в `experiments` с решением, заметкой,
скоупом и результатами. В админке есть поиск по названию, гипотезе, скоупу и
target. Это позволяет отвечать: «мы это уже проверяли, вот что вышло».

Общий uplift выглядит огромным, но target conversion на 25 клиентах — шумный:
в разных прогонах он гуляет от 18% до 32%.

Устойчивый вывод: **эффект в первую очередь в exposure, а не в качестве
товара**. Рост общего conversion — это распределение. Нужна вторая волна,
поэтому решение — `extend`, а не `promote`.

Это и есть ценность платформы: она показывает, **где именно** возникает эффект.

## API

```text
GET  /v1/admin/experiments
POST /v1/admin/experiments/demo
POST /v1/admin/experiments/{id}/decision
```

Решение:

```json
{"decision":"promote","note":"подтверждено на пилоте"}
```

## Схема

- `experiments` — гипотеза, скоуп, варианты, target, статус, решение;
- `experiment_assignments` — стабильный вариант клиента;
- `experiment_events` — exposed / clicked / purchased + guardrail-поля и margin.

`extend` не просто меняет статус: эксперимент остаётся running и получает
`ends_at = now() + 14 дней` для следующей волны.

## База знаний

Завершённые эксперименты не удаляются: в таблице `experiments` остаются
гипотеза, скоуп, метрики, решение и заметка. Это и есть первая версия базы
знаний: что проверяли, где, с каким результатом и что решили.

## Ограничения

- Это синтетическая симуляция, не рыночное доказательство.
- 25 клиентов на вариант — мало для статистической значимости.
- Нет маржи: нужна себестоимость.
- Нет guardrail-метрик по renewal/upsell в этой версии.
- Решение принимает человек; платформа не меняет семантику связи сама.

## Следующий шаг

- guardrails: renewal, upsell, fallback, margin;
- sequential testing и минимальная выборка;
- база знаний: гипотеза → результат → скоуп → TTL;
- пилот на реальном трафике ЛК.

## Эмулятор гипотез

Гипотезу можно прогнать на описанном профиле клиента, не дожидаясь реального
трафика.

Профиль хранится в `client_profiles`:

| Поле | Что это |
|---|---|
| `name` | человекочитаемое имя профиля |
| `audience` | `b2b` или `b2c` |
| `industry` | отрасль из справочника `lk_clients`, может быть пустой |
| `description` | свободное описание задачи клиента |

При миграции создаются четыре демо-профиля: стоматологическая клиника, школа,
розничная сеть и частный покупатель.

Прогон запускается из карточки гипотезы кнопкой **«Прогнать на эмуляторе»**:
выбирается профиль (или создаётся новый), количество показов (200–2000) и
запускается симуляция. Старый прогон этой гипотезы заменяется, реальные события
не затрагиваются: эмулятор пишет строки с `client_id LIKE 'emu:%'`.

### Как считается попадание

Формула прозрачная и детерминированная:

| Фактор | Вес |
|---|---:|
| Совпадение аудитории B2B/B2C | 0.15 |
| Совпадение отрасли или отсутствие ограничения | 0.05–0.07 |
| Смысловые совпадения и общие слова описания с товаром | до 0.65 |
| Отраслевая релевантность по реальным покупкам | до 0.10 |
| Приоритет типа связи (`upgrade`, `adjacent_task`, …) | до 0.05 |

Смысловые совпадения считаются по небольшому словарю задач: почта, офисные
программы, антивирус и защита, резервное копирование, контроль доступа,
графика и дизайн, разработка, обучение, бухгалтерия, торговля и склад,
медицина, инфраструктура. Дополнительно учитываются общие значимые слова
описания и названия товара.

Названия товаров очищаются от рыночных префиксов вида «Предоставление доступа
к сервисам», иначе слово «доступа» совпадало бы со всеми позициями.

Попадание ограничено 95%: даже идеальное совпадение не даёт 100%, потому что
это оценка, а не факт покупки.

### Что моделируется

- `control` — популярный товар, который система показала бы без гипотезы;
- `treatment` — целевой товар гипотезы;
- клик и покупка разыгрываются детерминированно от попадания и `seed`;
- пишутся `exposed`, `clicked`, `purchased`, флаги renewal/upsell/fallback;
- после прогона карточка гипотезы, guardrails и решение работают на этих
  событиях.

Это симуляция на профилях, а не реальный трафик. Её метрики не смешиваются с
офлайн-бэктестом каталога.

API:

```bash
curl localhost:8080/v1/admin/client-profiles

curl -X POST localhost:8080/v1/admin/client-profiles \
  -H 'Content-Type: application/json' \
  -d '{"name":"Клиника","audience":"b2b","industry":"Медицинские организации",
       "description":"Нужны почта, антивирус и защита данных"}'

curl -X POST localhost:8080/v1/admin/experiments/<id>/emulate \
  -H 'Content-Type: application/json' \
  -d '{"profile_id":"prof-clinic","impressions":400}'

curl localhost:8080/v1/admin/experiments/<id>/emulations
```

## Демо-сценарий

1. «Гипотезы» → **«Добавить гипотезу»**.
2. Источник: `Google Workspace Business Standard`, цель: `Google Workspace Starter`,
   тип связи: `upgrade`, аудитория B2B.
3. В карточке — **«Прогнать на эмуляторе»**.
4. Профиль «Стоматологическая клиника», 400 показов, **«Запустить прогон»**.
5. Показать: попадание ~63%, совпавшие смыслы (почта, офисные программы),
   control 15% → treatment 21%, uplift +35%, guardrail ok.
6. Решение **«Внедрить»** — гипотеза уходит в базу знаний.

## Витрина клиента: настоящие показы

Чтобы показы были настоящими, а не сгенерированными, есть клиентская страница:

```text
http://localhost:8080/lk
```

На ней выбирается клиент каталога (`lk_clients`), и открывается блок из топ-3.
Каждое открытие страницы — это настоящий вызов `/v1/recommendations`, то есть
реальный показ. Пока никто не открыл страницу, показов нет.

Кнопки **«Клик»** и **«Купить»** на карточке отправляют настоящие
`clicked` / `purchased` через `/v1/events`. Только после этого в карточке
гипотезы появляются клики и покупки.

Клиенты, у которых целевой товар уже куплен, на витрине не выбираются: продление
уже купленного не рекомендуется. `variant_of` и снятые с продажи товары в блок
не попадают. Если истории нет — показываются популярные товары отрасли
(холодный старт).

Клиент видит только товары и человеческие причины: «более широкая редакция»,
«дополняет покупку», «часто выбирают». Никаких `product_id`, `trace_id`,
вариантов и статусов связей.

Системная информация скрыта за кнопкой **«Системная информация»**: там
`client_id`, `strategy`, `cold_start`, `experiment_id`, `variant`, `trace_id`,
выбор клиента, профиль (тип, отрасль, сегмент, группа, источник), история
покупок (заказы, товары, даты) и по каждой карточке `product_id`,
`relation_type`, `forced_by_experiment`, `source_product_id`, `score`,
`system_reason`. Товары из истории, которые стали источником рекомендации,
помечаются в таблице.

В системной панели можно создать нового клиента: тип (ЮЛ/ИП/ФЛ), отрасль из
справочника, сегмент и группа. Новый клиент стартует без истории, поэтому сразу
показывает холодный старт. В клиентском виде ни профиля, ни истории, ни формы
создания нет — всё это доступно только по кнопке «Показать системную
информацию».

В админке кнопка **«Витрина клиента»** открывает эту страницу.

Ограничение: показов будет столько, сколько раз страницу реально открыли.
Автоматических прогонов, которые накручивают показы, больше нет.
