# Платформа проверки гипотез: вертикальный срез

Одна гипотеза проходит полный цикл:

```text
гипотеза → назначение → exposure → метрики → решение
```

Это не «ещё один A/B», а слой, который связывает рекомендацию с проверяемым
эффектом и решением.

## Создание гипотезы

Гипотеза создаётся в разделе **«Гипотезы»** кнопкой **«Добавить гипотезу»**.
Форма работает на каталоге (`lk_items`), а не на синтетическом `products`.

Поля:

| Поле | Обязательно | По умолчанию |
|---|---|---|
| Источник (`from_id`) | да | — |
| Цель (`to_id`) | да | — |
| Тип связи (`relation_type`) | да | первый активный тип |
| Название | нет | генерируется из товаров, можно изменить |
| Формулировка | нет | генерируется, можно изменить |
| Аудитория | да | `b2b` |
| Отрасль | нет | пусто, то есть все отрасли |
| Primary metric | да | `conversion` |
| Guardrails | нет | `renewal, upsell, fallback` |
| Traffic split | да | 50/50 |

Название и формулировка генерируются из очищенных названий товаров: общие
префиксы вроде «Предоставление доступа к сервисам» отбрасываются, чтобы
заголовок оставался читаемым. После ручной правки автогенерация для этого поля
отключается.

Новая гипотеза стартует в статусе `running` **без событий**: 0 exposure на
оба варианта. Guardrail в этом состоянии рекомендует `extend` («мало данных»),
и кнопка «Внедрить» заблокирована. Это ожидаемое поведение, а не ошибка.

API:

```bash
curl -X POST localhost:8080/v1/admin/experiments \
  -H 'Content-Type: application/json' \
  -d '{
    "from_id":"GAPPS-BUS-STD-1USER-1MO-First-Year",
    "to_id":"GAPPS-STARTER-1USER-1MO-First-Year",
    "relation_type":"upgrade",
    "title":"Показ Starter после Business",
    "hypothesis":"Апгрейд на Starter повышает конверсию в B2B",
    "audience":"b2b",
    "industry":"",
    "metric":"conversion",
    "guardrails":"renewal, upsell, fallback",
    "traffic_split":0.5
  }'
```

Если для пары уже идёт эксперимент, API возвращает его `id` с
`created: false`, дубль не создаётся. Кнопка **«Проверить гипотезой»** в
карточке связи в «Каталоге» создаёт гипотезу тем же API.

## Как это работает

1. Клиент детерминированно попадает в `control` или `treatment` по хэшу
   `experiment_id + client_id`.
2. Каждый запрос рекомендаций пишет `exposed` в `experiment_events`.
3. Если target показан, exposure привязывается к `product_id`.
4. Клик и покупка target копируются в `experiment_events`.
5. Результаты считаются по вариантам, включая:
   - exposures;
   - target shown;
   - clicks;
   - purchases;
   - CTR;
   - overall conversion;
   - target conversion.
6. Считаются guardrails: renewal, upsell, fallback.
7. Человек принимает решение: `promote`, `reject`, `extend`.

## Почему target conversion важнее uplift

Пример синтетического прогона 50 клиентов × 10 сессий (не данные каталога):

| Вариант | Exposure | Target shown | Покупки | Conversion | Target conv |
|---|---:|---:|---:|---:|---:|
| control | 250 | 28 | 5 | 2.0% | **17.9%** |
| treatment | 250 | 228 | 67 | 26.8% | **29.4%** |

Guardrails в том же прогоне:

| Вариант | Renewal | Upsell | Fallback |
|---|---:|---:|---:|
| control | 76.0% | 20.0% | 0.0% |
| treatment | 72.0% | 24.0% | 0.0% |

Renewal слегка падает. Поэтому решение — не `promote`, а `extend`: нужна
вторая волна и проверка, не теряем ли продления.

## Guardrail hard-stop

Перед решением платформа проверяет:

| Guardrail | Порог | Действие |
|---|---|---|
| Renewal | падение ≥ 5 п.п. | блок `promote`, `extend` |
| Renewal | падение ≥ 10 п.п. | `reject` |
| Fallback | рост ≥ 5 п.п. | `reject` |
| Margin на exposure | падение ≥ 20% | `reject` |
| Мало данных | <100 exposure на вариант | `extend` |

Если человек нажимает `promote`, а guardrail сработал, решение автоматически
заменяется на `extend` или `reject`, а причина пишется в заметку.

## Time-to-reject

Плохая гипотеза (CorelDRAW офисному сотруднику) останавливается на
**100 exposure на вариант**, то есть на 200 сессиях при сплите 50/50.

Первый чекпоинт на 50/50 только помечает проблему (`extend`, мало данных),
второй — автоматически переводит эксперимент в `reject`. Подробнее:
`analysis/bad_hypothesis_stop.md`.

## Margin guardrail

В `products` появилось поле `cost`. Пока оно равно 0, маржа считается
недоступной и guardrail не блокирует решение. Когда заказчик даст
себестоимость, платформа начнёт считать:

- revenue по покупкам;
- margin на purchase;
- margin на exposure;
- падение маржи treatment против control.

## База знаний

```text
GET /v1/admin/experiments/knowledge?q=PDF&decision=reject
```

Завершённые эксперименты остаются в `experiments` с решением, заметкой,
скоупом и результатами. В админке есть поиск по названию, гипотезе, скоупу и
target. Это позволяет отвечать: «мы это уже проверяли, вот что вышло».

Общий uplift выглядит огромным, но target conversion на 25 клиентах — шумный:
в разных прогонах он гуляет от 18% до 32%.

Устойчивый вывод: **эффект в первую очередь в exposure, а не в качестве
товара**. Рост общего conversion — это распределение. Нужна вторая волна,
поэтому решение — `extend`, а не `promote`.

Это и есть ценность платформы: она показывает, **где именно** возникает эффект.

## API

```text
GET  /v1/admin/experiments
POST /v1/admin/experiments/demo
POST /v1/admin/experiments/{id}/decision
```

Решение:

```json
{"decision":"promote","note":"подтверждено на пилоте"}
```

## Схема

- `experiments` — гипотеза, скоуп, варианты, target, статус, решение;
- `experiment_assignments` — стабильный вариант клиента;
- `experiment_events` — exposed / clicked / purchased + guardrail-поля и margin.

`extend` не просто меняет статус: эксперимент остаётся running и получает
`ends_at = now() + 14 дней` для следующей волны.

## База знаний

Завершённые эксперименты не удаляются: в таблице `experiments` остаются
гипотеза, скоуп, метрики, решение и заметка. Это и есть первая версия базы
знаний: что проверяли, где, с каким результатом и что решили.

## Ограничения

- Это синтетическая симуляция, не рыночное доказательство.
- 25 клиентов на вариант — мало для статистической значимости.
- Нет маржи: нужна себестоимость.
- Нет guardrail-метрик по renewal/upsell в этой версии.
- Решение принимает человек; платформа не меняет семантику связи сама.
