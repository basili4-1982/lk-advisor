# Реестр связей v5 и Workbench

## Зачем реестр

Связь между товарами — не поле карточки и не правило, срабатывающее в момент показа, а
самостоятельная сущность: у неё есть тип, направление, провенанс, статус, версия, владелец и
срок действия. Витрина рекомендаций и демо-граф только читают подтверждённые рёбра.

Рабочая поверхность мерчандайзера — таблица `/admin#registry` («Каталог v5»). Граф остаётся
витриной и в этом плане не меняется.

## Схема

Таблица `relations` (переименована из `lk_relation_candidates` миграцией `023_relation_registry.sql`).

| Поле | Смысл |
|---|---|
| `from_item_id`, `to_item_id` | концы ребра, ссылки на `lk_items` |
| `type` | код из `relation_types` (`accessory`, `upgrade`, `alternative`, `bundle`, `adjacent_task`, `compatibility`, `variant_of`, …) |
| `status` | жизненный цикл, см. ниже |
| `provenance_kind` | `manual`, `llm`, `co_purchase`, `attribute`, `rule`, `import` |
| `confidence` | уверенность вместе с методом и источником, а не «голая вероятность» |
| `evidence` | массив доказательств: `{kind, summary, details}`; старые `{source, value}` читаются |
| `version` | оптимистическая блокировка; ревью не перезапишет чужое решение |
| `audience`, `industry`, `org_type` | область действия; пустая строка = для всех |
| `valid_from`, `valid_until` | срок бизнес-связи |
| `revalidate_after` | когда связь пора перепроверить |
| `owner_id`, `created_by`, `approved_by`, `approved_at` | ответственность |
| `rejection_reason`, `rejected_until` | память отказа и кулдаун |
| `supersedes` | ребро-предшественник |

Аудит — append-only таблица `relation_events`: `actor_kind`, `actor_id`, `action`,
`payload_before`, `payload_after`, `rubric_version`, `created_at`.

Реестр внутренний: он видит весь каталог v5, включая товары, скрытые публичной витриной.
Публичные ответы по-прежнему фильтруются через `lk_item_privacy`.

## Статусы

| Статус | Значение |
|---|---|
| `candidate` | предложено генератором, ждёт человека |
| `active` | подтверждено человеком, может попадать в выдачу |
| `rejected` | отклонено; причина и кулдаун 90 дней обязательны |
| `stale` | истёк `revalidate_after`; не удалено, но не показывается |
| `expired` | истёк срок бизнес-связи (`valid_until`) |
| `superseded` | заменено новым ребром |

Синтетический каталог (`product_relations`) живёт отдельно и сохраняет старые статусы
`confirmed|quarantine|llm_suggested|rejected`. Это осознанная граница: движок рекомендаций
не переписывался.

## Провенанс и доказательства

- `co_purchase` — строгий режим: пара в одной корзине/заказе, без транзитивного замыкания.
- `attribute` — структурные связи из `product_group`, в первую очередь `variant_of`.
- `llm` — типизация и объяснение; LLM не удаляет человеческие решения.
- `manual` — арбитр, имеет приоритет над правилами.

Доказательство показывается чипом с числами: `co-purchase: 12 заказов, B2B 9`,
`attribute: product_group=G121231`. У ручного ребра доказательство пустое —
источник и автор видны в провенансе и аудите.

## TTL и пересмотр

| Источник | Срок |
|---|---|
| `co_purchase` | 90 дней |
| `llm` | 180 дней |
| `manual` | бессрочно, но с `revalidate_after` по событиям цены/версии/срока |
| `compatibility` | по изменению атрибута |
| `variant_of` | структурная, пересчитывается генерацией |

`POST /v1/admin/registry/sweep` переводит просроченные рёбра в `stale`, а истёкшие — в
`expired`. В демо это кнопка «Проверить TTL»; ежедневного планировщика пока нет.
Co-purchase-кандидаты при генерации получают `revalidate_after` из
`relation_types.default_ttl_days` (90 дней), `variant_of` — структурная связь без
календарного TTL.

## API

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/v1/admin/registry/relations` | список с фильтрами |
| `GET` | `/v1/admin/registry/metrics` | сводка Workbench |
| `POST` | `/v1/admin/registry/relations/{id}/review` | решение по одному ребру |
| `POST` | `/v1/admin/registry/relations/bulk-review` | массовое решение по `ids` или фильтру |
| `POST` | `/v1/admin/registry/generate` | генерация `variant_of` и co-purchase кандидатов |
| `POST` | `/v1/admin/registry/sweep` | TTL: `stale` и `expired` |
| `PUT` | `/v1/admin/registry/aliases/{item_id}` | короткое имя товара (`short_name`, пустое — удалить) |

Фильтры списка: `q`, `type`, `status`, `source`, `family`, `audience`, `org_type`, `owner`,
`min_conf`, `max_conf`, `expiring`, `sort`, `limit`, `offset`. Сортировка — только из белого
списка, значения идут параметрами.

Ревью:

```json
{"decision": "confirm|reject|defer", "note": "почему", "expected_version": 3}
```

- `reject` без непустой причины возвращает `400`;
- устаревшая версия — `409`;
- неизвестное ребро — `404`.

Массовое ревью принимает `ids` (чекбоксы Workbench) или `filter`. Без `ids`, типов или
`min_confidence` возвращается `400`: «одобрить всё» запрещено. Если статус не задан, берутся
только `candidate` — массовое действие не переподтверждает активные и отклонённые.

Генерация:

```json
{"min_co_purchase": 3, "limit": 500, "include_variants": true}
```

Возвращает `co_purchase`, `variant`, `skipped_rejected`, `skipped_hub`. Пары, отклонённые
человеком, повторно не предлагаются до истечения кулдауна. Товары-хабы (топ-1% по степени)
не притягивают новые рёбра.

## Workbench

Вкладка «Каталог v5» в `/admin`:

- метрики: всего, активных, кандидатов, покрытие каталога, stale share, концентрация хабов;
- фильтры и четыре пресета: **Все**, **Спорные** (кандидаты 0.5–0.75), **Истекают** (30 дней),
  **Структурные** (`variant_of`);
- таблица: источник, цель, тип, статус, провенанс, уверенность, доказательство, семейство,
  срок, версия;
- карточка выбранного ребра с evidence-чипами и решениями;
- массовые действия: подтвердить, отклонить, отложить; причина отказа обязательна;
- генерация и TTL-проверка.

## Догрузка новых позиций

В «Каталоге» есть кнопка **«Импорт»**: CSV с колонками `item_id, title, sku, product_group, available, category` (разделитель `,` или `;`). Excel сохраняется как CSV. Импорт делает upsert по `item_id` и не удаляет связи и алиасы.

Тот же импорт доступен из CLI, если нужно загрузить большой файл:

```bash
python3 analysis/import_items.py --csv new_positions.csv
python3 analysis/import_items.py --dataset new_dataset.xlsx
python3 analysis/import_items.py --dataset new_dataset.xlsx --orders
```

`--orders` обновляет клиентов/заказы и пересобирает co-purchase; после него нажмите «Сгенерировать». Полная перезагрузка `import_dataset.py` по-прежнему делает `TRUNCATE` и подходит только для чистой БД.

## Короткие имена

Полные названия товаров — юридические простыни, поэтому Workbench показывает короткое имя:

1. если в `item_aliases` есть запись для `item_id` — используется она;
2. иначе работает эвристика: срезаются юридические обёртки, упаковка, подставляются отраслевые сокращения (`GWS`, `M365`, `KES`, `KSOS`), бренд + версия.

Алиас задаётся в карточке ребра кнопкой «Алиас» или через API. Клик по названию в таблице разворачивает полное имя — его можно прочитать и скопировать. Поиск ищет и по алиасу, и по полному названию.

## Память отказов

Отклонённая пара `(from, to, type)` хранится с причиной и `rejected_until = now() + 90 дней`.
Генератор проверяет её перед вставкой, поэтому один и тот же кандидат не возвращается каждым
прогоном. Память ведётся по типу; пара может прийти с другим предполагаемым типом.

## Что осталось за рамками

- Перевод демо-графа с 3D на 2D и пять сценариев-кадров.
- LLM-типизация co-purchase пар и precision по типам.
- Полноценный split view с групповыми кандидатами и preview выдачи.
- Rule engine для `compatibility`, релизы-срезы и права по категориям.
- Пересчёт variant/new-product share остаётся в `analysis/baseline_official.py` и
  `analysis/evaluate.py`; Workbench показывает покрытие и состав рёбер, а не подменяет
  офлайн-метрику.
