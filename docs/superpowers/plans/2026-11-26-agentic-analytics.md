# План: агентная аналитика и авто-перестройка показов

**Цель:** замкнутый цикл «показ → событие → анализ → изменение стратегии/весов → новый показ».

**Не входит:** автоматическое изменение семантики связей, запретов и правил безопасности. Это только через ручную валидацию.

## T15. Хранение аналитики

**Задача:** хранить не только показы/клики/покупки, но и то, **какой стратегией** они получены.

**Данные:**

```text
recommendation_requests: + strategy, variant, audience
recommendation_events:   + strategy, audience
strategy_state:          audience, strategy, enabled, alpha, beta
settings:                auto_strategy, scoring_weights_b2b, scoring_weights_b2c
```

**Приёмка:**

- у каждого показа есть `strategy` и `audience`;
- клик/покупка наследуют стратегию из запроса;
- можно посчитать CTR и конверсию по стратегии и сегменту;
- старые события не ломаются (`default`).

## T16. Анализ аналитики

**Задача:** считать метрики по стратегиям и сегментам, а не только общий CTR.

**Метрики:**

- показы, клики, покупки;
- CTR и conversion с Beta/Laplace-сглаживанием;
- Fill Rate;
- пропуски по причинам;
- покрытие и новизна;
- дрейф: падение CTR после N показов.

**Приёмка:**

- `GET /v1/admin/analytics` отдаёт `by_strategy`, `by_audience`, `skip_reasons`;
- в админке видно, какая стратегия лучше для B2B и B2C;
- малые выборки не дают ложных выводов (сглаживание).

## T17. Изменение стратегии

**Задача:** авто-А/Б с контекстом.

**Руки:**

- `hybrid`;
- `popular`;
- `cold_start`;
- `use_case`;
- `solo_service`.

**Алгоритм:**

- старт с офлайн-приоров;
- epsilon-greedy или Thompson sampling;
- контекст: B2B/B2C/студент/отрасль;
- exploration не больше 20%;
- минимум 20–30 показов на руку;
- авто-откат при падении метрик;
- `auto` включается в админке.

**Приёмка:**

- при `auto=false` B2B идёт в `hybrid`, B2C — в `popular`;
- при `auto=true` распределение трафика меняется по результатам;
- решение и причина видны в админке;
- есть ручной откат.

## T18. Распределение весов

**Задача:** веса скоринга не одни на всех, а по сегментам и стратегиям.

**Что меняется:**

- `scoring_weights_b2b`;
- `scoring_weights_b2c`;
- `scoring_weights_default`;
- версия весов пишется в событие (`weights_version`).

**Авто-режим:**

- двигать веса только в заданном коридоре;
- не чаще одного раза в N показов;
- проверять на offline replay;
- откат при просадке.

**Приёмка:**

- B2B и B2C могут иметь разные веса;
- изменение весов видно в аудите;
- событие хранит версию весов;
- можно сравнить две версии по CTR/конверсии.

## T19. Авто-перестройка связей

**Задача:** не менять семантику, но подсвечивать проблемы.

**Действия:**

- связь с 500+ показами и 0 кликов → снизить вес;
- связь с высоким CTR/конверсией → поднять вес;
- товар с 1000+ показов и 0 кликов → в очередь «проверить карточку/связь»;
- спорные изменения → `quarantine` и человек.

**Приёмка:**

- авто-действия ограничены весами и карантином;
- подтверждение/отклонение связи остаётся у человека;
- все изменения в `admin_audit`.

## Порядок

1. T15 — хранение.
2. T16 — анализ.
3. T17 — стратегии.
4. T18 — веса.
5. T19 — авто-перестройка связей.

## Guardrails

- не менять правила безопасности и запреты;
- не подтверждать LLM-связи автоматически;
- не превышать 20% exploration;
- не менять веса без минимальной выборки;
- всегда иметь rollback.


## T20. Обратная связь по товарам и связям

- `internal/feedback`: Beta(1,19), CTR, multiplier 0.65–1.35.
- Буст/штраф применяется к кандидату до разнообразия.
- Событие хранит `feedback_multiplier`.
- Минимум 10 показов, иначе нейтрально.

## T21. Exploration-слот

- 10% запросов.
- Заменяется только последняя `cross_sell`-карточка.
- Renewal, upsell, analog и alternative не заменяются.
- Событие пишется с `source=exploration`.

## T22. Позиция клика

- `analytics.Record` находит rank показа и пишет его в клик.
- Это база для position-bias correction.
- Сырой CTR пока не корректируется; следующий шаг — IPS/rank prior.
