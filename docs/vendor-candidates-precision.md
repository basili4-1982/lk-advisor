# Точность кандидатов из внешнего слоя

**Что проверяли:** можно ли строить связи из `vendor_products` (вендор, линейка,
редакция, платформа) и не получится ли мусора, как при наивном матчинге
названий.

## Метод

1. Импортировали 16 внешних продуктов и сопоставили с 172 SKU каталога.
2. Сгенерировали кандидатов только между товарами без существующих связей:
   одна линейка и разные редакции → `variant_of`, разные продукты одной
   линейки без редакций → `adjacent_task`, одна платформа/редакция с разными
   платформами → `alternative`.
3. Ограничили по 10 SKU-пар на одну пару внешних продуктов, чтобы месячные и
   пользовательские SKU не залили реестр дублями.
4. Разметили кандидатов:
   - `confirmed` — одна линейка, разные непустые редакции;
   - `needs_review` — связь по платформам/разным продуктам линейки;
   - `invalid` — всё остальное.

## Результат

| Показатель | Значение |
|---|---:|
| Кандидатов | 47 |
| Подтверждено структурно | 26 |
| Требует проверки | 21 |
| Явно ошибочных | 0 |
| Precision подтверждённых | **55.3%** |
| Доля ложных связей | **0%** |

Распределение:

| Линейка | Тип | Кандидатов |
|---|---|---:|
| Google Workspace | variant_of | 21 |
| Dr.Web Security Suite | adjacent_task | 21 |
| 1С-Битрикс | variant_of | 5 |

## Примеры

Подтверждённые:

- Google Workspace Starter → Standard;
- Google Workspace Standard → Starter (обратное направление как вариант);
- 1С-Битрикс Стандарт → Старт;
- 1С-Битрикс Стандарт → Малый бизнес.

Требуют проверки:

- Dr.Web Desktop Security Suite → Dr.Web Server Security Suite;
- Dr.Web Desktop Security Suite → Dr.Web Enterprise Security Suite.

Это не «альтернативы», а дополнения: серверная и десктопная защита могут
использоваться вместе. Тип исправлен на `adjacent_task`, но совместимость
нужно подтвердить документацией вендора.

## Что это значит

1. **Слой entity resolution работает.** Ни одной ложной связи вида
   «Office → Small Office» из первого прототипа не осталось.
2. **Редакционные лестницы надёжны.** Все 26 `variant_of` — одна линейка,
   разные редакции. Это можно автоматически отправлять в каталог как
   кандидатов.
3. **Комплементарные связи требуют документа.** 21 пара Dr.Web семантически
   правдоподобна, но тип и совместимость должны подтверждаться страницей
   вендора или матрицей совместимости.
4. **47, а не 50.** После дедупликации по внешним продуктам осталось 47
   осмысленных пар. Догонять до 50 дублями месяцев и пользователей смысла нет.

## Вывод

Внешние данные дают новый слой знаний и не ломают реестр. Следующий шаг —
подтверждать `adjacent_task` по документации вендора, а не по разнице
платформ.

Воспроизведение:

```bash
python3 analysis/vendor_candidates_precision.py
```

## Подтверждение дополнений

21 кандидат `adjacent_task` (Dr.Web Desktop / Server / Enterprise) проверен по
странице вендора, указанной в evidence.

Результат:

| Показатель | Значение |
|---|---:|
| Проверено | 21 |
| Подтверждено страницей | **0** |
| Осталось на проверку | 21 |

Страница `drweb.ru` не называет линейки Desktop/Server/Enterprise и не содержит
явной фразы о совместном использовании. Значит, для `adjacent_task` нужна не
главная страница, а карточка продукта или матрица совместимости.

Это ожидаемый результат: внешние страницы хорошо дают платформы и редакции, но
комплементарные связи требуют более точного источника.

## Импорт реестра ПО

Добавлен импорт XML реестра:

```bash
curl -X POST localhost:8080/v1/admin/vendor-products/import-registry \
  -F file=@reestr.xml
```

Парсер терпим к структуре: ищет реестровый номер, название, правообладателя,
класс, ссылку, платформы и альтернативные названия по русским и английским
тегам. Официальную выгрузку с демо-стенда получить не удалось, поэтому
проверен на каноническом XML-примере.
