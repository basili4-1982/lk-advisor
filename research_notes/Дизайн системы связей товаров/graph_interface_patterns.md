# Graph Interface Patterns for Product Catalogs and Recommendation Graphs

Scope: public documentation, product tours and papers as of late 2026. Context assumed throughout: a product-relation graph with **817 public nodes today**, a **136k-offer** full catalog behind it, relation types `accessory / upgrade / alternative / bundle / adjacent task`, provenance from `manual / LLM / co-purchase`. All recommendations are for a demo that must impress *and* stay honest about coverage.

---

## What interaction patterns actually work: overview+filter, focus+context, ego networks, expand/collapse, cluster collapse, semantic zoom, minimap, search, filters, breadcrumbs, saved views, guided tours

### Takeaway
Mature graph tools converge on a much smaller pattern set than the design space suggests: **search-first entry → ego network with a degree control → capped expand → filter by type/property → fade-not-hide spotlight → saved named view**. "Overview first" is the textbook opener, but in catalog tools the real opener is a *thing* (a SKU, an account, a case), and the overview is a fallback for orientation.

### Cited Findings

**The canon**
- The Visual Information-Seeking Mantra is "overview first, zoom and filter, then details on demand", paired with seven tasks: overview, zoom, filter, details-on-demand, **relate**, **history**, **extracts** — [Shneiderman 1996, "The Eyes Have It"](https://www.cs.umd.edu/~ben/papers/Shneiderman1996eyes.pdf). The `relate` and `history` tasks are the ones a product graph is actually for, and `extracts` is why saved views/export matter.
- Semantic zoom (representation changes qualitatively with scale, not just a uniform affine transform) is formalised as abstraction functions + embedding functions + a scale-to-layer mapping (commonly `n = floor(log2 Z)`), with per-level constraints of no label overlap, no edge crossings and area proportionality; a paper on ontology graph visualisation reports a user study with "an increase in readability, visual clarity, and information clarity" — [Emergent Mind summary of semantic zoom](https://www.emergentmind.com/topics/semantic-zoom); [Semantic Zooming for Ontology Graph Visualizations (ACM)](https://dl.acm.org/doi/abs/10.1145/3148011.3148015) (claim taken from the paper's abstract snippet, not the full text).

**Neo4j Bloom — curated business views + saved scenes**
- A **Perspective** defines categorisation of entities, property visibility, relationship visibility, styling (color, icon, caption) and custom search phrases; one graph can be viewed through several Perspectives "each tailored for a different business purpose" (the docs' own example: a shipping perspective showing only orders, products, customers) — [Bloom Perspectives](https://neo4j.com/docs/bloom-user-guide/current/bloom-perspectives/bloom-perspectives/). Note the model: views are **authored centrally, not assembled by the visitor**.
- A **Scene** is saved state (filters, graph, visualisation, style), auto-saved on every change, switchable from a searchable Scene panel, shareable; style changes are scene-local unless saved back to the Perspective — [Scenes and sharing data](https://neo4j.com/docs/bloom-user-guide/current/bloom-tutorial/export-data/). Warning worth copying: "Scenes rely on node and relationship IDs… changes to this underlying data can cause data in saved Scenes to appear incorrectly if IDs are reused" (e.g. backup/restore).
- **Slicer** = property-range scrubbing over a timeline with playback, up to **5 ranges**, three playback modes (slide range to end / start of range to end / within range); while the Slicer is open you can only select/deselect nodes, and closing offers **Keep Scene** vs **X (restore)** — [Bloom Slicer](https://neo4j.com/docs/bloom-user-guide/current/bloom-tutorial/slicer/).
- **Graph pattern search** builds `(node)-[rel]->(node)` step by step with proactive suggestions, wildcards `(any)` for label and relationship, and property-value suggestions that **query the database** and therefore require indexes — [Bloom graph pattern search](https://neo4j.com/docs/bloom-user-guide/current/bloom-tutorial/graph-pattern-search/).
- Bloom's feature index confirms the rest of the interaction set: full-text search, edit graph data, GDS integration, Slicer, Scenes/sharing, deep links — [Bloom features in detail](https://neo4j.com/docs/bloom-user-guide/current/bloom-tutorial/). Freshness note: **standalone Bloom is deprecated as of 1 Jan 2027**; it continues as a Studio tool in Aura/Enterprise Studio/Desktop — [Bloom 2.38 docs home](https://neo4j.com/docs/bloom-user-guide/current/).

**Linkurious — the best-documented "don't explode the canvas" mechanics**
- **Expand** three ways (double-click, context menu, property panel) with **Selective Expand**: pick category and edge type, pick degree semantics — *Neighbors* (default), **Most connected**, **Least connected** — and cap "the maximum number of retrieved neighbors". Two thresholds (`advanced.expandThreshold`, `advanced.superNodeThreshold`) decide whether you get everything, a selective modal, or a full relationship/category picker. Super nodes are marked with a **plus badge and their connection count**; multi-expand is blocked when any selected node is a super node — [Expand nodes](https://doc.linkurious.com/user-manual/latest/expand/).
- **Filter panel**: Nodes/Edges tabs, per-category and per-property-value **counters**, a select-all icon and a hide toggle per value; hiding does not delete — hidden nodes stay visible **in light grey**; "Missing values" and "invalid values" rows are first-class; "Applied Filters" chips + Reset — [Filter panel](https://doc.linkurious.com/user-manual/latest/filter-panel/).
- **Node grouping**: rules group nodes sharing a property value (e.g. all nodes of category X with the same `city`); **one rule active at a time**; collapsed groups render as a grey circle with a **`x4` count badge** and category icon (mixed-category groups get a mixed icon); collapse/expand all from empty-canvas right-click; "all grouped nodes remain accessible, and all associated functionalities (such as expand, queries, and custom actions) remain available"; grouping repositions nodes and **unpins pinned nodes** — [Node grouping](https://doc.linkurious.com/user-manual/latest/nodegrouping/).
- **Timeline** filter: per node category / edge type choose *single date* or *date range* (open-ended ranges run to today); drag handles or type From/To; bars count items per bucket; a range-mode toggle to **"As at"** keeps only items existing on one date; zooming in far enough switches the chart from bars to **one row per item** — [Timeline](https://doc.linkurious.com/user-manual/latest/timeline/).

**Kumu — the storytelling vocabulary**
- **Focus**: hides everything except the selection, then walk in/out **by degree** with `+`/`-`, a number key for exact degrees, `esc` to restore; pre-definable in the view (`focus: #jack out 2`, multiple hubs comma-separated, `focus-direction: in|out|all`); **prompted mode** starts from a search box and builds the map from "name out 3" — [Kumu focus](https://docs.kumu.io/guides/focus).
- **Showcase** = the focus+context primitive: instead of hiding unselected data it makes it **translucent** (`foreground-opacity`, `background-opacity`), with modes `normal` (selection + connections between selected), `loose` (selection + neighbours), `strict` (selection only) — [Kumu showcase](https://docs.kumu.io/guides/showcase).
- **Views** are named bundles of decorations/filters/settings that can apply to several maps; **partial views** + a **view toggle control** let readers switch presentations with one click — [Views](https://docs.kumu.io/guides/views), [Partial views](https://docs.kumu.io/guides/partial-views), [Showcase control](https://docs.kumu.io/guides/controls/showcase-control).
- Kumu's own tour sells exactly the demo moves: filter to high-strength links, focus within 3 degrees, **showcase** to fade the rest, and **before/after views of the same map** — [Kumu tour](https://kumu.io/tour).

**Obsidian graph view — the cheapest credible implementation of the whole set**
- Filters: search term, tags, attachments, **"Existing files only"** (a note need not exist to be linked — i.e. unresolved links are ghost nodes), **orphans** toggle. Groups: colour by search query. Display: arrows on/off, **text fade threshold**, node size, link thickness, time-lapse animation. Forces: centre, repel, link, link distance. Local graph = ego network with a **depth slider** ("each level of depth will show notes connected to the notes revealed at the previous depth") — [Obsidian Graph view](https://obsidian.md/help/plugins/graph).
- Node size encodes degree: "the more nodes that reference a given node, the bigger it gets"; hover highlights that node's connections; click opens the note; right-click opens a context menu — [same](https://obsidian.md/help/plugins/graph).

**Component-level primitives (what you get for free vs. must build)**
- AntV G6 ships the supporting chrome as plugins: `minimap`, `timebar`, `toolbar`, `contextmenu`, `tooltip`, `legend`, `snapline`; and as behaviours: `collapse-expand`, `focus-element`, `hover-activate`, `fix-element-size`, `auto-adapt-label` — [G6 full docs (llms-full.txt)](https://g6.antv.antgroup.com/llms-full.txt). Note that `render` = `draw` + layout + `fitView`, and repeated data updates are batched until `draw`/`render` — [G6 FAQ](https://g6.antv.antgroup.com/en/manual/faq).
- Cytoscape.js gives label level-of-detail for free via `min-zoomed-font-size`: below that effective font size the label is not drawn at all — [Cytoscape.js style docs](https://js.cytoscape.org/).

### Inferences
- **Recommended stack for 817 nodes** (in priority order): (1) global search / command palette that jumps to a node; (2) ego network of the selected node with a **degree slider 1–3** (Kumu/Obsidian pattern) rather than a raw "expand all"; (3) **capped expand** with a "load 25 / 50 / all" choice and a category filter (Linkurious selective expand); (4) filter rail with **live counts per relation type and per source**, plus chips for applied filters; (5) **fade-not-hide** spotlight for the hovered/selected node (Kumu showcase) because hiding destroys the mental map; (6) saved named views ("Scenes"); (7) minimap only once the graph exceeds ~1.5 screens — below that it is decoration.
- **Breadcrumbs are the one pattern no reviewed tool ships as an expansion trail.** Every tool relies on undo/back and on the canvas itself (GitHub offers a per-row "Show paths" *query*, which is a different thing — it computes provenance, it does not record where the user went). For a demo that walks a path (offer → accessory → alternative → adjacent task) you must build an explicit path bar of chips, because the canvas cannot answer "how did I get here" and `history` is one of Shneiderman's seven tasks.
- Curated perspectives beat user-assembled views for a demo: Bloom's model (author the view, visitor explores inside it) is both less work and more impressive than a filter playground.
- Copy Bloom's **ID fragility warning** into the design: saved views/scenes should store *stable business keys* (SKU, relation id), not database row ids, or every re-import breaks the demo.

### Gaps
- No public, methodologically comparable usability study of "expand/collapse vs. filter-first" in a *product catalog* graph was found; the evidence base is vendor docs plus generic IVIS papers.
- No vendor documents breadcrumb/trail UX for graphs, so the recommendation above is inference, not evidence.
- Bloom's docs do not state a node/edge ceiling for a Scene; Linkurious publishes threshold *names* but not default values.

## When 2D is better than 3D, when 3D is genuinely useful, and the known failure modes of 3D force graphs

### Takeaway
Default to **2D**. 3D buys you one documented benefit — better long-term recall — and one aesthetic benefit: a bounded, non-planar cluster reads as a shape instead of a knot. It costs you occlusion, depth ambiguity, label legibility, picking accuracy and camera disorientation. Every product graph tool whose rendering I could verify (Bloom, Linkurious, Kumu, Obsidian, Sigma, Cytoscape, G6's default renderer, cosmos.gl) is **2D**; 3D exists mainly as an open-source demo genre.

### Cited Findings
- In a VR study of conventional 3D charts, "the results reveal a **decline in interpretation accuracy with 3D charts**, but improved long-term recall. Participants perceived limited success in accomplishing analytic tasks using this visualization method" (n and effect sizes not visible in the accessible abstract) — [Jeong et al., Journal of Visualization 28:239–253 (2025), published online 9 Dec 2024](https://link.springer.com/article/10.1007/s12650-024-01033-6).
- The same paper defines the core failure: "**Occlusion** refers to situations in 3D data visualization in which certain objects or data points are obscured or hidden by other elements within the scene. When multiple objects or data points are present… they may overlap or obstruct each other; users may struggle to perceive all relevant information clearly" — [same paper, PDF](https://rd.springer.com/content/pdf/10.1007/s12650-024-01033-6.pdf) (quote taken from the indexed PDF text snippet, since the PDF itself could not be fetched as text).
- The same literature review notes "the literature has discouraged the use of 3D graphs whenever possible (Wilke 2019), for instance, suggesting 'Use multiple 2D bar graphs instead of a single 3D bar graph'" — [same](https://link.springer.com/article/10.1007/s12650-024-01033-6). (Secondary citation of Wilke; I did not read Wilke's book.)
- A psychophysics study of 2D vs 3D bar charts (method of constant stimuli, 36 charts) was built around the hypothesis "that the just-noticeable-difference for 3D charts would be larger than for 2D charts" — i.e. 3D was expected to make magnitude discrimination coarser. Caveat: only the abstract snippet was accessible, which states the prediction; I did not read the reported result — [Perception & Motor Skills 92(2):495 (2001)](https://journals.sagepub.com/doi/10.2466/pms.2001.92.2.495).
- `3d-force-graph` (ThreeJS/WebGL + `d3-force-3d` or `ngraph`) documents its own control model as "**Left-click: rotate, Mouse-wheel/middle-click: zoom, Right-click: pan**" — three different meanings for three mouse buttons, none of them the 2D convention of drag-to-pan — [large-graph example](https://vasturiano.github.io/3d-force-graph/example/large-graph/); its largest bundled example is "**~4k elements**" — [repo README](https://github.com/vasturiano/3d-force-graph).
- In that library, links default to `linkOpacity 0.2` and `linkWidth 0`, where width 0 renders a ThreeJS `Line` "whose width is **constant (1px) regardless of distance**" — so at depth, edges neither thicken nor fade predictably and the primary relational cue is a 20%-opacity hairline — [README link styling table](https://github.com/vasturiano/3d-force-graph).
- AntV G6 supports 3D layouts (`D3Force3D`, "numDimensions: fixed to 3", adds z-axis centre/collision/radial/coordinate forces) but treats them as one layout among many, not the default — [G6 full docs, D3Force3D](https://g6.antv.antgroup.com/llms-full.txt).
- The fastest large-graph engines are explicitly 2D: cosmos.gl advertises "Beyond 1 million nodes and edges" with a GPU force simulation and renderer — [cosmos.gl](https://cosmos.gl/). Sigma.js v4 is WebGL 2D with a single stage canvas plus a transparent mouse layer — [Sigma rendering concepts](https://www.sigmajs.org/concepts/rendering/).
- 3D does have a legitimate demo role in the same ecosystem: `3d-force-graph` ships directional arrows, directional moving particles, curved links, text-as-nodes, image nodes and HTML-in-nodes examples — useful for *explaining* a relation type on screen — [README examples list](https://github.com/vasturiano/3d-force-graph).

### Inferences
- **Use 2D for everything that must be read**: labels, provenance, confidence, audit, comparison. Use 3D only for (a) a bounded "hero" subgraph of roughly **≤300–500 nodes** where the point is shape, not reading; (b) an optional toggle, never the default; (c) an auto-rotating *screensaver* state for a booth/kiosk, which is the one context where camera motion costs nothing.
- Concrete 3D failure modes to design against, in the order they will bite in a catalog demo:
  1. **Occlusion** — the alternative you needed is behind the bundle cluster. Mitigation: on hover, isolate (dim everything not 1 hop away) and raise the hovered node's depth bucket.
  2. **Depth ambiguity** — "is this edge in front of or behind that node?" Mitigation: size-by-depth + fog + never rely on line crossings; if a judgement depends on it, it belongs in 2D.
  3. **Label illegibility** — billboarded labels overlap at distance and shrink with perspective. Mitigation: density-culled labels, labels only for the focused node + neighbours.
  4. **Camera disorientation / loss of "up"** — the rotate/zoom/pan mouse mapping above replaces the 2D convention of drag-to-pan, so the first 30 seconds are spent learning the camera rather than reading the data. Mitigation: no free orbit in the demo path; preset camera positions ("front / top / isometric") with tweened transitions and a persistent "reset view".
  5. **Motion discomfort** — the only *citable* motion-comfort work I reached is VR/stereo-display research (Shibata et al. 2011, "The zone of comfort: predicting visual discomfort with stereo displays", J. Vision 11 — seen only as a reference in the Jeong et al. bibliography, not read). On a desktop 3D force graph the realistic symptom is disorientation and "where did my node go", not nausea; treat nausea as a VR/headset risk, not a laptop risk. **This distinction is my inference, not a sourced finding.**
  6. **Picking errors** — the node you click is not the node you meant. Sigma solves this in 2D with a hidden picking framebuffer rendered at half resolution (`pickingDownSizingRatio` default 2) — [Sigma rendering](https://www.sigmajs.org/concepts/rendering/); in 3D the same trick works but the *user's* targeting is the weak link.
- **Honesty angle**: if the demo opens in 3D, a technical buyer reads it as "style over substance" — the same buyer knows Bloom, Linkurious and Kumu are 2D. The stronger move is a 2D graph that is visibly *fast and legible*, plus one deliberate 3D "shape" view labelled as such.

### Gaps
- I could not access a controlled study of **3D node-link graphs specifically** (as opposed to 3D bar/scatter charts) measuring occlusion-induced error rates; the classic "Visualizing Graphs in Three Dimensions" (Ware & Mitchell) abstract was behind CAPTCHA/paywall on every route tried. Treat the 3D evidence here as adjacent-domain evidence.
- No public benchmark of `3d-force-graph` frame rates vs. node count beyond the ~4k example.

## How Bloom, Linkurious, Graphileon, Kumu, Obsidian, GitHub, Sigma.js, Cytoscape.js, AntV G6 and 3d-force-graph handle labels, edge bundling, clustering, large graphs and cross-page links

### Takeaway
The binding constraint everywhere is **labels**, not nodes. Every mature library either culls labels by zoom/size (Cytoscape `min-zoomed-font-size`, Sigma density-based culling + SDF atlas) or moves them off-canvas (tooltip/panel). Clustering is a **first-class data operation** in the tools that sell to non-developers (Kumu cluster, Linkurious grouping, G6 combo, Cytoscape compound). **Edge bundling is essentially absent from commercial product-graph tools**; it appears in the infovis/d3 tradition and needs a real hierarchy to be honest.

### Cited Findings

**Labels**
- Sigma v4 renders labels **on the GPU via an SDF-based text atlas** (glyph bitmaps pre-rasterised into a texture atlas, each character a textured quad), which keeps labels crisp at any zoom; it also exposes a density-based culling mode where `edgeLabelAnchors: "allNodes"` uses "the same density-based culling as node labels" — [Sigma rendering](https://www.sigmajs.org/concepts/rendering/), [Sigma settings](https://www.sigmajs.org/reference/settings/).
- Sigma separates a coarse categorical **depth layer** (`depthLayers` buckets: custom WebGL layer, edges, edge labels, backdrops, nodes, label attachments, node labels) from a continuous `zIndex`; moving an item between buckets does not reprocess the graph, changing `zIndex` does — a concrete design for "bring the hovered node and its label to the front" — [Sigma rendering](https://www.sigmajs.org/concepts/rendering/).
- Cytoscape: "Labels: drawing labels is expensive… Consider setting `min-zoomed-font-size` in your style so that when labels are small — and hard to read anyway — they are not rendered"; backgrounds and outlines make labels more expensive; and on edge labels it advises "Consider not having labels for edges" — [Cytoscape performance](https://js.cytoscape.org/).
- Bloom styles captions per Perspective (color, icon, caption) rather than letting each user style freely — [Bloom Perspectives](https://neo4j.com/docs/bloom-user-guide/current/bloom-perspectives/bloom-perspectives/).
- Obsidian exposes a **text fade threshold** slider — labels dissolve continuously as you zoom out — [Obsidian Graph view](https://obsidian.md/help/plugins/graph).

**Clustering / grouping / collapse**
- Kumu **cluster** creates *new elements* for each value of a chosen field and draws connections from the original elements to those value-elements — i.e. clustering is a data transform, not a visual bubble; it turns a flat spreadsheet into a bipartite map (people → organisations) — [Kumu cluster](https://docs.kumu.io/guides/clustering).
- Linkurious grouping is rule-based on a property, one rule at a time, with count badges and "collapse all / expand all"; grouped nodes keep expand, query and custom actions — [Node grouping](https://doc.linkurious.com/user-manual/latest/nodegrouping/).
- G6 calls it **combo** (compound grouping) and pairs it with the `collapse-expand` behaviour and `drag-element` — [G6 full docs](https://g6.antv.antgroup.com/llms-full.txt).
- Cytoscape **compound nodes** exist and work, but are explicitly a performance tax: "Compound nodes make style calculations and rendering more expensive. If your graph does not require compound nodes, you can improve performance by not using compound parent nodes" — [Cytoscape performance](https://js.cytoscape.org/).
- Obsidian's "groups" are *not* clusters — they are colour rules over search queries, with no collapse — [Obsidian Graph view](https://obsidian.md/help/plugins/graph).

**Edge bundling**
- Hierarchical edge bundling (Holten 2006) routes adjacency edges along a hierarchy so they bundle where they share ancestors, "decreas[ing] the clutter usually observed in complex networks" and revealing implicit parent-level adjacency; the analogy given is bundling electrical wires and fanning them out at the terminus — [Data-to-Viz: hierarchical edge bundling](https://www.data-to-viz.com/graph/edge_bundling.html), [Holten, IEEE TVCG 12(5), 2006](https://ieeexplore.ieee.org/document/4015425).
- Bundling is not free of distortion: "due to strong edge attraction, bundled results often show unnecessary curvature and tangling at bundle intersections. **Inappropriate bundling may fail to reveal true data patterns and even mislead users**" — [LEB: Visualizing large graphs by layering and bundling graph edges, The Visual Computer (2018)](https://link.springer.com/article/10.1007/s00371-018-1509-7). Caveat: this quote comes from the publisher's abstract snippet as returned by search, not from the full text, and the paper is about a *parameterised* bundling method rather than a refutation of bundling.
- None of Bloom, Linkurious, Kumu, Obsidian or G6's documented feature sets include edge bundling. Linkurious offers **edge grouping** instead: enabling a type groups "all the parallel edges with the same direction of that type", the caption next to the edge type shows **how many edges are in the group**, and selecting the group opens a panel with the type, the count, and **aggregated properties** — numeric properties rolled up with Sum / Average / Minimum / Maximum (with the count of valid values used), date properties reduced to **FIRST DATE** and **LAST DATE** — [Edge grouping](https://doc.linkurious.com/user-manual/latest/edgegrouping/). This is aggregation-as-truth: the group is a *summary you can open*, not a bundle you have to trust.

**Large graphs — what the vendors actually claim**
- Sigma: "handles large graphs well out of the box. But with **hundreds of thousands of edges**, some choices start to matter a lot." Concrete findings: disabling edge antialiasing is "up to **x5 performances gain** on the whole GPU rendering process"; semi-transparency is much slower than opaque, so "prefer a solid color close to the background over an `opacity` lower than 1"; **every edge pays the vertex cost of the heaviest registered path**, and the defaults register `pathLoop` (66 vertices) so "by default every straight edge is drawn with 66 vertices"; edge events are off by default because "edge picking requires drawing all edges a second time" — [Sigma performance](https://www.sigmajs.org/how-to/technical/performance/).
- Sigma, on where the time goes: "On big graphs, frames are usually **fragment-bound**… In our benchmark, halving the vertex count only shaved **~6%** off the frame time, while opacity and antialiasing changes moved it far more, **up to ~80%** shaved in some case" — [same](https://www.sigmajs.org/how-to/technical/performance/).
- Cytoscape's tuning list, in its own "descending order of significance": animations off; labels off or on-demand; solid `haystack` edges instead of beziers/dashes; no arrows unless they carry meaning ("opaque edges with arrows are more than twice as fast as semitransparent edges with arrows"); simplify node style (background images, borders); `pixelRatio: 1`; avoid compound nodes; `hideEdgesOnViewport`; `textureOnViewport`; avoid many node overlays; recycle instances — [Cytoscape performance](https://js.cytoscape.org/).
- cosmos.gl: GPU force simulation + rendering, "keeping hundreds of thousands of points and millions of links within reach of your browser", with public examples at 5,570 authors/16,067 links, 1,890,815 points/2,315,222 road links, and 10,000,000 points — [cosmos.gl](https://cosmos.gl/).
- Bloom: generating a Perspective by full database scan is slow above "**> 10,000,000 nodes and relationships combined**", where a quick scan is offered instead — the only vendor-published scale number found — [Bloom Perspectives](https://neo4j.com/docs/bloom-user-guide/current/bloom-perspectives/bloom-perspectives/).
- G6 batches: "G6 merges differences and updates the canvas uniformly after `draw` or `render` for multiple data updates to improve performance" — [G6 FAQ](https://g6.antv.antgroup.com/en/manual/faq).

**Cross-page links (from a product page / email / ticket into the graph)**
- Bloom **deep links** accept `search`, `perspective` and `run=true|false`: the link pre-fills the search box, selects the Perspective (which also selects the database), and optionally executes the first query suggestion — [Bloom deep links](https://neo4j.com/docs/bloom-user-guide/current/bloom-tutorial/deep-links/). This is the canonical "open the graph *at this thing*" pattern.
- GitHub's dependency graph is a **table with graph affordances**, not a canvas: dependencies/dependents per repository, version, license, which manifest pulled it in, vulnerability status; transitive provenance via a "**Show paths**" action per row; search; "sorted automatically with vulnerable packages at the top" — [About the dependency graph](https://docs.github.com/en/code-security/supply-chain-security/understanding-your-software-supply-chain/about-the-dependency-graph).
- GitHub's *network* graph is the honest-truncation pattern: it "shows up to **100 of the most recently pushed-to branches**", with "to see older branches, click and drag within the graph" and an explicit keyboard-shortcuts popup — [Understanding connections between repositories](https://docs.github.com/en/repositories/viewing-activity-and-data-for-your-repository/understanding-connections-between-repositories).
- Obsidian inverts the direction: the **local graph sits beside the note** you are reading, at a chosen depth — the graph is a sidebar widget on a document page, not a destination — [Obsidian Graph view](https://obsidian.md/help/plugins/graph).
- Graphileon's model is application composition: "applications are graphs" made of function-nodes wired by trigger-relationships, with UI widgets (`AgGridView`, `ChartView`, `MapView`, `TimeLineView`, `CalendarView`, `NetworkView`, `InputView`) and backend functions (`Timer`, `Query`, `I/O`, `Request/API`, `Iterate`, `Email`), plus app-level RBAC and multilingual UI — [Graphileon Cloud](https://graphileon.com/graphileon-cloud/), [graphileon.com](https://graphileon.com/). The takeaway is architectural: the graph view is one widget among several, sharing selection with a grid and a timeline.

### Inferences
- For a product catalog, **skip edge bundling**. Hierarchical bundling needs a hierarchy that users believe in; a merchandising taxonomy is real but shallow, and the LEB paper's warning ("may… even mislead users") is exactly the risk you cannot take in a demo about *trustworthy* relations. Cluster-by-family + edge grouping of parallel same-type edges gets 80% of the decluttering for 10% of the risk.
- Labels: budget for **one** label layer at rest (node captions, density-culled), and put edge labels in the side panel / hover tooltip. If edge type must be visible at rest, encode it in colour and encode it again in the legend — do not draw text on edges at 817 nodes.
- Adopt Sigma's depth-layer idea conceptually even in another library: hovered node + its label go to a "top" bucket; everything else stays put. This preserves the mental map, which full re-layout does not.
- The Graphileon widget model is the right target architecture for the workbench: `NetworkView` + `AgGridView` + `TimeLineView` sharing one selection state, so the graph never has to do table jobs.

### Gaps
- No vendor publishes a nodes/edges-vs-FPS table. Sigma's numbers are relative ("x5", "~6%", "~80%") on unnamed datasets; cosmos.gl's are example sizes, not benchmarks.
- Linkurious' `expandThreshold` / `superNodeThreshold` defaults are not documented publicly (they are admin-configurable), so "cap at N" cannot be sourced.
- Graphileon's help centre returned HTTP 500 on every route tried; its interaction details (selection sync, NetworkView options) could not be verified from primary docs.

## Handling pagination and partial graphs: external links, ghost nodes, stubs, "expand to page", breadcrumbs, previews

### Takeaway
The honest way to show a 136k catalog is **three explicit devices plus one trail**: (1) an **aggregate node** carrying a count ("+1,204 offers"), (2) **capped expand** with an explicit "showing 50 of 1,204" and a *load more / expand to page* action, (3) **ghost/stub nodes** for neighbours that exist but are not loaded, drawn in a visually distinct "not here yet" style; and (4) a **breadcrumb of the expansion path** so the partial view is explicable. Never silently truncate.

### Cited Findings
- Linkurious is the only tool with a fully documented truncation contract: expand returns all neighbours only below `expandThreshold`; between the two thresholds you get a **Selective Expand** modal; above `superNodeThreshold` the node is badged with its connection count and the modal lists every relationship and category; and the modal lets you set "the maximum number of retrieved neighbors" and choose *most connected* / *least connected* to decide *which* neighbours you get — [Expand nodes](https://doc.linkurious.com/user-manual/latest/expand/).
- Linkurious' grouping keeps counts visible on the collapsed mark (`x4` badge), so a collapsed cluster is never a mystery — [Node grouping](https://doc.linkurious.com/user-manual/latest/nodegrouping/).
- GitHub network graph caps at 100 branches and says so in the docs, with a gesture ("click and drag") to reach older ones — [GitHub docs](https://docs.github.com/en/repositories/viewing-activity-and-data-for-your-repository/understanding-connections-between-repositories).
- GitHub dependency graph answers "why is this here?" with a **path view** rather than by drawing the path by default ("click … then 'Show paths', to see the transitive path which brought in the dependency") — [About the dependency graph](https://docs.github.com/en/code-security/supply-chain-security/understanding-your-software-supply-chain/about-the-dependency-graph).
- Obsidian's "**Existing files only**" toggle is a ghost-node switch: a link can point at a note that does not exist, and the graph can either show those unresolved targets or hide them; a separate "orphans" toggle shows/hides nodes with no links at all — [Obsidian Graph view](https://obsidian.md/help/plugins/graph).
- Kumu can drop unconnected elements wholesale with `ignore-orphans: true` in the view settings — [Kumu filter](https://docs.kumu.io/guides/filter).
- Bloom's saved Scenes store IDs; if IDs are reused (backup/restore) a saved partial graph "may appear incorrectly" — a direct warning that *partial* views are the most fragile thing you can persist — [Scenes and sharing data](https://neo4j.com/docs/bloom-user-guide/current/bloom-tutorial/export-data/).
- Bloom deep links make a partial graph addressable: the URL carries the search that reproduces it — [Deep links](https://neo4j.com/docs/bloom-user-guide/current/bloom-tutorial/deep-links/).

### Inferences
- **Ghost node spec** (nothing in the literature names this, so treat as design proposal): dashed 1px outline, no fill, count inside or beside it, label "1,204 more offers", and a single click target that opens a **paged list** rather than expanding on the canvas. Distinguish two kinds: *known-unloaded* (we have the data, we chose not to draw it) and *external* (a supplier page, a competitor SKU, an out-of-catalog reference) — external gets an outward arrow glyph and opens a new tab.
- **"Expand to page"** should be a *navigation* action, not a canvas action: it deep-links to the table view pre-filtered by the same predicate (e.g. `/offers?family=…&relation=accessory&source=co-purchase`), with the same breadcrumb preserved. This is the only way to keep the graph honest at 136k while still letting someone reach row 900.
- **Breadcrumb spec**: chips of the traversal (`Камера X › Аксессуары (12) › Штатив Y`), each chip a click that *collapses everything after it* and restores that exact state — i.e. breadcrumbs double as undo for expansion. Include counts in the chips; a chip without a count hides the fact that you are in a partial view.
- **Preview on hover, not on click**: hover shows a card (photo, price band, relation chips with source badges); click pins/focuses. This is the only pattern that lets a demo move fast without a wall of modals.
- Coverage honesty must be **in the chrome, not in a footnote**: a persistent strip "817 of 136k offers · relations: 412 manual / 288 LLM (unreviewed) / 117 co-purchase (30d)". Every partial view inherits it.

### Gaps
- No public source describes ghost/stub-node conventions for product graphs; the closest primitives are Obsidian's unresolved links and Linkurious' super-node badge. Everything in the "ghost node spec" above is design inference.
- No documented pattern for "expand to page" (graph → filtered table deep link) in any reviewed tool; Bloom's deep links go the other direction (page → graph).

## Making a graph demo tell a story: layers (segment, family, time), annotations, presets, before/after, spotlight, a short guided scenario

### Takeaway
A convincing demo is a **sequence of named states**, not a sandbox. Build 4–6 presets (saved views), each a *sentence*: "this camera has 9 accessories, 3 of them only from co-purchase"; layer toggles for provenance and time; a spotlight that fades rather than hides; annotations pinned to nodes/edges; and one 60–90 second scripted path with camera transitions and a visible "step 2 of 5".

### Cited Findings
- Bloom's **Scenes** are exactly presets: named, auto-saved, searchable, shareable state including filters, graph, visualisation and style — [Scenes and sharing data](https://neo4j.com/docs/bloom-user-guide/current/bloom-tutorial/export-data/).
- Bloom's **Slicer** is the time layer with a *playback* button — nodes appear/disappear as the range sweeps — plus three playback modes and a Keep/Restore choice on close. That is a demo primitive, not just a filter — [Slicer](https://neo4j.com/docs/bloom-user-guide/current/bloom-tutorial/slicer/).
- Linkurious' **Timeline** offers a per-item row view when you zoom in (one bar/point per node or edge, grouped by category) — the "show me the actual events" zoom level that a bar chart cannot give — [Timeline](https://doc.linkurious.com/user-manual/latest/timeline/).
- Kumu sells **before/after views of the same map** as a first-class use of views, plus focus and showcase for "reduce the complexity… while you introduce the basic concepts" — [Kumu tour](https://kumu.io/tour), [Focus](https://docs.kumu.io/guides/focus).
- Kumu ships "a built-in **presentation builder** and publishing platform" for sharing finished maps — [kumu.io](https://kumu.io/). Its views can be **layered** via `@import` and switched by a **view toggle control**, which is the mechanism behind a "step through the story" UI — [Partial views](https://docs.kumu.io/guides/partial-views), [Showcase control](https://docs.kumu.io/guides/controls/showcase-control).
- Linkurious separates **three** layers that are usually conflated, and the split is worth copying verbatim: *graph data* (nodes/edges, editable, written back to the DB), *annotations* ("explain your findings directly on the graph, next to the nodes and edges they refer to… displayed on the visualization itself, rather than in a side panel… stored with the visualization. They are not part of your graph data and are **never written back to the graph database**"), and *comments* (a panel per visualisation, visible to anyone with access, only the author can delete their own, comments survive a user's deletion, `@` mentions notify by email, and the visualisation must be saved before commenting) — [Annotations](https://doc.linkurious.com/user-manual/latest/annotations/), [Comments panel](https://doc.linkurious.com/user-manual/latest/visualization-comments-panel/). The demo-relevant consequence: annotations are **free** — you can write the story onto the graph without polluting the 817-node dataset or the 136k catalog.
- Spotlight semantics: Kumu's showcase fades the unselected to `background-opacity` (default suggestion 0.1) instead of removing it, with `normal/loose/strict` scopes — [Showcase](https://docs.kumu.io/guides/showcase).
- Graphileon's premise is that a dashboard is composed of widgets wired together ("applications are graphs… nodes that represent functions, connected by relationships that represent triggers") — so a "guided scenario" can literally be a chain of views — [Graphileon Cloud](https://graphileon.com/graphileon-cloud/).

### Inferences
- **A 5-beat scenario for this catalog** (each beat = one saved preset + one sentence of narration):
  1. *One offer, alone.* Focus a single SKU; neighbours fade in at 1 hop. Say the number out loud: "817 offers in the public graph, 136k in the catalog — this is one of them."
  2. *The five relation types, one at a time.* Toggle relation-type filters so `accessory`, `upgrade`, `alternative`, `bundle`, `adjacent task` each light up in turn with its own colour and its own count in the legend. This is the "we have a schema, not a hairball" beat.
  3. *Provenance.* Turn on the source layer: manual edges solid at full opacity, LLM edges solid but with a midpoint `LLM` badge, co-purchase edges thinner with a date in the popover. Say the review ratio out loud. This is the honesty beat and it is also the most impressive one, because nobody else shows it.
  4. *The surprise.* Spotlight a node whose best "upgrade" edge came from co-purchase, not from the manual set — the graph found something merchandisers missed. Fade, don't hide.
  5. *Scale, honestly.* Click the aggregate/ghost node: "1,204 more offers in this family — not drawn, here is the paged list." Then jump to the table via expand-to-page. Ends on credibility, not on a fake galaxy.
- **Before/after must be the same layout.** Toggle a layer (manual-only ↔ +LLM ↔ +co-purchase) with positions frozen; if the layout re-runs, the audience sees a different graph and concludes the data is noise. Pre-compute and persist positions for the 817 nodes.
- **Annotations** should be attached to *edges* at least as often as nodes — the interesting claim in a product graph is "why are these two related", so a sticky note on an edge ("co-purchase spike, Black Friday") is worth more than a note on a node.
- Guided tour mechanics: a bottom bar with `1/5`, next/prev, and "exit tour"; camera tweens ≤600 ms; disable free pan/zoom during the tour (or the presenter will lose the frame); `esc` exits and restores the pre-tour scene (Bloom's Keep/Restore pattern).

### Gaps
- No public data on whether guided tours improve comprehension vs. free exploration in graph tools; the "presentation builder" claim is marketing copy on Kumu's homepage, not evidence.
- Linkurious' *sticky notes* (as distinct from annotations and comments) were only visible as a navigation entry and not read in full, so their persistence scope and permissions are unverified.

## What should stay in tables/lists rather than the graph: editing, bulk actions, comparison, audit

### Takeaway
Anything with a **column, a sort order, a checkbox, or an author** belongs in a table. The graph answers "what is connected to what and why"; the table answers "which of these 40, and in what order, and who changed it". The strongest published evidence is that adjacency **matrices** beat node-link diagrams on reliability across a broad task set, and that GitHub's dependency product is a table with a "Show paths" affordance rather than a canvas.

### Cited Findings
- A crowd-sourced study (n=150) comparing node-link, adjacency-matrix and bipartite layouts on large directed networks (500-node overview tasks; 50- and 20-node detail tasks) found "**bipartite layouts are beneficial for revealing the overall network structure, while adjacency matrices are most reliable across the different tasks**" — [Comparative Evaluation of Bipartite, Node-Link, and Matrix-Based Network Representations (arXiv 2208.04458)](https://arxiv.org/abs/2208.04458).
- An earlier large-participant online study "revealed **statistically significant differences**" between node-link and matrix representations across a broad spectrum of tasks on a large dataset typical of real networks — [Revisited Experimental Comparison of Node-Link and Matrix Representations (arXiv 1709.00293)](https://arxiv.org/abs/1709.00293).
- GitHub's dependency graph is a **table**: rows carry version, license, the manifest that included the dependency, and vulnerability status; sorting is automatic with vulnerable packages first; the graph appears only as an on-demand "Show paths" — [About the dependency graph](https://docs.github.com/en/code-security/supply-chain-security/understanding-your-software-supply-chain/about-the-dependency-graph).
- Bloom supports **editing graph data** and **CSV export** of a scene (all-in-one, or separate node/relationship files, with label/type/property selection) — i.e. the tool itself hands editing/analysis off to other surfaces — [Bloom features](https://neo4j.com/docs/bloom-user-guide/current/bloom-tutorial/), [Scenes and sharing data](https://neo4j.com/docs/bloom-user-guide/current/bloom-tutorial/export-data/).
- Linkurious splits inspection and editing into panels (inspect data, edit properties and categories, create/delete nodes and edges) alongside the canvas, and keeps **annotations** (notes pinned on the graph, never written back to the DB) in a third, separate layer — [Linkurious manual](https://doc.linkurious.com/user-manual/latest/edit/), [Annotations](https://doc.linkurious.com/user-manual/latest/annotations/).
- Graphileon composes `AgGridView` (a data grid) next to `NetworkView` in the same application, sharing the graph store — the clearest published statement that grid and network are peers, not alternatives — [Graphileon Cloud](https://graphileon.com/graphileon-cloud/).
- In-canvas chrome is expensive: Cytoscape warns that "overlays can not be cached" and that many simultaneous overlays hurt performance, and that background images/borders on nodes are costly — a rendering-level argument for keeping forms and buttons out of the canvas — [Cytoscape performance](https://js.cytoscape.org/).

### Inferences
- **Split view, shared selection** is the right workbench shape: graph on the left, table on the right, one selection model, one filter model. Clicking a row focuses the node; brushing nodes filters the table. Graphileon's widget model and Linkurious' panels both imply this; neither ships it as a single documented pattern.
- Keep in **tables/lists**, never in the canvas: bulk relation edits; accept/reject of LLM-suggested edges (a QA queue with confidence, evidence snippet, and reviewer); price/stock/lead-time columns; comparison of 2–5 offers (a spec matrix, or an adjacency matrix for relation comparison); audit trail (who changed which edge, when, from what source); import/export; permissions.
- **Comparison specifically**: for 3–5 products a spec table wins outright; for "which of these 40 accessories fit X" use a **matrix** (offers × relation types) — this is where the matrix literature above applies directly, and it also solves the "hairball of 40 spokes" problem without any layout work.
- Audit belongs in a **timeline list with diffs**, not in a time-sliced graph. The graph can *link* to it ("this edge was created 12 Mar by LLM, accepted by …") via a provenance popover, but the log itself is rows.

### Gaps
- No study compares graph-vs-table for **catalog/merchandising** tasks specifically; the matrix evidence comes from generic network-task studies.
- No public source on optimal split-view proportions or selection-sync UX for graph+table workbenches.

## Visual encodings that work for relation type, confidence, status, direction, time, family, segment, solo nodes and external links

### Takeaway
Spend the encoding budget deliberately: **hue = relation type** (max 5–6, we have exactly 5), **width/opacity = confidence**, **ring + midpoint badge = provenance/status**, **arrowhead only for genuinely directional types**, **a bundle node (not an edge) for bundles**, **a parked rail for solo nodes**, **a distinct outline + outward glyph for external links**. Never let two channels encode the same variable, and never rely on colour alone.

### Cited Findings
- Linkurious exposes a fixed, documented encoding vocabulary, one page per channel: **captions**, **node colour**, **node size**, **icons**, **edge colour**, **edge size** — plus a filter panel that counts by category and value. That is the whole sanctioned channel set for a mature investigative tool — [Captions](https://doc.linkurious.com/user-manual/latest/captions/), [Nodes color](https://doc.linkurious.com/user-manual/latest/node-color/), [Nodes size](https://doc.linkurious.com/user-manual/latest/node-size/), [Icons](https://doc.linkurious.com/user-manual/latest/icons/), [Edges color](https://doc.linkurious.com/user-manual/latest/edge-color/), [Edges size](https://doc.linkurious.com/user-manual/latest/edge-size/). Note what is *not* offered as a documented channel: there is no edge pattern/dash page and no animation page — colour, size, icon and caption are the whole vocabulary.
- Linkurious' **captions** are not a fixed field: the Design panel lists node (and separately, edge) properties, you pick which to show, and "Linkurious Enterprise will use the properties in the _order_ they appear in the list", rendering e.g. `Quality Event Planner - United States`; "if a node doesn't have a property, Linkurious Enterprise won't show a caption for that property for that node" — so captions are a composed, ordered, tolerant string — [Captions](https://doc.linkurious.com/user-manual/latest/captions/). This is the cheapest way to make 817 labels carry meaning (`Brand · Model · 128 GB`) without adding visual channels.
- Linkurious **node size** supports a `Dynamic` mode with Linear/Logarithmic scale functions over a property (their worked example: 140 companies sized by `funding_total` to answer "who got the biggest round"), with an explicit warning: "when dynamic sizing is enabled, the layout is **recomputed every time a visualization is opened** (except if you have 'incremental expand' enabled)" — [Nodes size](https://doc.linkurious.com/user-manual/latest/node-size/). Size-by-metric and stable layout are in direct tension in a real product.
- Kumu's data-driven decorations change "size, color, line thickness"; its own copy warns "the possibilities are endless, but **don't go too crazy… nobody wants to look at an ugly map**", and it recommends sizing elements by in/out degree and colouring by sector — [Kumu tour](https://kumu.io/tour).
- Obsidian: **arrows toggle link direction** globally; node size = degree; link thickness is a single global slider; colour comes from query-based groups — [Obsidian Graph view](https://obsidian.md/help/plugins/graph).
- `3d-force-graph` ships directional **arrows** and directional **moving particles** as distinct examples, plus gradient links, curved links and text-as-nodes — evidence that direction and flow are commonly encoded as animation/arrowheads, and that these are optional extras rather than defaults — [README examples](https://github.com/vasturiano/3d-force-graph).
- Cost of these channels (2D canvas): arrowheads "are expensive to render… consider not using them if they do not have any semantic meaning"; "**opaque edges with arrows are more than twice as fast as semitransparent edges with arrows**"; dotted/dashed edges are "much more expensive"; `haystack` (straight) edges are the cheapest — [Cytoscape performance](https://js.cytoscape.org/). In WebGL: semi-transparency is expensive, and "prefer a solid color close to the background over an `opacity` lower than 1" — [Sigma performance](https://www.sigmajs.org/how-to/technical/performance/).
- Accessibility is an explicit concern in the graph-viz literature: keyboard navigation, screen-reader support, colour/contrast choices and animation management are called out as first-class requirements — [Cambridge Intelligence, graph visualisation learning hub](https://cambridge-intelligence.com/learn/graph-visualization/).
- Semantic zoom's per-level constraints (no label overlap, no edge crossings, area proportionality) imply that encodings must **survive** a level change, not be re-invented per level — [Emergent Mind, semantic zoom](https://www.emergentmind.com/topics/semantic-zoom).

### Inferences
- **Concrete mapping for the five relation types** (2D, light background):
  - `accessory` — solid, thin, neutral-warm hue (e.g. amber), arrow *from* the parent offer *to* the accessory (it is directional: the accessory belongs to the parent).
  - `upgrade` — solid, medium width, arrowhead, cool hue (blue/indigo). Direction is the point ("this replaces that").
  - `alternative` — **no arrowhead**, same hue as `upgrade` but a lighter tint, and *no dash at rest* (dashes are a documented cost channel in both Sigma and Cytoscape; save them for the focused subgraph). Symmetric relations drawn with arrows are a lie — this is the one place where dropping the arrowhead matters more than any other styling decision.
  - `bundle` — **not an edge**: a small square/hex "bundle" node with a count, connected by thin spokes. A bundle is a hyperedge; drawing it as pairwise edges invents relations that do not exist.
  - `adjacent task` — solid, low-saturation grey-green, no arrowhead, drawn *thinner* than the others so it reads as "context, not catalog".
- **Confidence** = width + opacity together (never hue). Three buckets is enough: high (manual, reviewed), medium (LLM high-confidence or repeated co-purchase), low (single co-purchase event). Print the bucket definition in the legend as a number range, not an adjective.
- **Provenance/status** = a **ring on the node** (draft/published) and a **badge at the edge midpoint** (M / LLM / co-purchase), shown only above a zoom threshold or on hover. Dash as a *secondary* provenance cue only if the renderer is cheap enough — Sigma's and Cytoscape's docs both say dashes/transparency are the expensive channels, so reserve them for the focused subgraph.
- **Time** should not be an edge colour. Use (a) an edge "age" tick or a tiny sparkline in the provenance popover, (b) the Slicer/Timeline as a separate control that *filters*, and (c) one dedicated "co-purchase window" chip. Colour-by-recency on 817 nodes produces a meaningless rainbow.
- **Family/segment** = position and containment, not colour: cluster by family (Kumu-style or G6 combo), and let segment be a subtle background region/hull. Colour is already spent on relation type. If segment must be visible, use node *shape* or a small corner glyph.
- **Solo nodes** (offers with no relations) get a **parked rail/tray** at the edge of the canvas ("34 offers with no relations") rather than being scattered as dust — this turns a failure of the data into an honest, clickable statement.
- **External links** = distinct outline (double ring) + outward arrow glyph + they never expand; clicking opens a new tab. Also give them a different hit-test: they should not be draggable into the layout.
- **Encoding budget rule**: at most 2 channels per mark at rest (hue + width for edges; size + ring for nodes), everything else on hover/selection. This is the only way to keep a 5-relation, 3-source, 2-status graph legible without a 12-item legend nobody reads.

### Gaps
- No published perceptual study on encoding *relation type* specifically (most work is on node colour/size and on chart encodings); the mapping above is design judgement plus vendor convention.
- No source on how to encode **LLM confidence** in a graph; confidence visualisation literature is mostly about uncertainty in scientific data.
- Dash/opacity cost trade-offs are documented per-library, not cross-library; the "reserve dashes for the focused subgraph" rule is inference.

## Performance limits and rendering techniques at 1k, 10k and 100k nodes and edges

### Takeaway
817 nodes is a non-problem — any library, any laptop, and you should spend the budget on labels and motion instead. 10k is a WebGL problem with level-of-detail discipline. 100k is a **GPU-simulation or pre-layout** problem, and 136k is a **don't-render-it** problem: aggregate, cluster, and page. The dominant cost at scale is **pixels, not vertices** — overdraw, transparency and antialiasing, not node count.

### Cited Findings
- Sigma's benchmark conclusion, quoted exactly: frames on big graphs are "usually **fragment-bound**: the GPU spends its time shading and blending pixels, not processing vertices. In our benchmark, **halving the vertex count only shaved ~6% off the frame time**, while opacity and antialiasing changes moved it far more, **up to ~80% shaved in some case**" — [Sigma performance](https://www.sigmajs.org/how-to/technical/performance/).
- Sigma's specific wins: `antialiasEdges: false` → "up to **x5 performances gain** on the whole GPU rendering process"; avoid semi-transparency (use a solid colour near the background instead); register only the edge paths you need because "every edge pays the vertex cost of the **heaviest** registered path" (defaults include `pathLoop` at 66 vertices, so straight edges cost 66 vertices each); lower curve tessellation (`pathCurved({segments: 12})`, `pathLoop({segments: 12})`); edge events off unless used; `pickingDownSizingRatio` (default 2) trades picking precision for cost — [same](https://www.sigmajs.org/how-to/technical/performance/), [Sigma settings](https://www.sigmajs.org/reference/settings/).
- Sigma's rendering architecture for scale: one WebGL stage, SDF label atlas on the GPU, attribute **data textures** so shaders can look up any node/edge by index, GPU picking via a hidden framebuffer, and categorical depth buckets that avoid re-processing — [Sigma rendering](https://www.sigmajs.org/concepts/rendering/).
- Cytoscape (canvas 2D) is candid that it degrades: "You may notice that performance starts to degrade on graphs with large numbers of elements… performance is a function of graph size", and rendering cost is "a function of the area that it needs to render", so high-DPI displays hurt; its mitigations are the descending-significance list quoted in the previous section (`hideEdgesOnViewport`, `textureOnViewport`, `pixelRatio: 1`, no compound nodes, no overlays) — [Cytoscape performance](https://js.cytoscape.org/).
- Cytoscape also documents a **GPU escape hatch**: `cosmos-over-cytoscape`, "a physics simulation layout that makes use of parallelism on the GPU to support large graphs", and recommends `fCoSE` as the first force-directed layout to try for quality/perf — [Cytoscape layouts](https://js.cytoscape.org/).
- cosmos.gl: GPU force simulation and rendering, "keeping hundreds of thousands of points and **millions of links** within reach of your browser"; published examples include 5,570 nodes/16,067 links, 1,890,815 points/2,315,222 links, and 10,000,000 points — [cosmos.gl](https://cosmos.gl/).
- `3d-force-graph` runs physics on `d3-force-3d` or `ngraph.forcelayout3d` and renders with ThreeJS/WebGL; its own largest bundled demo is ~4k elements — [README](https://github.com/vasturiano/3d-force-graph).
- G6 batches canvas updates ("merges differences and updates the canvas uniformly after `draw` or `render`"), and `render` additionally runs layout + `fitView` — so `render` is not a cheap repaint — [G6 FAQ](https://g6.antv.antgroup.com/en/manual/faq).
- Bloom's only published scale threshold: a full-scan Perspective build is slow beyond "> 10,000,000 nodes and relationships combined", where a quick scan is offered — [Bloom Perspectives](https://neo4j.com/docs/bloom-user-guide/current/bloom-perspectives/bloom-perspectives/).
- The de-cluttering alternatives that buy scale without rendering: cluster/collapse (Linkurious grouping, G6 combo, Kumu cluster), super-node badges + selective expand (Linkurious), and aggregation with counts — [Node grouping](https://doc.linkurious.com/user-manual/latest/nodegrouping/), [Expand nodes](https://doc.linkurious.com/user-manual/latest/expand/), [Kumu cluster](https://docs.kumu.io/guides/clustering).

### Inferences
- **Budget table** (targets, not vendor claims):

  | Scale | What to render | Technique | Realistic target |
  |---|---|---|---|
  | 1k nodes / ~3k edges (our 817) | everything, labels on, arrows on | plain canvas 2D or WebGL; pre-computed layout; no LOD needed | 60 fps, no tricks |
  | 10k / 30k | everything as marks, **labels culled** | WebGL (Sigma/G6 WebGL), `antialiasEdges:false`, opaque edges, label LOD by zoom + density, cluster-collapse for dense families, edge events off | 30–60 fps; labels only for focus + neighbours |
  | 100k / 300k | **aggregates first** | GPU simulation (cosmos.gl) *or* offline layout + tiled/streamed positions; community/family aggregation as the default view; drill-down replaces global view | 30 fps on marks; the useful view is the aggregate |
  | 136k catalog | never all at once | server-side aggregation (family/segment), super-node counts, expand-to-page, ghost nodes | the graph never holds >2–5k marks |

- **Pre-compute and persist the layout for the 817.** A force layout that re-runs on every load means the demo's mental map changes between sessions, before/after comparisons break, and saved views become meaningless. Store x/y (and a layout version) with the node record.
- **The cheapest big win is not the renderer, it is the LOD policy**: at rest show ~1 label per 40–60 px of screen, expand labels on hover/selection/zoom, and never draw edge text. This is exactly what Sigma's density culling, Cytoscape's `min-zoomed-font-size` and Obsidian's text-fade threshold are all approximations of.
- **For the full catalog, do the aggregation on the server** and ship pre-aggregated families with counts to the client. The browser should never receive 136k rows to then throw 99% away — that is both slow and dishonest about what the graph is showing.
- **Instrument it**: track frame time and label count, and put a debug toggle (like Sigma's `DEBUG_displayPickingLayer` / GPU timer logs) behind a query param so the "impressive" demo can be defended with numbers when a technical buyer asks.

### Gaps
- No public, reproducible benchmark of the same graph across Sigma / G6 / Cytoscape / cosmos.gl at 1k/10k/100k; every number found is either relative (Sigma) or an example size (cosmos.gl).
- Cytoscape's docs give no absolute node ceiling; "very, very large graphs" is as specific as it gets.
- No source on **server-side pre-layout + streaming** for product graphs (the tiling/streaming approach is inferred from general large-graph practice, not from a cited vendor).
- Nothing found on mobile/tablet performance for these libraries; if the demo is laptop-only this does not matter, but it is unverified for touch devices.
