# Knowledge graph, ontology and data-catalog products: how they model, review and govern relationships

Scope note: this note covers relation/edge modelling, provenance and evidence, review workflows, versioning/deprecation, permissions, impact analysis and graph-vs-table UX in Neo4j (+n10s/Bloom/GDS), Stardog, Ontotext GraphDB, Graphileon, Linkurious, Atlan, Collibra, DataHub, OpenMetadata, Apache Atlas, and — because it is the closest analogue to a product catalogue — Akeneo PIM association types. Standards (OWL, SHACL, RDF-star, PROV-O, named graphs) are included only where they map onto a concrete product behaviour.

---

## 1. How do these tools define relation types and ontologies?

### Takeaway
Every mature product separates a **relation type registry** (a schema object with direction, allowed endpoint types, cardinality and semantics) from **relation instances** (edges/assertions). The strongest pattern for a product catalogue is Collibra's "relation type = head + tail + role + co-role" plus its "complex relation" (an edge promoted to an entity so it can carry its own attributes), with OWL/OpenMetadata-style characteristics (symmetric, transitive, inverse) declared as machine-actionable flags rather than prose.

### Cited Findings

**Collibra — relation type as a first-class schema object**
- A relation type defines "which asset types can be related and which connections can exist between the asset types"; it has exactly four elements: **Head** (asset type at the head), **Tail** (asset type at the tail), **Role** (name from head→tail, e.g. "is part of") and **Co-role** (name from tail→head, e.g. "contains"). Relations are bidirectional: "the Column asset is part of the Table asset, and the Table asset contains the Column asset" — [Collibra: About relation types](https://productresources.collibra.com/docs/collibra/2026.02/Content/Assets/Characteristics/Relations/RelationTypes/to_relation-types.htm).
- Relation types are attached to asset types through **assignments** in the operating model, not globally: "When you associate a relation type with an asset type through an assignment, you can add relations of that relation type to the assets of that asset type" — [Collibra: About relation types](https://productresources.collibra.com/docs/collibra/2026.02/Content/Assets/Characteristics/Relations/RelationTypes/to_relation-types.htm).
- Some relation types are **system-managed**: you cannot edit their public ID or delete them, but you can rename them (e.g. for translation) — [Collibra: About relation types](https://productresources.collibra.com/docs/collibra/2026.02/Content/Assets/Characteristics/Relations/RelationTypes/to_relation-types.htm).
- The API's `AddRelationTypeRequest` requires `coRole`, `role`, `sourceTypeId`, `targetTypeId` — i.e. direction and both endpoint types are mandatory at creation, not optional metadata — [Collibra Developer: Relation Types API](https://developer.collibra.com/api/references/data-governance/relation-types).
- **Explicit vs derived relations**: explicit relations are "a direct, manually created connection", "physically registered (persisted) in the database"; derived relations are "an indirect connection … automatically inferred based on existing explicit relations", "calculated dynamically … and is not persisted", and **cannot be manually created**. Collibra's own guidance: use derived when an existing path already conveys the meaning; switch to explicit if you hit performance problems — [Collibra: About relations](https://productresources.collibra.com/docs/collibra/latest/Content/Assets/Characteristics/Relations/co_relations.htm).
- **Complex relation type (CRT)**: "a complex relation is an entity that can't exist on its own. It exists only through its links to other assets", and "can have attributes of its own, for example, Description and Priority". The CRT defines which relations and attributes a complex relation may have, with **min/max cardinality per relation type and per attribute type**; at least one relation type must have min cardinality ≥ 1; a complex relation cannot have more than 32,767 relations to assets — [Collibra: About complex relation types](https://productresources.collibra.com/docs/collibra/2026.08/Content/Assets/Characteristics/ComplexRelations/ComplexRelationTypes/co_complex-relation-types.htm).
- CRT editing is deliberately restrictive: you can edit name/description/display options, "you can't edit existing relations and attributes in the complex relation, but you can add relations and attributes"; to change existing ones "you need to delete the complex relation type first and then create a new one. Note that the new complex relation type will have a new ID" — [Collibra: Manage complex relation types](http://productresources.collibra.com/docs/collibra/latest/Content/Assets/Characteristics/ComplexRelations/ComplexRelationTypes/ta_create-complex-relation-type.htm).
- Deleting a relation type is blocked when it is "used in data quality rules or referenced by derived relation types" (HTTP 400) — [Collibra Developer: Relation Types API](https://developer.collibra.com/api/references/data-governance/relation-types).

**DataHub — aspects + typed edges + relationship vocabulary**
- DataHub's model is entities, aspects (metadata documents) and relationships: "a relationship represents a named edge between 2 entities. They are declared via foreign key attributes within Aspects along with a custom annotation (@Relationship). Relationships permit edges to be traversed bi-directionally" — [DataHub: The Metadata Model](https://docs.datahub.com/docs/metadata-modeling/metadata-model).
- The glossary ships a small, opinionated relationship vocabulary with explicit direction semantics: **Inherits (Is A)** directed, **Contains (Has A)** directed, **Synonym** undirected, **Antonym** undirected, **Translates to** directed, **Valid value** directed, **Related to** undirected. Directed types carry a reverse label ("Inherits" reads back as "Inherited by") — [DataHub: Relating Glossary Terms](https://docs.datahub.com/docs/features/feature-guides/ontology/relating-glossary-terms).
- DataHub explicitly discourages the generic type: "Use **Related to** only when nothing else fits. It records that two terms are connected but not how, so there is nothing for a traversal to act on. If you find yourself using it a lot, you probably want a custom relationship type" — [DataHub: Relating Glossary Terms](https://docs.datahub.com/docs/features/feature-guides/ontology/relating-glossary-terms).
- **Custom relationship types** are created by flipping a switch on an entity-valued *structured property*: "Treat as Relationship". Four settings define meaning: **Direction** (directed default / undirected symmetric), **Reverse Label** (display only, "never creates a second edge"), **Transitive** ("A → B → C implies A → C … used by SPARQL's RDFS regime"), **Equivalent Properties** (CURIEs/IRIs such as `skos:broader`, `skos:exactMatch`) — [DataHub: Adding Custom Relationships](https://docs.datahub.com/docs/features/feature-guides/ontology/custom-relationships).
- The split of responsibilities is explicit: the structured property "is the veneer … what users assign"; the relationship type (`urn:li:relationshipType:*`) "carries the predicate identity: the display name, direction semantics, transitivity, reverse label, and RDF predicate mapping. Graph edges are keyed by *this*" — [DataHub: Adding Custom Relationships](https://docs.datahub.com/docs/features/feature-guides/ontology/custom-relationships).
- DataHub's modelling guidance is directly transferable: "**One relationship per meaning.** Resist reusing *Related to* with a comment explaining what was actually meant"; "**Name both directions**"; "**Only mark transitive when it is true.** Transitivity licenses inference; a wrong claim produces confidently wrong answers under closure"; "Map to standards where one fits" — [DataHub: Adding Custom Relationships](https://docs.datahub.com/docs/features/feature-guides/ontology/custom-relationships).
- Edges are **materialized asynchronously** from the property assignment: "a newly assigned relationship takes a moment to appear in the graph and the traverse APIs", and "Deleting the property removes the edges" — [DataHub: Adding Custom Relationships](https://docs.datahub.com/docs/features/feature-guides/ontology/custom-relationships).

**OpenMetadata — the most complete public relation-type schema**
- A relationship type is described as "the difference between 'these two terms are somehow related' and 'Churn Rate is calculatedFrom Cancelled Subscriptions, calculatedFrom is not symmetric, and it maps to om:calculatedFrom in RDF'" — [Collate: Relationship Types (Ontology Studio)](https://docs.getcollate.io/ai-2-0/how-to-guides/ontology/studio/relationship-types).
- The type object carries: unique `Name` ("the unique key of the type. It can't change after the type is created"), `Display Name` ("the label shown on graph edges and badges"), `Description`, **Category** (Core / OWL-SKOS / Custom), **Characteristics** ("the OWL characteristics that apply to the type, such as Symmetric or Transitive"), **RDF Predicate**, cardinality, cross-glossary flag, colour — [Collate: Relationship Types](https://docs.getcollate.io/ai-2-0/how-to-guides/ontology/studio/relationship-types).
- "Characteristics are OWL property characteristics. They aren't labels: reasoners and the inference engine act on them." — [Collate: Relationship Types](https://docs.getcollate.io/ai-2-0/how-to-guides/ontology/studio/relationship-types).
- System-defined types "carry a lock icon. They can be updated but never deleted, and their delete action is disabled"; "To check how many relations use a type before you remove it, call `GET /api/v1/glossaryTerms/relationTypes/usage`. It returns each type with the number of relations currently using it." — [Collate: Relationship Types](https://docs.getcollate.io/ai-2-0/how-to-guides/ontology/studio/relationship-types).
- **Version discrepancy worth flagging**: the same product documents relation-type *category* two different ways. The v2.1 Ontology Explorer docs group types as **Hierarchical / Associative / Equivalence** ("Hierarchical: Parent/child style relationships … Associative: General related-to style … Equivalence: Same-as style") — [OpenMetadata: Manage Relation Types (v2.1)](https://docs.open-metadata.org/v2.1.x/how-to-guides/data-governance/ontology/relationship-types) — while the Ontology Studio docs use **Core / OWL-SKOS / Custom · Admin-defined** ("where the meaning of the type comes from") — [Collate: Relationship Types](https://docs.getcollate.io/ai-2-0/how-to-guides/ontology/studio/relationship-types). The two taxonomies answer different questions (semantic shape vs provenance of meaning) and are not interchangeable.
- The admin table for relation types exposes exactly the columns a relation registry needs: **Name**, **Display Name**, **Category** (Hierarchical / Associative / Equivalence), **Symmetric**, **Transitive**, **Cross-Glossary**, **Cardinality**, **Color** — and system-defined types "show a lock icon next to their name and can't be edited or deleted", while "Custom relation types … can be edited or removed" — [OpenMetadata: Manage Relation Types](https://docs.open-metadata.org/v2.1.x/how-to-guides/data-governance/ontology/relationship-types).
- Cardinality is a four-value enum on the type: **One-to-One** ("Each source term can connect to exactly one target term, and each target term to exactly one source term"), **One-to-Many**, **Many-to-One**, **Many-to-Many** — [OpenMetadata: Manage Relation Types](https://docs.open-metadata.org/v2.1.x/how-to-guides/data-governance/ontology/relationship-types).
- A newly added relation type is "immediately available as an edge label in the Ontology Explorer graph and as an option in the Relationship Type filter" — type creation and visualisation vocabulary are the same registry, with no separate deploy step — [OpenMetadata: Manage Relation Types](https://docs.open-metadata.org/v2.1.x/how-to-guides/data-governance/ontology/relationship-types).
- "Relationship types are versioned entities like any other, with full history", and "The RDF Predicate is the identity of this relationship in the knowledge graph and in every exported ontology. Changing it after edges exist changes what downstream consumers see. Choose it carefully when you create the type." — [Collate: Relationship Types](https://docs.getcollate.io/ai-2-0/how-to-guides/ontology/studio/relationship-types).
- Default types and their characteristics: `relatedTo`→`om:relatedTo` (Symmetric), `antonym`→`om:antonym` (Symmetric), `partOf`→`om:partOf`, `hasPart`→`om:hasPart`, `calculatedFrom`→`om:calculatedFrom`, `usedToCalculate`→`om:usedToCalculate`, `synonym`→`skos:exactMatch` (Symmetric), `broader`→`skos:broader` (Transitive), `narrower`→`skos:narrower` (Transitive), `seeAlso`→`rdfs:seeAlso` (Symmetric), `subClassOf`→`rdfs:subClassOf` (Transitive), `superClassOf`→`om:superClassOf` (Transitive) — [Collate: Relationship Types](https://docs.getcollate.io/ai-2-0/how-to-guides/ontology/studio/relationship-types).
- Design guidance from the same page, unusually direct: "Prefer a few well-defined types over many similar ones. Every type is a decision modelers must make correctly on every edge. Three types used consistently beat twelve used approximately. Add a type when it unlocks a query you can't express without it." — [Collate: Relationship Types](https://docs.getcollate.io/ai-2-0/how-to-guides/ontology/studio/relationship-types).
- Deprecation of a *type* has a dedicated field: `Replaced by` — "The successor type when a type is deprecated, so consumers can follow the migration" — [Collate: Relationship Types](https://docs.getcollate.io/ai-2-0/how-to-guides/ontology/studio/relationship-types).

**Apache Atlas — relationshipDef with cardinality and tag propagation**
- `AtlasRelationshipDef` "defines a relationship" with two ends, "each of which specify cardinality, an EntityDef type name and name and optionally whether the end is a container"; it has `relationshipCategory` (the UML type, e.g. ASSOCIATION), a `propagateTags` flag "indicating which way tags could flow over the relationships", and `attributeDefs` on the relationship itself — but "only primitive types are allowed" on relationship attributes — [Apache Atlas: AtlasRelationshipDef](https://atlas.apache.org/api/v2/json_AtlasRelationshipDef.html).
- RelationshipDefs "introduce new attributes to the entity instances", so relationship attributes are surfaced as if they were attributes of the endpoints; typeDefs carry `typeVersion`, `version`, `createTime/updateTime`, `createdBy/updatedBy` — [Apache Atlas: AtlasRelationshipDef](https://atlas.apache.org/api/v2/json_AtlasRelationshipDef.html).

**Neo4j — schema is thin, semantics come from a toolkit or from modelling discipline**
- Native Neo4j has no ontology layer; relationship *types* are labels on edges and properties live on the edge. Semantics (OWL/RDFS/SKOS, SHACL validation, basic inferencing) come from the **neosemantics (n10s)** plugin, which imports/exports RDF and ontologies and validates against SHACL; n10s "is only available for Neo4j self-hosted (CE and EE) and is **not** available in Aura" — [Neo4j Labs: neosemantics](https://neo4j.com/labs/neosemantics).
- When a relationship needs to connect more than two things or carry rich, shared context, Neo4j's official guidance is either "turn the Role node into a property of the WORKED_AT relationship" or "use an **intermediate node**" — a hyperedge replacement; the example promotes "works at" to an `Employment` event node holding start/end dates — [Neo4j: Modeling designs](https://neo4j.com/docs/getting-started/data-modeling/modeling-designs).
- Neo4j's own modelling literature frames the trade-off as generic-vs-specific relationship types: many specific types give query clarity; one generic type plus a discriminator property gives flexibility at the cost of every query filtering on the property (community/engineering guidance, not a normative doc) — [Neo4j community: many relationship types vs one with properties](https://community.neo4j.com/t/is-it-better-to-have-many-different-relationship-types-or-one-relationship-with-properties/1669).

**Stardog / Ontotext GraphDB — the ontology *is* the schema**
- Stardog validates data against SHACL shapes stored as RDF, "best practice is to store SHACL definitions in one or more named graphs to make managing them easier", and `icv.active.graphs` restricts which graphs are treated as shapes — [Stardog: Data Quality Constraints](https://docs.stardog.com/data-quality-constraints).
- GraphDB supports SHACL via RDF4J's `ShaclSail`; every SHACL repository has a reserved shapes graph, and `sh:shapesGraph` can point at a custom one. Supported features include `sh:targetClass`, `sh:targetNode`, `sh:targetSubjectsOf`, `sh:targetObjectsOf`, `sh:path` (including multi-hop path expressions) and `sh:inversePath` — [GraphDB 10.1: SHACL Validation](https://graphdb.ontotext.com/documentation/10.1/shacl-validation.html).
- GraphDB's inference is ruleset-driven: "full standard-compliant reasoning for RDFS, OWL-Horst, OWL2-RL, and OWL2-QL", plus custom `.pie` rulesets; inference results are updated automatically as data changes — [GraphDB 10.8: Inferencing](https://graphdb.ontotext.com/documentation/10.8/inference.html).
- OWL itself supplies the vocabulary these tools reuse: `FunctionalObjectProperty` (at most one outgoing edge), `InverseFunctionalObjectProperty` (at most one incoming), `SymmetricObjectProperty`, `AsymmetricObjectProperty`, `TransitiveObjectProperty`, `Reflexive/Irreflexive`, plus `ObjectPropertyDomain/Range` and `InverseObjectProperties` — [OWL 2 Structural Specification](https://www.w3.org/TR/owl-syntax/); `owl:inverseOf` is defined so that every (x,y) in P1 implies (y,x) in P2 and vice versa — [OWL Web Ontology Language Reference](https://www.w3.org/TR/owl-ref).

**Akeneo PIM — the closest product-catalogue analogue**
- Association types link products and product models; there are three manual kinds: **1-way** ("product A is associated with product B"), **2-way** ("product B will be automatically associated with product A") and **association with quantities** ("product A is associated with 2 quantities of product B") — [Akeneo: Manage your association types](https://help.akeneo.com/serenity-build-your-catalog/34-serenity-manage-your-association-types).
- An association type is essentially **immutable after creation**: you fill in the code, optionally set the 2-way or quantity switch, and "You can only edit the labels"; "The 2-way association property cannot be updated once the association type is created" and the same for "association with quantities" — [Akeneo: Manage your association types](https://help.akeneo.com/serenity-build-your-catalog/34-serenity-manage-your-association-types).
- **Automatic associations** (product compatibility) are rules, not hand-picked links: choose source (Products) and target (Products or a Reference entity), a primary product selection, a compatible-product selection, then attribute-based conditions; leave conditions empty to match everything; a **Preview** must be checked before "Save and Enable"; every new rule "is disabled by default, so nothing is exposed in your catalog until you enable it"; rules can be 1-way or 2-way and duplicated — [Akeneo: Manage product compatibility](https://help.akeneo.com/serenity-build-your-catalog/manage-product-compatibility).
- Rules support **negative filters** to exclude specific references ("these products are excluded from the selection, so they are never matched by the rule, even when they meet the conditions") — [Akeneo: Manage product compatibility](https://help.akeneo.com/serenity-build-your-catalog/manage-product-compatibility).
- The API normalises all three kinds into one item shape: every association item names `association_type`, `type` (`product`, `product_model`, `group`, or `record`) and `id`; quantified items additionally carry `quantity`. Automatic associations "list the entities its rule resolves to, when the rule applies to the product" — [Akeneo: REST API reference](https://api.akeneo.com/api-reference.html).

### Inferences
- A relation-type registry should be modelled as data (rows), not as enum values in code: Collibra, OpenMetadata and DataHub all let admins add types at runtime, and all three keep a **stable identity** (public ID / name / URN) separate from display labels. For a product catalogue this means `accessory`, `upgrade`, `alternative`, `bundle`, `compatibility` should be seeded rows with stable codes, not a Postgres enum — otherwise every new relation type is a migration and every label change is a data change.
- The minimum viable type schema, synthesising Collibra + OpenMetadata + Atlas: `code` (immutable), `display_name`, `reverse_display_name`, `description`, `source_entity_types[]`, `target_entity_types[]`, `direction` (directed/symmetric), `cardinality` per side (min/max, incl. "quantified" for bundles), `transitive` (default false), `category` (core/standard-mapped/custom), `rdf_predicate` or standard mapping (optional), `status` (active/deprecated), `owner`, `version`.
- Collibra's "complex relation" is the pattern to copy for **bundles and compatibility sets**: a bundle is not a binary edge, it is an entity with its own attributes (price rule, validity window, region) that happens to link N products. Promoting the edge to an entity is the only clean way to attach evidence, confidence, reviewer, TTL and version to a *relation* rather than to a product.
- Akeneo's immutability rule is a strong signal: direction and "quantified" are structural, so they are frozen at creation and only labels stay editable. This is cheap governance that prevents silent semantic drift of historical edges. If our system needs to change direction semantics, the right move is a **new type** plus a `supersedes`/`replaced_by` pointer, not an in-place edit (see §2 on OBO deprecation practice).
- Derived/inferred relations should be stored **separately from asserted ones** (Collibra's explicit-vs-derived split). Mixing them makes review impossible: a reviewer cannot approve a statement whose origin is a path traversal. In our case `alternative` computed by embedding similarity is derived; `alternative` confirmed by a merchandiser is asserted.

### Gaps
- No public documentation was found on how Collibra or Atlan model **relation-level cardinality for product-like many-to-many with quantities**; Akeneo is the only source found that treats "quantity" as a first-class property of a relation type.
- Neo4j has no first-party ontology/relation-type registry; the only official route is n10s, which is unavailable on Aura. No public doc describes a Neo4j-native "relation type with allowed endpoint types" construct — that constraint must be enforced in the application or via SHACL.
- Graphileon documents its own meta-model (UI components as nodes, triggers as edges) but publishes no relation-type/ontology registry for the *domain* graphs it operates on — [Graphileon Knowledge](https://graphileon.com/graphileon-knowledge). Its `docs.graphileon.com` documentation host was unreachable from the research environment on repeated attempts, so its dashboard/NetworkView behaviour is only partly verified here.

## 2. How do they handle evidence/provenance, confidence, suggested links, approval/rejection, ownership, audit, versioning and deprecation?

### Takeaway
The mature pattern is a **three-state assertion lifecycle** — candidate/suggested → reviewed (approved or rejected, with reason) → published — where the assertion carries its own provenance, confidence, reviewer and timestamps, and where **deprecation is a state, not a delete**. Every product surveyed keeps rejection as a durable record (so the same bad suggestion is not re-proposed forever) and keeps deprecation/soft-delete distinct from hard delete.

### Cited Findings

**Provenance and confidence at the statement level**
- RDF-star exists precisely for this: a quoted triple can be annotated without being asserted — `<< :employee38 :jobTitle "Assistant Designer" >> :accordingTo :employee22 ; :confidence 0.8`. The W3C community write-up stresses the semantics: quoting means "we do not endorse the claim"; the annotation carries claimer and confidence — [RDF-DEV CG: RDF-star patterns for provenance](https://www.w3.org/community/rdf-dev/2022/01/26/provenance-in-rdf-star).
- The same note flags a limitation worth designing around: "each statement made about a particular triple must be interpretable independently of the other statements made about that triple" — i.e. annotations on the same triple do not compose into one record; if you need a single auditable relation record, use a reified node (Collibra complex relation / Neo4j intermediate node) rather than parallel annotations — [RDF-DEV CG](https://www.w3.org/community/rdf-dev/2022/01/26/provenance-in-rdf-star).
- RDF-star is a W3C-documented extension of RDF and SPARQL ("a compact alternative to standard RDF reification"), not a vendor dialect — [W3C: RDF-star and SPARQL-star](https://www.w3.org/2021/12/rdf-star.html).
- PROV-O gives the standard vocabulary if provenance must be interoperable: `Entity` / `Activity` / `Agent`, with `prov:wasDerivedFrom`, `prov:wasAttributedTo`, `prov:wasGeneratedBy`, `prov:wasInformedBy` for activity-only chains — [W3C: PROV-O](https://www.w3.org/TR/prov-o/).
- Named graphs are the practical provenance container in triple stores: an RDF dataset is "exactly one default graph … zero or more named graphs", a triple may appear in several graphs and "each occurrence is considered a distinct triple"; named graphs are explicitly justified for "sane data management, access control, or to attach metadata to the overall graph" — [Stardog: RDF Graph Data Model](https://docs.stardog.com/tutorials/rdf-graph-data-model).
- GraphDB makes the provenance problem concrete: forward-chaining "materializes all implicit statements in the default graph. Therefore, it is impossible to trace which graphs these implicit statements are coming from." Its **provenance plugin** re-runs inference over a specific named graph at query time so derived statements can be attributed — [GraphDB 10.0: Provenance plugin](https://graphdb.ontotext.com/documentation/10.0/provenance-plugin.html).
- GraphDB's **Proof plugin** answers "which rule fired and which premises have been matched to produce that statement", and "will obey the FGAC checks and display only statements the user has access to … the explanation … will be available … only if that user has access to all the statements that triggered the inference" — [GraphDB 10.8: Inferencing](https://graphdb.ontotext.com/documentation/10.8/inference.html).
- DataHub's edge materialization is asynchronous and derived from a property assignment, which means provenance of the edge is recoverable from the property's own audit trail, but the edge itself is a projection — [DataHub: Adding Custom Relationships](https://docs.datahub.com/docs/features/feature-guides/ontology/custom-relationships).

**OpenMetadata Ontology — provenance and release semantics (closest match to our problem)**
- The whole ontology layer is stored **in the relational database**, not in a triple store: "ontologies, concepts, properties, relationship types, and constraints are stored in the relational database as first-class OpenMetadata entities, with versions, owners, and change events" — [OpenMetadata: Ontology Core Concepts](https://docs.open-metadata.org/v2.1.x-SNAPSHOT/how-to-guides/ontology/concepts).
- Relations carry provenance explicitly: "**Relations record who created them and when, plus a provenance marker that distinguishes manually authored edges from imported, suggested, or inferred ones**" — [OpenMetadata: Ontology Core Concepts](https://docs.open-metadata.org/v2.1.x-SNAPSHOT/how-to-guides/ontology/concepts).
- Inferred data is kept physically separate so it can never be confused with curated data: "Inferred triples in the knowledge graph are written into **separate named graphs** and marked, for example `om:inferred` and `om:inferredTagSource`, so a derived tag is never mistaken for a curated one" — [OpenMetadata: Ontology Core Concepts](https://docs.open-metadata.org/v2.1.x-SNAPSHOT/how-to-guides/ontology/concepts).
- Versioning is **draft-then-release**, not per-row history: "Edits to an ontology collect as unpublished changes on its working draft. **Publishing** captures them as a numbered, immutable **release**. If the ontology has reviewers, a release is reviewed through the approval workflow before it goes live. Otherwise, an author or owner publishes it directly. Only one release is **Active** at a time" — [OpenMetadata: Ontology Core Concepts](https://docs.open-metadata.org/v2.1.x-SNAPSHOT/how-to-guides/ontology/concepts).
- Read isolation follows the draft/release split: "Users without edit permission, the knowledge graph, and Export of a published release read the active release. Users with edit permission can also read the working draft" — [OpenMetadata: Ontology Core Concepts](https://docs.open-metadata.org/v2.1.x-SNAPSHOT/how-to-guides/ontology/concepts).
- Identity is decoupled from naming, twice over: an ontology has a stable "Ontology IRI … It stays the same if you rename the ontology", and every concept has "an IRI: a stable, globally unique identifier. Renaming the concept keeps it" — [OpenMetadata: Ontology Core Concepts](https://docs.open-metadata.org/v2.1.x-SNAPSHOT/how-to-guides/ontology/concepts).
- Namespace changes are treated as an irreversible structural decision: "Changing an ontology's namespace after concepts exist changes how new IRIs are minted. Decide the namespace before you start authoring at scale, the same way you would decide a package name" — [OpenMetadata: Ontology Core Concepts](https://docs.open-metadata.org/v2.1.x-SNAPSHOT/how-to-guides/ontology/concepts).
- There is an explicit **decidability guardrail**: with `RDF_STRICT_OWL_PROFILE=true` (default) "OpenMetadata rejects authored axioms that fall outside the supported OWL 2 DL profile. That keeps the model decidable, which is exactly what bounds the work a reasoner has to do"; and a chain/disjointness rule naming a reserved predicate "is left out of the projection, and the server logs a warning" rather than failing the whole export — [OpenMetadata: Ontology Core Concepts](https://docs.open-metadata.org/v2.1.x-SNAPSHOT/how-to-guides/ontology/concepts).
- Governance level is a first-class field (L1 foundational/standards, L2 enterprise model, L3 domain model), with owners and reviewers per ontology — [OpenMetadata: Ontology Core Concepts](https://docs.open-metadata.org/v2.1.x-SNAPSHOT/how-to-guides/ontology/concepts).

**Suggested links and machine-generated assertions**
- Atlan's **Asset ↔ Term Linker** is the most detailed public description of LLM-proposed links at scale: "A sample decides every pair and writes nothing to your assets"; "Publishing writes the links the sample proposed. Each one is checked again first, and a link is skipped if its term's certificate is no longer one the agent links, its asset has left the collection, or the pair has been linked since"; "Links are added, never replaced or removed"; and explicitly: "**Can I approve individual links? No.** Publishing takes the sample's links as a whole. At the scale this template runs, approving each link by hand isn't practical, so the sample comes with a CSV you can download and audit instead"; "There's no bulk undo yet" — [Atlan: FAQ – Asset ↔ Term Linker](https://docs.atlan.com/product/capabilities/governance/context-agents-studio/faq/asset-term-linker).
- That same FAQ explains why correct pairs still go to review and how candidates are found: "The agent finds candidates through words in names and descriptions, and through mentions in READMEs and custom metadata" — [Atlan: FAQ – Asset ↔ Term Linker](https://docs.atlan.com/product/capabilities/governance/context-agents-studio/faq/asset-term-linker).
- Atlan's non-LLM suggestion engine is deliberately conservative: suggestions are made only for assets "of the same type with the same name", only when the field is empty, and "only users with the necessary edit permissions for that asset will be able to apply the metadata suggestions" — [Atlan: Suggestions from similar assets](https://docs.atlan.com/product/integrations/automation/always-on/references/suggestions-from-similar-assets).
- Link prediction as a productised feature: Neo4j GDS link-prediction pipelines train on "positive examples … selected from the relationships in the graph" and "negative examples … sampled from non-adjacent nodes", then "infer the probability of the existence of a relationship between two non-adjacent nodes" — i.e. the model outputs a scored candidate, not an edge — [Neo4j GDS: Link prediction pipelines](https://neo4j.com/docs/graph-data-science/2026.09/machine-learning/linkprediction-pipelines/link-prediction).
- GraphDB's similarity plugin returns ranked "closest semantically related terms/documents" with "a similarity score … shown in the second column of the results" — a candidate generator, again without write-back — [GraphDB 11.5: Semantic similarity searches](https://graphdb.ontotext.com/documentation/11.5/semantic-similarity-searches.html).

**Approval / rejection workflows**
- **DataHub change proposals**: users without edit rights propose Tags, Glossary Terms, Owners, Domains, Descriptions and Structured Properties; proposals appear "in a proposed state", are "sent to the inbox of reviewers", and "a full log of all accepted or rejected proposals is kept for each user". Privileges are split into `Propose *` and `Manage * Proposals` — [DataHub: Change Proposals](https://docs.datahub.com/docs/managed-datahub/change-proposals).
- DataHub **Context review** adds a pre-merge evaluation step: "Proposals assigned to you appear under Tasks > Proposals. Open one to see what's changing, edit it if needed, and run the relevant evals against it. DataHub answers each eval as if the change were already published, so you can see whether it fixes or breaks anything. Then approve or reject it"; approvers are "the owners of the context involved, and admins"; "A rejected proposal is closed without changing anything. To try again, propose the change again" — [DataHub: Reviewing Context Changes](https://docs.datahub.com/docs/features/feature-guides/context/context-review).
- **OpenMetadata glossary approval**: with reviewers assigned, a new term "will show up in the Glossary, but will be marked as **Draft**"; "Only the assigned Reviewers can Approve or Reject the term"; "A Task is assigned for the Reviewers"; "Users can discuss further about the term by replying on the task" with @mentions; approved → Approved label, rejected → Rejected label. Crucially, "In case, the glossary does not have any Reviewers assigned, then the glossary terms will be Approved by default" — [OpenMetadata: Glossary Approval Workflow](https://docs.open-metadata.org/latest/how-to-guides/data-governance/glossary/approval).
- **Atlan requests**: "Any user without edit access to an asset's metadata can request changes"; the UI turns an attempted edit into a suggestion; requests have three states — "Pending … still awaiting approval", "Approved … someone has already accepted (and applied)", "Rejected … declined (and will not be applied)"; approval requires edit access ("admin and member users"); only admins can see all requests across assets — [Atlan: Manage requests](https://docs.atlan.com/product/capabilities/requests/how-tos/manage-requests).
- Atlan's request model is permission-shaped rather than workflow-shaped: "Admin users can directly change assets where they have permission, and suggest changes to all other assets" — the same action either applies immediately or becomes a proposal depending on the actor's rights — [Atlan: What are requests?](https://docs.atlan.com/product/capabilities/requests/concepts/what-are-requests).
- **MDM steward queues** show the same pattern with explicit thresholds: tasks appear when a pair scores "above the Manual Review threshold but below the Automatic Match threshold"; queue statuses are Pending / Approved ("candidate was accepted and the alias was confirmed") / Rejected; the steward needs "authority to decide whether two records represent the same real-world object" — [FactVerse: MDM Steward Queue](https://datamesh.com/factverse-docs/dfs/mdm/steward-queue), [Verato: Stewardship Tasks](https://support.verato.com/hc/en-us/articles/11394384625172).
- **Collibra workflows can be triggered by relation creation**, which is the mechanism that makes relation-level review possible without a bespoke queue: "Workflows start depending on their configuration: Manually … Following an event: Workflows start automatically when specific events occur in Collibra, such as the creation of a new asset, a change in an attribute value, or **the addition of a relation**". Workflows "can interact with assets, attributes, and relations", and "can log every step and decision within a workflow, providing a clear audit trail" — [Collibra: Workflows](https://productresources.collibra.com/docs/collibra/latest/Content/Workflows/to_workflows.htm).
- **Collibra** encodes review in asset **statuses** used by workflows: `Candidate` ("The initial status of an asset. Newly created assets have the Candidate status"), `Under Review` ("stakeholders are reviewing an asset … remains in this status until it is accepted"), `Accepted` ("The stewards approved an asset definition … enters the Accepted status at the end of the Approval and Simple Approval workflows"), `Approved`, `Archived` — [Collibra: Out-of-the-box statuses](https://productresources.collibra.com/docs/collibra/2026.08/Content/Settings/OperatingModel/Statuses/ref_overview-status-types.htm).
- **Linkurious** applies the review pattern to *graph investigations* rather than schema: a case can be moved to "In progress, Confirmed or Dismissed", each change "will be prompted for an optional note, to document the decision for future reference", cases can be assigned, commented, @mentioned, and the "history of assignement … with comments and status changes" is kept in the activity panel — [Linkurious: Investigating cases](https://doc.linkurious.com/user-manual/latest/alert-investigate/).

**Ownership**
- DataHub models ownership as a first-class relationship (`OwnedBy`) with **custom ownership types** as net-new entities, so an owner can be labelled with organisation-specific roles; creating types needs `Manage Ownership Types`, assigning needs `Edit Owners` — [DataHub: Custom Ownership Types](https://docs.datahub.com/docs/ownership/ownership-types).
- DataHub's privilege list is the clearest public decomposition of "who may touch what" at the metadata level: `Edit Tags`, `Edit Glossary Terms`, `Edit Description`, `Edit Links`, `Edit Status` (soft delete), `Edit Lifecycle Stage`, `Edit Domain`, `Edit Deprecation`, `Edit Incidents`, `Edit Lineage`, `Edit Properties`, `Edit Owners` — [DataHub: Policies Guide](https://docs.datahub.com/docs/authorization/policies).
- Collibra splits responsibility by role in the operating model (stewards approve definitions; technical stewards grant access; reviewers appoint assignees) as described in its status definitions — [Collibra: Out-of-the-box statuses](https://productresources.collibra.com/docs/collibra/2026.08/Content/Settings/OperatingModel/Statuses/ref_overview-status-types.htm).

**Audit and versioning**
- DataHub is explicit that its GraphQL API exposes only current aspect values: "There is no GraphQL query that returns aspect history … RawAspect has only aspectName, payload … and renderSpec. It has no version, created, actor or history fields." History must come from the **Timeline CLI/API**, the **Audit Events Search API** (`/audit/search`, returning `timestamp`, `actorUrn`, `sourceIP`, `eventSource`), or Kafka `MetadataChangeLog_Versioned_v1` (default 7-day retention) — [DataHub Support: Metadata Versioning and Audit History](https://support.datahub.com/hc/en-us/articles/41912220561691).
- DataHub's retention is bounded by default: "version retention keeps the 20 latest versions of each aspect, so older versions are deleted", and the support guidance is to export audit data externally for compliance — [DataHub Support: Metadata Versioning and Audit History](https://support.datahub.com/hc/en-us/articles/41912220561691).
- DataHub glossary terms have both **lifecycle stages** and **versions**: stages are Draft / In Review / Rejected / Published / Deprecated / Archived with different search visibility (only Published and Deprecated appear in default search); each stage can declare `allowedPreviousStages` and "A change that breaks that rule is refused"; with `ENTITY_VERSIONING_ENABLED=true` a term can have several versions, and "The new version copies the previous version's metadata … and starts in the **Draft** stage, so the previous version stays the latest one until the new version is published" — [DataHub: Business Glossary](https://docs.datahub.com/docs/glossary/business-glossary).
- Stardog offers transaction-level safety rather than per-edge history: explicit `begin`/`commit`/`rollback`, and permissioned rollback of *other users'* transactions (`READ` + `EXECUTE` on `admin:<db>` plus `READ`/`WRITE` on `db:<db>`) — [Stardog: Transactions](https://docs.stardog.com/operating-stardog/database-administration/transactions).
- GraphDB ships a "Data history and versioning plugin" that "enables you to access past states of your database through versioning of the RDF data model level" (SE edition) — [GraphDB 9.4: Data history and versioning](https://graphdb.ontotext.com/documentation/9.4/standard/data-history-and-versioning.html).
- Linkurious keeps an **audit trail** of read and write operations, disabled by default, with `mode` (`r`/`w`/`rw`), `logResult`, and `strictMode` (synchronous logging before returning results); the docs warn that enabling it "can impact performances negatively" — [Linkurious: Audit trail](https://doc.linkurious.com/admin-manual/latest/audit-trail).

**Deprecation**
- DataHub keeps **deprecation and deletion as separate aspects**: "Deprecation is the deprecation aspect … Soft delete is the status aspect with `removed=true`"; deprecation carries a `note` and a `decommissionTime`; "Hard delete permanently removes the entity's rows … You can't undo it"; `datahub delete` is soft by default; stale-entity removal writes only the status aspect and "does not set or clear deprecation" — [DataHub Support: Dataset Deprecation and Soft Deletion](https://support.datahub.com/hc/en-us/articles/41912100671643).
- Deprecated glossary terms in DataHub stay functional: "The term remains in the system and its relationships are preserved. Assets tagged with the term retain those associations" — [DataHub: GlossaryTerm entity](https://docs.datahub.com/docs/generated/metamodel/entities/glossaryterm).
- OWL's original deprecation contract: `owl:DeprecatedClass` / `owl:DeprecatedProperty` mean "the term should not be used in new documents that commit to the ontology. This allows an ontology to maintain backward-compatibility while phasing out an old vocabulary" — [OWL Web Ontology Language Reference](https://www.w3.org/TR/owl-ref).
- OBO Foundry's operational rules for obsoleting a term are the most concrete published procedure: mark with `owl:deprecated "true"^^xsd:boolean` (or `is_obsolete: true`), "Prepend the string 'obsolete ' … to the term label", provide `replaced_by`, "developers SHOULD pre-announce term obsoletions", and if a definition change would "substantially change its referents, then a new term with new IRI and definition MUST instead be created" — [OBO Foundry: Principle 19, Term Stability](https://obofoundry.org/principles/fp-019-term-stability.html).
- Atlan expresses lifecycle as a **certificate** with four values: "**Verified** for ready to be used. **Draft** for work in progress. **Deprecated** if the asset no longer exists. **No certificate** if not required", and certificates are filterable in asset search — [Atlan: Add certificates](https://docs.atlan.com/product/capabilities/discovery/how-tos/add-certificates).
- Akeneo's automatic compatibility rules default to disabled: "Every new rule, including a duplicate, is disabled by default, so nothing is exposed in your catalog until you enable it" — an enable/disable lifecycle for a *rule* rather than per-edge — [Akeneo: Manage product compatibility](https://help.akeneo.com/serenity-build-your-catalog/manage-product-compatibility).

### Inferences
- The relation record (not the product) must be the unit of governance. Concretely: `relation_id, type_code, from_id, to_id, state, source_kind (manual|llm|co_purchase|rule|import), source_ref, confidence, evidence[], created_by, created_at, reviewed_by, reviewed_at, reject_reason, valid_from, valid_to, expires_at, superseded_by, version`.
- Rejection must be **stored and queryable**, not just a status flip: without it, an LLM re-proposes the same pair every run and reviewers burn out. DataHub's "full log of all accepted or rejected proposals" and the MDM steward queue's Rejected state both imply a durable negative memory. A `rejected_pairs` table keyed on `(from, to, type, source_kind)` with a cool-down is the cheap implementation.
- Atlan's explicit refusal to support per-link approval at scale is a warning, not a template: it works for term-linking where the blast radius is a tag, and fails for product semantics where a wrong `compatibility` claim breaks a customer's purchase. For us, per-relation review is mandatory, so the queue must be **batched by evidence pattern** (e.g. "142 co-purchase pairs for type `accessory`, confidence 0.6–0.7, same category") with approve-all/reject-all plus drill-down, rather than one card per pair.
- Evidence should be a list of typed, addressable items, not a free-text note: `co_purchase(order_count, window, support, lift)`, `llm(model, prompt_version, rationale_text, run_id)`, `manual(user_id, comment)`, `spec_sheet(document_url, page)`, `rule(rule_id, version)`. GraphDB's Proof plugin and RDF-star's `accordingTo` both show the value of being able to answer "why is this edge here?" mechanically.
- Deprecation of a *relation type* and of a *relation instance* are different operations and need different guards. Type deprecation needs the Collibra/OpenMetadata guard (block deletion while in use, expose usage counts) plus OBO's `replaced_by` + pre-announcement; instance expiry needs a TTL + revalidation job, which none of the catalog vendors document publicly.
- Ownership should be attached at three levels: the relation type (schema owner), the relation instance (reviewer/steward), and the product (catalogue owner). DataHub's split of `Edit Deprecation` / `Edit Lifecycle Stage` / `Edit Owners` shows these are genuinely separate permissions in practice, not one "edit" right.

### Gaps
- **No public source documents per-edge TTL or automatic revalidation** in Collibra, Atlan, DataHub or OpenMetadata. The nearest analogue is Akeneo's rule enable/disable and Linkurious case status, neither of which is time-based expiry. Any TTL design must be inferred, not cited.
- No public documentation of **relation-level audit granularity** in Collibra or Atlan (i.e. whether a change to a single relation appears in an activity feed with before/after values). DataHub documents its aspect-level history limits; the others do not publish equivalents.
- No public evidence on **how rejected LLM suggestions are remembered** in Atlan's Asset↔Term Linker beyond "a link is skipped if … the pair has been linked since" — the negative-memory behaviour is undocumented.
- Confidence scoring is documented as an output (Neo4j GDS probability, GraphDB similarity score, MDM thresholds) but **no surveyed catalogue product documents a calibrated confidence model for manually-reviewed semantic relations**.

## 3. How do they visualise graphs for exploration without making the graph the primary editing surface?

### Takeaway
The consistent pattern is **table/list first, graph second, and graph read-only**. DataHub and OpenMetadata both ship the same shape: a tabular "Related Terms" tab that is editable, plus a separate graphical view that is explicitly read-only and multi-hop. Graphs are used for *orientation* (what is central, what is orphaned, what is duplicated), not for authoring; where editing exists in a canvas (Linkurious), it is permissioned separately and audited.

### Cited Findings
- DataHub states the split outright: "**Related Terms** is a tabular view, grouped by relationship type. It supports editing — this is where you add and remove relationships. **Relationships** is a graphical view. It is read-only, but it shows more than one hop, so you can explore outward from the term" — [DataHub: Visualizing Your Ontology](https://docs.datahub.com/docs/features/feature-guides/ontology/visualizing-your-ontology).
- DataHub's graph exists in two scopes: a **global view** ("renders every glossary term that participates in at least one relationship") and a **focused view** anchored on one term ("The anchor term is badged as **Home**, and the graph starts one hop out. Expand any neighbour to walk further"), with a deep link `…/ontology?urn=…` — [DataHub: Visualizing Your Ontology](https://docs.datahub.com/docs/features/feature-guides/ontology/visualizing-your-ontology).
- The rationale for showing a graph at all is stated as pattern-finding: "A graph makes things easy to spot that a list does not: which concepts are central, which are orphaned, and where two teams have modelled the same idea twice" — [DataHub: Visualizing Your Ontology](https://docs.datahub.com/docs/features/feature-guides/ontology/visualizing-your-ontology).
- DataHub's graph has **filters as the primary interaction**: search "filters the graph to terms matching your query, along with the terms they are connected to", and "**Relationship types** filters the graph to specific relationship types. Selecting only *Inherits*, for example, collapses the graph down to your concept taxonomy … Each type shows how many edges of that type exist" — [DataHub: Visualizing Your Ontology](https://docs.datahub.com/docs/features/feature-guides/ontology/visualizing-your-ontology).
- Nodes with no relationships are hidden because "they carry no information in a relationship graph, and hiding them keeps the layout readable. The info bar at the bottom tells you how many were left out" — [DataHub: Visualizing Your Ontology](https://docs.datahub.com/docs/features/feature-guides/ontology/visualizing-your-ontology).
- Edge rendering carries semantics: edges are "labelled and colour-coded by its type", directed edges "drawn with an arrow pointing from source to destination", and hovering shows "its type, whether it is directed, and whether it is transitive" — [DataHub: Visualizing Your Ontology](https://docs.datahub.com/docs/features/feature-guides/ontology/visualizing-your-ontology).
- OpenMetadata's **Ontology Explorer** is likewise "the read-only graph view", with authoring pushed to a separate product surface ("Collate adds **Ontology Studio**, a workspace for authoring, reviewing, and publishing ontologies"); it has a summary bar with counts for Terms, Metrics, Relations and **Isolated** terms, glossary-box clustering, a Model/Data toggle, and Overview / Hierarchy / Cross Glossary view modes — [OpenMetadata: Ontology Explorer](https://docs.open-metadata.org/v2.1.x/how-to-guides/data-governance/ontology).
- Atlan follows the same shape: "Related assets displays all the assets that have associations with each other beyond a parent-child relationship", and "Related assets are additionally listed in the **Relations** tab of the asset sidebar"; the profile's Overview shows lineage view + related assets, with lineage downloadable as CSV or image — [Atlan: What are asset profiles?](https://docs.atlan.com/product/capabilities/discovery/concepts/what-are-asset-profiles).
- Atlan also puts the graph *inside* the glossary term sidebar as a small visual, not the editing surface: "Under Associated terms in the term profile, you can view a visual representation of your term relationships: Click any term attribute to focus on that specific term relationship … zoom … expand" — [Atlan: Set up glossaries](https://docs.atlan.com/product/capabilities/governance/glossary/how-tos/set-up-glossaries).
- Collibra keeps relations as a **table/tile/list on the Summary tab** of the asset page: "Both derived and explicit relations are shown on the Summary tab on an asset page, as a relation table, tile, or list", with a diagram icon on derived relations that "shows the relation paths on which the derived relation is based" — [Collibra: About relations](https://productresources.collibra.com/docs/collibra/latest/Content/Assets/Characteristics/Relations/co_relations.htm).
- Collibra's lineage viewer encodes **uncertainty and completeness in the canvas**: grey nodes mean "No relation exists between the data object and another"; a warning icon means "the name of a table was found by the transformations code search in the source code on which the analysis failed. Consequently, the lineage flow of the table is probably incomplete"; a "dot" arrow "Shows that there are hidden data objects … when only the endpoints of the technical lineage flow are shown" — [Collibra: The technical lineage graph](https://productresources.collibra.com/docs/collibra/latest/Content/CollibraDataLineage/TechnicalLineage/ref_technical-lineage-graph.htm).
- Neo4j Bloom is search-first by design: "Bloom is a search-first environment for you to explore your graph", where the search bar suggests Search phrases, graph patterns, full-text search and actions; **Perspectives** scope what vocabulary and styling a business user sees — [Neo4j Bloom: Search phrases](https://neo4j.com/docs/bloom-user-guide/current/bloom-tutorial/search-phrases-advanced), [Neo4j Bloom: Perspectives](https://neo4j.com/docs/bloom-user-guide/current/bloom-perspectives/bloom-perspectives).
- Bloom's **Search phrases** are "an alias for a pre-defined graph query, which is saved within a Perspective", can be parameterised, can chain parameters, and can call algorithms; but the docs warn "it is possible to modify data with a Search phrase as any valid Cypher query can be used. It is not recommended to use Search phrase for this goal as an end-user might not be aware of the consequences" — [Neo4j Bloom: Search phrases](https://neo4j.com/docs/bloom-user-guide/current/bloom-tutorial/search-phrases-advanced).
- Linkurious is the counter-example where the canvas *is* the workspace: "The workspace allows you to explore the graph database and represent it visualization as a node-link diagram", with a dashboard of saved visualisations, a data-model discovery view listing "all available node categories, edge types and how they're connected", and the properties of each — [Linkurious: First visualization](https://doc.linkurious.com/user-manual/latest/visualization-create/).
- Graphileon inverts the metaphor entirely: it is "a graph-driven dashboard development environment. It uses a graph-database to store user-interface components (e.g. Networks, Tables, Forms) in nodes … and triggers in relations … to define the interactions and data-flows between the UI components" — so the graph is the app definition, and end users see Networks/Tables/Forms/Charts/Maps/Timelines — [Graphileon Documentation](https://docs.graphileon.com/).
- Graphileon's own composition pattern is **table → network drill-down**, which is the same "list first, graph on demand" shape reached from the opposite direction: a dashboard wires a query to a `TableView`, and "Click on a table row to trigger a CypherQuery with output to a NetworkView, to display all individual instances", with right-click opening a separate context menu — [Graphileon: A table with rowClick and context menu](https://docs.graphileon.com/graphileon/For_Dashboard_Designers/Examples/A_table_with_rowClick_and_context_menu.html); the trigger mechanism is generic — "a Neo4jQuery can trigger a TableView to visualize its results" — [Graphileon: Triggers](https://docs.graphileon.com/archive/2.3.0/For_Dashboard_Designers/Triggers.html). *Caveat: the `docs.graphileon.com` host was unreachable from the research environment on repeated attempts; these two statements come from search-engine snippets of those pages, not from a directly fetched copy. Treat as indicative.*

### Inferences
- The defensible UI contract for a product catalogue: **product detail page = table of relations** (grouped by type, with state badge, source badge, confidence, reviewer, valid-until), **relation detail = drawer/page** (evidence list, history, approve/reject/expire), **graph = read-only, anchored on the current product, one hop by default, expand on click, capped node count**. This is DataHub's exact split and it survives large graphs.
- Graphs should be *filtered by relation type* before anything else, because that is what turns a hairball into a taxonomy view. Showing per-type edge counts in the filter (DataHub) also doubles as a cheap health metric ("we have 40k `accessory` edges and 12 `bundle` edges").
- Encode uncertainty in the visual language, following Collibra's lineage graph: dashed/dotted edges for derived or unconfirmed, solid for approved; a count badge for collapsed neighbours (DataHub); a visible "hidden N nodes" indicator whenever the render is truncated (DataHub's info bar, Collibra's dot arrow). Never let a truncated graph imply completeness.
- "Isolated entities" is a first-class metric worth copying from OpenMetadata: products with zero relations are the backlog for relation discovery, and surfacing the count creates a natural work queue.

### Gaps
- No public usability research or benchmark comparing table-first vs canvas-first curation throughput; the table-first consensus is inferred from the fact that DataHub, OpenMetadata, Atlan and Collibra all ship it, not from measured evidence.
- Linkurious documents canvas interaction limits but no public data on how many nodes users can meaningfully read before the view stops being useful (its thresholds are engineering limits, not perceptual ones — see §4).
- No surveyed catalogue documents a **"propose on the graph"** interaction (e.g. rubber-band two nodes to suggest a relation). Editing on canvas appears uniformly either absent or gated behind separate write permissions.

## 4. How do they scale to large graphs and keep editing safe?

### Takeaway
Two separate problems with two separate toolkits. **Scale** is handled by hard render caps, supernode detection, server-side layout, pre-computed search indexes and expand-on-demand — never by "just render it". **Safe editing** is handled by coarse-but-explicit permissions per node category / edge type, transactions with rollback, schema validation at write time (SHACL guard mode), and an audit trail that can be made synchronous when correctness matters more than latency.

### Cited Findings

**Render and query caps**
- Linkurious exposes the numbers: `supernodeThreshold` default **10000** adjacent edges before a node is treated as a supernode; `edgesBetweenSupernodes` default false ("Linkurious always return edges between a supernode and a regular node"); `expandThreshold` default **50** — "When the user expands a node with too many neighbors, Linkurious Enterprise will ask to refine the query so that fewer neighbors are returned"; `rawQueryLimit` default **500**; `rawQueryTimeout` default **60000 ms**; `sampledItemsPerType` default **1000** for schema sampling; `indexingChunkSize` default **5000** — [Linkurious: Advanced settings](https://doc.linkurious.com/admin-manual/latest/advanced-settings).
- Bloom caps visualisation work: "Bloom will limit the number of records processed for the visualization to **10000** unless a smaller limit has been set in the query. This is to prevent the app from hanging or crashing for queries that return too many records" — [Neo4j Bloom: Search phrases](https://neo4j.com/docs/bloom-user-guide/current/bloom-tutorial/search-phrases-advanced).
- Bloom also recommends query shape for performance: "It is recommended that Search phrases either return a path or a set of nodes. Returning only relationships may cause unexpected behaviour in addition to no graph visualization changes" — [Neo4j Bloom: Search phrases](https://neo4j.com/docs/bloom-user-guide/current/bloom-tutorial/search-phrases-advanced).
- DataHub's ontology graph "is capped at a fixed number of terms so the first render stays fast. The info bar says when the cap is in effect. Expand individual nodes, search, or filter by relationship type to reach beyond it" — [DataHub: Visualizing Your Ontology](https://docs.datahub.com/docs/features/feature-guides/ontology/visualizing-your-ontology).
- DataHub's impact analysis defaults to one hop "to minimize processor-intensive queries", offers 2 and 3+ degrees, and caps CSV export at **10,000 records** (progress shows "10,000+" when the cap is hit) — [DataHub: Lineage Impact Analysis](https://docs.datahub.com/docs/act-on-metadata/impact-analysis), [DataHub Support: Impact Analysis reports](https://support.datahub.com/hc/en-us/articles/50281784462363).
- Linkurious offloads heavy work off the request path: a "worker pool … used to run alerts, custom queries and compute server-side visualization layouts, so that these do not affect the application responsiveness" — [Linkurious: Advanced settings](https://doc.linkurious.com/admin-manual/latest/advanced-settings).

**Write-time validation**
- Stardog's **guard mode** turns constraints into transaction failures: "Once guard mode is enabled, modifications of the database (via SPARQL Update or any other method), whether adds or deletes, that violate the integrity constraints will cause the transaction to fail." It must be enabled explicitly (`icv.enabled=true`) with the DB offline, and validation by default runs **without** reasoning but can be run with it — [Stardog: Data Quality Constraints](https://docs.stardog.com/data-quality-constraints).
- SHACL gives the vocabulary for graded enforcement: `sh:severity` with `sh:Info`, `sh:Warning`, `sh:Violation` (default `sh:Violation`), and "The specific values of sh:severity have no impact on the validation, but MAY be used by user interface tools to categorize validation results" — i.e. a warning can be surfaced without blocking the write — [W3C: SHACL](https://www.w3.org/TR/shacl).
- SHACL's validation report is a machine-readable per-violation record: `sh:focusNode`, `sh:resultPath`, `sh:value`, `sh:sourceConstraintComponent`, `sh:sourceShape`, `sh:resultSeverity`, `sh:resultMessage` — a ready-made schema for "why was this edge rejected by the validator" — [W3C: SHACL](https://www.w3.org/TR/shacl).
- GraphDB requires the decision at repository-creation time: "If you need a repository with SHACL validation enabled, you must enable this option at configuration time. SHACL validation cannot be enabled after the repository has been created" — [GraphDB 11.1 manual](https://graphdb.ontotext.com/documentation/11.1/pdf/GraphDB.pdf).

**Permissions granularity**
- Neo4j RBAC is allowlist/denylist at graph-element level: "Privileges control the access rights to graph elements using a combined allowlist/denylist mechanism … You are able to access a resource if you have a GRANT (allowlist) and do not have a DENY (denylist) relevant to that resource"; privileges can be granted "on the entire graph or specific elements", and can be made immutable; Enterprise/Aura Business Critical only — [Neo4j: Role-based access control](https://neo4j.com/docs/operations-manual/2026.09/authentication-authorization/manage-privileges).
- Linkurious grants per **node category** and per **edge type**: `NONE` (can't search or display), `READ`, `EDIT` (edit properties), `CREATE AND DELETE` — a four-level ladder that maps almost 1:1 onto "see relation / see + annotate / create + remove relation" — [Linkurious: Standard access-rights](https://doc.linkurious.com/admin-manual/latest/access-rights).
- Stardog uses named graphs as a security boundary (named-graph security is a distinct resource type in its security model) — [Stardog: Named Graph Security](https://docs.stardog.com/operating-stardog/security/named-graph-security).
- DataHub authorises per **aspect** and per **action**, including a distinct `Edit Lineage` privilege for adding/removing lineage edges — so "may edit descriptions" does not imply "may assert relations" — [DataHub: Policies Guide](https://docs.datahub.com/docs/authorization/policies).
- Graphileon's own meta-model carries permissions as edges: "(:IA_Function {type})-[:REQUIRE {for: read|query|filter}]->(:IA_Permission)", with `(:IA_User)-[:ALLOW]->(:IA_Permission)` and nested teams — [Graphileon Knowledge](https://graphileon.com/graphileon-knowledge).

**Operational safety**
- Stardog's transaction model supports explicit rollback of in-flight work and permissioned rollback of another user's transaction, with the caveat that "Rolling back another user's transaction takes both actions: EXECUTE on its own is not enough, since a transaction you are not allowed to see is not one you may end" — [Stardog: Transactions](https://docs.stardog.com/operating-stardog/database-administration/transactions).
- DataHub warns that concurrent writers can silently overwrite each other: lineage "added by hand and programmatically may conflict with one another to cause unwanted overwrites", and recommends manual editing only where lineage is not also ingested, or enabling `incremental_lineage` — [DataHub: About DataHub Lineage](https://docs.datahub.com/docs/features/feature-guides/lineage).
- DataHub's `incremental_lineage` flag has a documented side effect that matters for TTL design: "if you do set this flag, lineage edges that used to exist will not be removed, and so you may need to use time-based filtering to accurately determine current lineage" — [DataHub: About DataHub Lineage](https://docs.datahub.com/docs/features/feature-guides/lineage).
- Linkurious treats audit as a correctness/latency trade-off: `strictMode: true` means "no results will be returned to the user until the logging operation is complete … This will ensure that no audit trail records are lost in case of system crash but can have a substantial negative effect on the responsiveness of the server" — [Linkurious: Audit trail](https://doc.linkurious.com/admin-manual/latest/audit-trail).

### Inferences
- For a catalogue of, say, 10^5–10^6 products and 10^6 relations, the graph should never be the query surface. Render caps of ~200–500 nodes, expand-on-demand, per-type filters and a precomputed adjacency table will beat any canvas. The vendor numbers (Bloom 10k, Linkurious 500 raw / 50 expand, DataHub fixed cap) are all *upper* bounds for exploration, not targets.
- "Supernode" handling is essential for products: a best-selling accessory or a universal charger will have tens of thousands of `compatibility` edges. Following Linkurious, the correct behaviour is to *not* draw edges between two supernodes, to always allow supernode↔normal edges, and to force the user to refine before expanding a supernode.
- Safe editing needs three independent mechanisms, not one: (a) **optimistic concurrency** on the relation record (version/etag, reject stale writes) — DataHub's overwrite warning shows what happens without it; (b) **write-time validation** of endpoint types, direction and cardinality (SHACL guard-mode pattern, but in the app layer); (c) **soft delete + audit** so a bad bulk import is reversible without a restore-from-backup.
- Because LLM and co-purchase sources are batch writers, they must be **idempotent upserts keyed on `(from, to, type, source_kind, run_id)`** and must never delete rows they did not create. This is the direct lesson from DataHub's manual-vs-ingested overwrite conflict and from Atlan's "Links are added, never replaced or removed".

### Gaps
- No public benchmark of relation-graph query latency at product-catalogue scale for any of these tools; all published numbers are configuration defaults, not measurements.
- Neo4j has no native per-edge TTL or per-edge version column documented as a first-class feature; TTL must be an application-level `expires_at` property plus a sweeper. No source found describing a vendor-native edge TTL.
- Collibra's derived-relations feature is documented with a performance caveat ("if you experience performance issues with a derived relation, use an explicit relation instead") but no published thresholds — [Collibra: About relations](https://productresources.collibra.com/docs/collibra/latest/Content/Assets/Characteristics/Relations/co_relations.htm).

## 5. What can we borrow for relation types, evidence, TTL, review queues and the knowledge base?

### Takeaway
Borrow five concrete patterns and reject three: (1) a typed relation registry with role/co-role and OWL-style characteristics, seeded and versioned as data; (2) relation-as-entity for anything with evidence, quantity or validity; (3) an explicit candidate→review→published lifecycle with durable rejection memory and graded severity; (4) deprecation-with-replacement plus usage guards instead of deletion; (5) table-first UI with a read-only, capped, type-filtered graph. Reject per-link manual approval at LLM scale (Atlan's own admission), in-place mutation of relation-type semantics (Akeneo's frozen flags, OBO's new-IRI rule), and graph-first authoring.

### Cited Findings
- **Registry as data, with stable identity + display labels + reverse labels**: Collibra (head/tail/role/co-role, system-managed types that can be renamed but not deleted), OpenMetadata (immutable name, display name, category, characteristics, RDF predicate, versioned with full history, usage counts before delete), DataHub (relationship type carries "the predicate identity … display name, direction semantics, transitivity, reverse label") — [Collibra](https://productresources.collibra.com/docs/collibra/2026.02/Content/Assets/Characteristics/Relations/RelationTypes/to_relation-types.htm); [Collate: Relationship Types](https://docs.getcollate.io/ai-2-0/how-to-guides/ontology/studio/relationship-types); [DataHub](https://docs.datahub.com/docs/features/feature-guides/ontology/custom-relationships).
- **Relation-as-entity for rich edges**: Collibra complex relations are "an entity that can't exist on its own", carry their own attributes, and support min/max cardinality per relation and per attribute; Neo4j's official alternative to a hyperedge is an "intermediate node" holding the shared context — [Collibra](https://productresources.collibra.com/docs/collibra/2026.08/Content/Assets/Characteristics/ComplexRelations/ComplexRelationTypes/co_complex-relation-types.htm); [Neo4j](https://neo4j.com/docs/getting-started/data-modeling/modeling-designs).
- **Quantified relations are a first-class kind, not a workaround**: Akeneo ships "association with quantities (when product A is associated with 2 quantities of product B)" and returns `quantity` on the association item — [Akeneo: association types](https://help.akeneo.com/serenity-build-your-catalog/34-serenity-manage-your-association-types); [Akeneo API](https://api.akeneo.com/api-reference.html).
- **Evidence/confidence annotation of a statement without asserting it**: RDF-star's `<<s p o>> :accordingTo :agent ; :confidence 0.8` pattern, with the explicit caveat that each annotation must stand alone — [RDF-DEV CG](https://www.w3.org/community/rdf-dev/2022/01/26/provenance-in-rdf-star); standardised in [W3C RDF-star](https://www.w3.org/2021/12/rdf-star.html); interoperable vocabulary in [PROV-O](https://www.w3.org/TR/prov-o/).
- **Provenance per source graph + explainable inference**: named graphs as the provenance container; GraphDB's provenance plugin for attributing derived statements, and its Proof plugin for "which rule fired and which premises have been matched" — [Stardog: RDF Graph Data Model](https://docs.stardog.com/tutorials/rdf-graph-data-model); [GraphDB provenance](https://graphdb.ontotext.com/documentation/10.0/provenance-plugin.html); [GraphDB inference/proof](https://graphdb.ontotext.com/documentation/10.8/inference.html).
- **Scored candidate generation as a separate stage**: Neo4j GDS link prediction "infer[s] the probability of the existence of a relationship between two non-adjacent nodes" trained on positive edges and sampled negatives; GraphDB similarity returns ranked results with scores; MDM queues route pairs between a manual-review threshold and an automatic-match threshold — [Neo4j GDS](https://neo4j.com/docs/graph-data-science/2026.09/machine-learning/linkprediction-pipelines/link-prediction); [GraphDB similarity](https://graphdb.ontotext.com/documentation/11.5/semantic-similarity-searches.html); [Verato](https://support.verato.com/hc/en-us/articles/11394384625172).
- **Review queue mechanics worth copying verbatim**: draft-by-default + assigned reviewers + task + threaded discussion + @mentions (OpenMetadata); propose/manage privilege split + reviewer inbox + permanent log of accepted *and* rejected (DataHub); pending/approved/rejected with reason on decision (Atlan, Linkurious cases, MDM steward queue) — [OpenMetadata](https://docs.open-metadata.org/latest/how-to-guides/data-governance/glossary/approval); [DataHub](https://docs.datahub.com/docs/managed-datahub/change-proposals); [Atlan](https://docs.atlan.com/product/capabilities/requests/how-tos/manage-requests); [Linkurious](https://doc.linkurious.com/user-manual/latest/alert-investigate/).
- **Pre-publish dry run**: Atlan's linker "sample decides every pair and writes nothing", then "Publishing writes the links the sample proposed. Each one is checked again first"; Akeneo requires a **Preview** and ships every rule disabled by default — [Atlan](https://docs.atlan.com/product/capabilities/governance/context-agents-studio/faq/asset-term-linker); [Akeneo](https://help.akeneo.com/serenity-build-your-catalog/manage-product-compatibility).
- **Deprecate, don't delete; and publish the replacement**: DataHub keeps deprecation (with `note`, `decommissionTime`) separate from soft delete and hard delete, and deprecated glossary terms keep their relationships; OBO requires `owl:deprecated true`, an "obsolete " label prefix, `replaced_by`, and pre-announcement; OWL states a deprecated term "should not be used in new documents" while remaining for backward compatibility — [DataHub Support](https://support.datahub.com/hc/en-us/articles/41912100671643); [DataHub GlossaryTerm](https://docs.datahub.com/docs/generated/metamodel/entities/glossaryterm); [OBO Foundry](https://obofoundry.org/principles/fp-019-term-stability.html); [OWL Reference](https://www.w3.org/TR/owl-ref).
- **Lifecycle stages with guarded transitions and hidden states**: DataHub's Draft / In Review / Rejected / Published / Deprecated / Archived, where only Published and Deprecated appear in default search, each stage declares `allowedPreviousStages`, and a violating change "is refused"; versions start in Draft so the previous version stays live until publication — [DataHub: Business Glossary](https://docs.datahub.com/docs/glossary/business-glossary).
- **Impact analysis before change, with depth control and export**: DataHub's degree-of-dependency default of 1, filters by entity type/platform/owner, CSV export, column-level selection, 10,000-record cap; Atlan's warehouse-side impact queries returning `DEPENDENCY_DEPTH` and a `NOTIFICATION_PRIORITY` ("DIRECT DEPENDENCY - HIGH PRIORITY") — [DataHub](https://docs.datahub.com/docs/act-on-metadata/impact-analysis); [Atlan](https://docs.atlan.com/platform/lakehouse/references/lineage-impact-analysis).
- **Usage-count guard before removing a type**: OpenMetadata's `GET /api/v1/glossaryTerms/relationTypes/usage` "returns each type with the number of relations currently using it" and the docs say to call it "to check how many relations use a type before you remove it"; Collibra's delete returns 400 when the type is used by DQ rules or derived relations — [Collate: Relationship Types](https://docs.getcollate.io/ai-2-0/how-to-guides/ontology/studio/relationship-types); [Collibra API](https://developer.collibra.com/api/references/data-governance/relation-types).
- **Graded validation instead of binary accept/reject**: SHACL `sh:Info` / `sh:Warning` / `sh:Violation` with per-result `focusNode`, `path`, `value`, `sourceConstraintComponent`; Stardog's guard mode converts violations into failed transactions at write time — [W3C SHACL](https://www.w3.org/TR/shacl); [Stardog](https://docs.stardog.com/data-quality-constraints).
- **Graph as read-only orientation, table as editing surface**: DataHub's editable "Related Terms" table vs read-only multi-hop "Relationships" graph; Collibra's relation table/tile/list on the asset Summary tab; OpenMetadata's read-only Ontology Explorer with authoring in a separate Studio — [DataHub](https://docs.datahub.com/docs/features/feature-guides/ontology/visualizing-your-ontology); [Collibra](https://productresources.collibra.com/docs/collibra/latest/Content/Assets/Characteristics/Relations/co_relations.htm); [OpenMetadata](https://docs.open-metadata.org/v2.1.x/how-to-guides/data-governance/ontology).
- **Caps, supernodes and truncated-view honesty**: Linkurious `supernodeThreshold` 10000 / `expandThreshold` 50 / `rawQueryLimit` 500; Bloom's 10000-record cap; DataHub's fixed initial term cap with an info bar; Collibra's dot arrow for hidden intermediate nodes — [Linkurious](https://doc.linkurious.com/admin-manual/latest/advanced-settings); [Bloom](https://neo4j.com/docs/bloom-user-guide/current/bloom-tutorial/search-phrases-advanced); [DataHub](https://docs.datahub.com/docs/features/feature-guides/ontology/visualizing-your-ontology); [Collibra lineage](https://productresources.collibra.com/docs/collibra/latest/Content/CollibraDataLineage/TechnicalLineage/ref_technical-lineage-graph.htm).

### Inferences — concrete borrowing list for product relations

| Concern | Borrow | From | Adapt for us |
|---|---|---|---|
| Relation type schema | head/tail asset types + role + co-role; immutable code; display + reverse label | Collibra, OpenMetadata, DataHub | `accessory`, `upgrade`, `alternative`, `bundle`, `compatibility` seeded as rows; `upgrade`/`accessory` directed with reverse labels ("upgraded by" / "accessory for"); `alternative` symmetric; `compatibility` directed and non-transitive |
| Type semantics | OWL characteristics as machine-actionable flags (symmetric, transitive, inverse, functional) | OpenMetadata, OWL 2 | Store `is_symmetric`, `is_transitive`, `inverse_type_code`; forbid transitive on `compatibility` and `alternative` (transitivity would wrongly chain A~B~C) |
| Rich edges | relation-as-entity with own attributes and min/max cardinality; quantified relations | Collibra CRT, Akeneo, Neo4j intermediate node | `bundle` = relation entity with `quantity`, `price_rule`, `valid_from/to`; `compatibility` = relation entity with `condition_text`, `spec_ref` |
| Evidence | list of typed evidence items; statement-level annotation without assertion | RDF-star, PROV-O, GraphDB proof | `evidence[]` rows: `{kind, ref, payload_json, captured_at}`; kinds `manual`, `llm`, `co_purchase`, `spec_sheet`, `rule`; always render "why is this edge here?" |
| Confidence | score + source + model/rule version, never a bare float | Neo4j GDS, GraphDB similarity, MDM thresholds | `confidence` + `confidence_method` + `scored_at`; two thresholds: auto-publish (never for semantics) and auto-reject; everything between goes to queue |

| Permissions | split propose vs manage vs deprecate vs edit-lineage; per-type grants | DataHub aspects, Atlan requests, Linkurious NODE/EDGE rights | roles: `viewer` (read published), `contributor` (propose), `merchandiser` (approve own category), `steward` (deprecate types, bulk import), `admin`; scope merchandiser by category |
| Impact analysis | depth-limited traversal + filters + export; "who depends on this" before deprecating | DataHub, Atlan | before deprecating a product or type: list affected products by type and depth, count customer-facing surfaces, export CSV for sign-off |
| UI | editable table by type + read-only anchored graph + type filters with counts + isolated count | DataHub, OpenMetadata, Collibra | product page: relations table grouped by type with state/source/confidence/valid-until; graph tab: 1-hop, expand, capped, dashed for unapproved; dashboard: "N products with no relations", "N candidates awaiting review" |
| Safety | idempotent upserts per source, no cross-source deletes, optimistic concurrency, soft delete | DataHub lineage warning, Atlan "links are added, never replaced" | batch writers own only their `source_kind` rows; `version` column with `If-Match`; delete = `status=deleted` + event |

- **Reject: per-link approval at machine scale.** Atlan's public position — "approving each link by hand isn't practical … the sample comes with a CSV you can download and audit instead" — is correct for tags and wrong for product semantics. Our review must be per-relation for anything customer-facing, which means the queue design (grouping, bulk actions, evidence-first sorting) carries the load, not the approval model.
- **Reject: editing relation-type semantics in place.** Akeneo freezes 2-way and quantity flags at creation; Collibra forces delete-and-recreate for CRT structure changes ("the new complex relation type will have a new ID"); OBO requires a new IRI when referents change. Changing `compatibility` from directed to symmetric, or `alternative` from non-transitive to transitive, must create a new type version with `supersedes`, and old edges must keep pointing at the old type.
- **Reject: graph-first authoring.** Every product that ships both surfaces makes the graph read-only. The one canvas-first tool (Linkurious) compensates with four-level per-type rights, an audit trail that can be made synchronous, and hard render caps — i.e. it pays for canvas editing with a lot of governance machinery we do not need if we keep the table as the editing surface.
- **Knowledge-base framing**: the relation store should be a *knowledge base of assertions*, not a *graph of facts*. Each row is a claim with an owner, a source, a confidence, a validity window and a review decision; the graph is a projection of currently-valid, approved claims. This is exactly the RDF-star distinction between quoting and asserting, and it is what makes "why is this here?", "who said so?", "is it still true?" and "what breaks if I remove it?" answerable without archaeology.

### Gaps
- No public source describes a **TTL/revalidation model for semantic relations** in any catalogue product; the TTL column above is a synthesis of adjacent mechanisms (Collibra CRT validity attributes, DataHub deprecation `decommissionTime`, Akeneo rule enablement), not a documented vendor feature. Treat it as a design proposal, not a citation.
- No public documentation of **how co-purchase-derived relations are governed** in any of the surveyed tools; Neo4j GDS link prediction is the nearest published mechanism and it stops at producing a probability.
- No public evidence on the **cost/latency of running SHACL validation per write** at catalogue scale; Stardog's guard mode is documented behaviourally but without performance figures.
- Whether any vendor supports **per-relation-type review SLAs or escalation** is undocumented; the review features found (tasks, inboxes, @mentions) are notification-level, not SLA-level.
