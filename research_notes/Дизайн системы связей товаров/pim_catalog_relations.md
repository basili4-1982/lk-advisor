# How PIM and e-commerce catalogs model and curate product-to-product relationships

Scope note: public documentation as of late 2026 (Akeneo Serenity/PIM 7, Pimcore 2026.3, Shopify API 2026-01+, Adobe Commerce 2.4.x + SaaS/CCDM, SAP Commerce 2205/2211, Bloomreach Discovery). No client data used. Sources are primary vendor docs unless explicitly flagged as vendor blogs.

Source-verification note (for the report writer): every URL below was HTTP-checked. Three exceptions are marked here so no claim rests on an unverified page — (1) the two `learning.sap.com` lesson pages (`cross-selling-and-up-selling-products`, `configuring-variant-products`) return 404 to a direct fetch because the site renders client-side; their content was captured from the search-result body and is used only for qualitative statements about the Backoffice flow and variant levels; (2) `help.shopify.com/en/manual/products/variants/add-variants` returns 403 to scripted fetches (bot blocking) but is a live public page, and its variant-limit text is corroborated by the Shopify changelog and blog; (3) the SAP "Modeling Product Variants" page now resolves 200 but its body is JS-rendered, so only the search abstract is quoted.

## How do the major systems model families, variants, and product-to-product links?

### Takeaway
Every mature system separates three things that are often conflated in homegrown catalogs: (1) an **attribute template** (family / attribute set / product type / class), (2) a **variant hierarchy** (product model → variant, base product → variant product, parent → children), and (3) **typed, directed links between product identities** (associations / product references / link types). The links are almost always a separate, first-class entity with a type + direction, not an attribute on the product.

### Cited Findings

**Akeneo**
- A family is "a set of attributes shared by products belonging to this family… a template for products"; a product belongs to **only one** family, may have none (then it has no default attributes and no completeness), and the family defines which attributes count as required for completeness — [Akeneo API concepts: Family](https://api.akeneo.com/concepts/catalog-structure.html); [What is a family?](https://help.akeneo.com/serenity-your-first-steps-with-akeneo/serenity-what-is-a-family)
- Variants are modeled with a **family variant** that fixes: number of variant levels (1 or 2), the variant axes per level, and the distribution of attributes between "common" and "variant" — [What about products with variants?](https://help.akeneo.com/serenity-your-first-steps-with-akeneo/serenity-what-about-products-with-variants)
- This yields up to **3 enrichment levels**: root product model → sub product model → variant product; a product model has a code but no SKU, a variant product has its own SKU (now optional) and UUID — [What about products with variants?](https://help.akeneo.com/serenity-your-first-steps-with-akeneo/serenity-what-about-products-with-variants)
- Associations are typed links to **products or product models**, defined by an Association Type that sets direction (1-way / 2-way) and optionally quantities ("1 oven, 2 shelves, 4 handles") — [Associations of products](https://help.akeneo.com/serenity-take-the-power-over-your-products/serenity-associations-of-products)
- Association types are **mandatory to create any link and there are no default types**; code is immutable after creation; the 2-way and "with quantity" flags **cannot be changed afterwards**; "2-way associations only allow two different products to be associated" — [Manage your association types](https://help.akeneo.com/v7-manage-your-association-types)
- Associations defined on a product model are **inherited by all its variant products**, and a variant product returns its model's associations in UI, API and exports — [Associations of products](https://help.akeneo.com/serenity-take-the-power-over-your-products/serenity-associations-of-products)
- Akeneo explicitly separates **three linking mechanisms**: manual associations (commercial: cross-sell, up-sell, substitution, product sets), automatic associations (technical fitment/compatibility), and **product link attributes** (when the link is part of the product data: bundle components, spare parts) — [Associations of products](https://help.akeneo.com/serenity-take-the-power-over-your-products/serenity-associations-of-products)
- The published comparison: manual = stored fixed matches, quantity support, shareable "Associated with" grid filter; compatibility = dynamic recomputation, unlimited matches, can target reference-entity records; product link attribute = single product, localizable/scopable, counts toward completeness, backlink on target; table attribute with product-link column = per-row metadata (measurement, text, date, boolean) and backlinks — [Define Product Compatibility](https://help.akeneo.com/serenity-build-your-catalog/manage-product-compatibility)
- Product link attributes have a **backlinks** view listing all products that link to the current product, regardless of locale/channel — [Manage composable products](https://help.akeneo.com/serenity-build-your-catalog/manage-composable-products-in-the-pim)
- API shape: `associations: { <associationTypeCode>: { products: [], product_models: [], groups: [] } }` plus a separate `quantified_associations: { <code>: { products: [{identifier, quantity}], product_models: [{identifier, quantity}] } }`; there are dedicated `GET /products-uuid/{uuid}/associations` and `GET /product-models/{code}/associations` endpoints returning typed items (product / product model / group / record, with `quantity` for quantified types) — [REST API reference](https://api.akeneo.com/api-reference.html)
- Association type API fields: `code`, `labels` (per locale), `is_quantified`, `is_two_way`; "Created without it, a manual association type is one-way and an automatic one is bidirectional" — [REST API reference](https://api.akeneo.com/api-reference.html)
- **No user-defined ordering** of associated items: products first, then product models; within each group sorted alphanumerically by internal ID; the same order is used in API/CSV/XLSX exports — [Associations of products](https://help.akeneo.com/serenity-take-the-power-over-your-products/serenity-associations-of-products)

**Pimcore**
- Relations are **data-type fields on the class**, not a global graph: Many-To-One, Many-To-Many, Many-To-Many Object Relation, plus **Advanced** variants that attach metadata columns (text, number, selection, boolean) to each link, editable inline in the object grid — [Relational Datatypes](https://docs.pimcore.com/platform/Pimcore/Objects/Object_Classes/Data_Types/Relation_Types)
- Advanced Many-To-Many allows mixing element types (documents, assets, objects) in one relation and exposes per-link metadata through GraphQL (`additionalLinkedElements { element { ... } metadata { name value } }`) — [GraphQL: advanced many-to-many metadata](https://docs.pimcore.com/platform/Datahub/GraphQL/Query/Query_Samples/Sample_Advanced_ManyToMany_Relation_Metadata)
- **Reverse Object Relation** fields expose and let editors modify relations *owned by another object* (e.g. "this accessory is an accessory of X") with **no storage of their own**; editing from the reverse side implicitly modifies the owning object and warns if that object is open elsewhere — [Reverse Object Relation Datatype](https://docs.pimcore.com/platform/Pimcore/Objects/Object_Classes/Data_Types/Reverse_Object_Relation_Type)
- Variants are child objects of type `OBJECT_TYPE_VARIANT`, hidden from the tree, shown in a dedicated "Variants" tab with paging/filtering/column hiding and visualization of **inherited values**; variants require inheritance to be enabled; a variant cannot contain objects of another class — [Object Variants](https://docs.pimcore.com/platform/Pimcore/Objects/Object_Classes/Additional_Class_Settings/Object_Variants)
- Structured per-category attributes are handled either by **Object Bricks** (own DB columns, supports relations, JOIN-able in listings) or **Classification Store** (EAV, simple types only, **no relations**, filtering only via custom subqueries); vendor rule of thumb: bricks for <30 categories, classification store beyond — [Object Bricks vs Classification Store](https://docs.pimcore.com/platform/Pimcore/Objects/Object_Classes/Object_Bricks_vs_Classification_Store/)

**Adobe Commerce / Magento**
- Product **types** carry the family role: simple, configurable (each option is a separate simple product with its own SKU), grouped (standalone products sold together, also purchasable separately), bundle ("build your own"), virtual, downloadable — [Create a product](https://experienceleague.adobe.com/en/docs/commerce-admin/catalog/products/product-create)
- Three native merchandising link types: Related Products (bought in addition; block on PDP, add-to-cart by checkbox), Up-sells (similar but higher quality/popularity/margin), Cross-sells (cart page, "impulse purchase"); each is a manually curated list with position — [Product settings – Related Products, Up-Sells, Cross-Sells](https://experienceleague.adobe.com/en/docs/commerce-admin/catalog/products/settings/related-products-up-sells-cross-sells)
- Correction to a common assumption ("Adobe hard-codes exactly three types"): in the schema, link types are **rows** in `catalog_product_link_type` (`link_type_id`, `code`) seeded with codes `relation`, `up_sell`, `cross_sell`, and the PHP constants are `LINK_TYPE_RELATED = 1`, `LINK_TYPE_UPSELL = 4`, `LINK_TYPE_CROSSSELL = 5` — so the set is extensible by adding rows/attributes even though the shipped UI only exposes three — [Catalog db_schema.xml](https://raw.githubusercontent.com/magento/magento2/2.4-develop/app/code/Magento/Catalog/etc/db_schema.xml); [InstallDefaultCategories.php (seeds link types + position attribute)](https://raw.githubusercontent.com/magento/magento2/2.4-develop/app/code/Magento/Catalog/Setup/Patch/Data/InstallDefaultCategories.php); [Model/Product/Link.php](https://raw.githubusercontent.com/magento/magento2/2.4-develop/app/code/Magento/Catalog/Model/Product/Link.php)
- Links are a real edge table with **typed per-link attributes**: `catalog_product_link(link_id, product_id, linked_product_id, link_type_id)` with a unique key on `(link_type_id, product_id, linked_product_id)`; per-link values live in `catalog_product_link_attribute` (`product_link_attribute_code`, `data_type`) plus typed value tables `_int` / `_decimal` / `_varchar` keyed by `link_id`. The seeded attribute is `position` (integer) for all three types — i.e. the same edge shape as Akeneo/Pimcore, just limited to one seeded attribute — [Catalog db_schema.xml](https://raw.githubusercontent.com/magento/magento2/2.4-develop/app/code/Magento/Catalog/etc/db_schema.xml); [InstallDefaultCategories.php](https://raw.githubusercontent.com/magento/magento2/2.4-develop/app/code/Magento/Catalog/Setup/Patch/Data/InstallDefaultCategories.php)
- **Inbound-link integrity is a DB-level cascade**: both `catalog_product_link.product_id` and `.linked_product_id` are foreign keys to `catalog_product_entity` with `onDelete="CASCADE"`, as are the link-attribute value tables on `link_id`; the variant table `catalog_product_relation(parent_id, child_id)` cascades on both columns too. So deleting a product silently removes every edge pointing at it (no block, no dangling rows) — [Catalog db_schema.xml](https://raw.githubusercontent.com/magento/magento2/2.4-develop/app/code/Magento/Catalog/etc/db_schema.xml)
- "Parent bundle product is always displayed as an up-sell product for all its child products automatically"; cross-sells can be shown/hidden per store view — [same](https://experienceleague.adobe.com/en/docs/commerce-admin/catalog/products/settings/related-products-up-sells-cross-sells)
- Storefront/API surface: GraphQL `related_products`, `upsell_products`, `crosssell_products`; Catalog Service returns a `links` array with `linkTypes: [related|crosssell|upsell]` — [products query](https://developer.adobe.com/commerce/webapi/graphql/schema/products/queries/products); [Catalog Service products query](https://developer.adobe.com/commerce/webapi/graphql/schema/catalog-service/queries/products/)
- CSV relation columns are fixed: `related_skus`, `upsell_skus`, `crosssell_skus`, comma-separated, **one row per SKU** — [KCS: importing upsell products does not update product links](https://experienceleague.adobe.com/en/docs/experience-cloud-kcs/kbarticles/ka-29955)
- Newer SaaS path: **CCDM / Merchandising Services** introduces catalog views (sources + policies + price books), **catalog layers that override attributes without changing source data**, policies (attribute-based assortment filters), recommendations, merchandising rules, facets, synonyms; "Commerce Foundation remains the source of truth for products and prices" — [Merchandising Services with CCDM overview](https://experienceleague.adobe.com/en/docs/commerce-admin/merchandising-with-ccdm/overview)

**SAP Commerce**
- Variants are modeled as **separate Product rows** linked by `baseProduct`, with variant types (`variantType`) and subtypes such as `ApparelStyleVariantProduct`; multi-level chains are normal (base → style/colour, non-purchasable → size, purchasable) — [Styles and Size Variants in the Product Cockpit](https://help.sap.com/docs/SAP_COMMERCE/4c33bf189ab9409e84e589295c36d96e/8af06a1b8669101483c085453d75849e.html); [Configuring Variant Products](https://learning.sap.com/learning-journeys/managing-products-in-the-backoffice-product-cockpit/configuring-variant-products)
- SAP documents **several alternative variant models** (including a `VariantProduct` subtype that only holds a relation to the variant product type), i.e. the variant model is an implementation decision, not a fixed platform primitive — [Modeling Product Variants](https://help.sap.com/docs/SAP_COMMERCE/917a3cf5902e4f7f9241ab456de71388/8c143a2d8669101485208999541c383b.html)
- Product-to-product links are `ProductReference` rows with a **qualifier/type enum** whose values are: `ACCESSORIES`, `BASE_PRODUCT`, `CONSISTS_OF`, `DIFF_ORDERUNIT`, `FOLLOWUP`, `MANDATORY`, `SIMILAR`, `SELECT`, `SPAREPART`, `OTHERS`, `UPSELLING`, `CROSSELLING` — [ProductReferenceTypeEnum (2205)](https://help.sap.com/doc/9fef7037b3304324b8891e84f19f2bf3/2205/en-US/de/hybris/platform/catalog/constants/GeneratedCatalogConstants.Enumerations.ProductReferenceTypeEnum.html)
- The reference DAO/service API takes `(qualifier, sourceProduct, targetProduct, type, …)`, confirming a typed edge record rather than a product field — [DefaultProductReferencesDao](https://help.sap.com/doc/9fef7037b3304324b8891e84f19f2bf3/2205/en-US/de/hybris/platform/catalog/references/daos/impl/DefaultProductReferencesDao.html)
- Out of the box the storefront Product References component renders "up to five products and the Similar reference type"; other types require developer customization — [Cross-Selling and Up-Selling Products](https://learning.sap.com/learning-journeys/managing-products-in-the-backoffice-product-cockpit/cross-selling-and-up-selling-products)

**Shopify**
- Shopify has **no first-class typed relation store**. Related recommendations are auto-generated from co-purchase/description/collection signals; only "related" is auto-generated, **complementary recommendations must be set up manually** (Search & Discovery app) — [Product recommendations](https://shopify.dev/docs/storefronts/themes/product-merchandising/recommendations)
- Custom relationships are modeled with **metafield reference types**: `product_reference`, `list.product_reference`, `metaobject_reference`, `list.metaobject_reference`, `list.mixed_reference`; docs explicitly warn: "Don't store handles or IDs in plain text fields… This breaks the connection between related data and prevents Shopify from retrieving it efficiently in Liquid or the Storefront API" — [Data modeling with metafields and metaobjects](https://shopify.dev/docs/apps/build/metaobjects/data-modeling-with-metafields-and-metaobjects); [List of data types](https://shopify.dev/docs/apps/build/metafields/list-of-data-types)
- Recommendation API: `GET /{locale}/recommendations/products.json?product_id=…&intent=related|complementary&limit=1..10` (default 10, default intent `related`) — [Product Recommendations API](https://shopify.dev/docs/api/ajax/reference/product-recommendations)
- Variants: up to **2,048 variants per product** for all merchants since Oct 15 2025, still **max 3 options**; >100 variants has caveats (250 media, themes/apps may not support) — [changelog](https://shopify.dev/changelog/posts/the-product-variant-limit-is-now-2048-for-all-merchants); [Adding variants](https://help.shopify.com/en/manual/products/variants/add-variants)
- **Combined listings** (Plus only) create a non-purchasable parent product over existing child products: parent + child options, up to **2000 variants across children**, parent max 3 options, max **60 child products**, one level only, cannot be a bundle — [About combined listings](https://shopify.dev/docs/apps/build/product-merchandising/combined-listings)
- Bundles are an app/API construct: fixed bundles via product-grouping API, customized bundles via cart-transform functions; Shopify Bundles app limits: **30 components fixed / 150 dynamic**, up to 2000 units per component, max 3 options and 100 variants per bundle, order lines list component SKUs not the bundle SKU — [Start building bundles](https://shopify.dev/docs/apps/build/product-merchandising/bundles/start-building); [Shopify Bundles](https://help.shopify.com/en/manual/products/bundles/shopify-bundles)

**Bloomreach (search/merchandising layer, not a PIM)**
- Merchandising is rule-based on top of the index: boost, bury, include, exclude, attribute rules, conditional **slots**, with preview of results per query/category/page and **global vs widget-level** rule layers ("Global-Recommendations rules only influence recommendation widgets like Frequently Viewed Together, Frequently bought Together, Similar Products") — [Product grid editor](https://documentation.bloomreach.com/discovery/docs/product-grid-editor); [Merchandising capabilities](https://documentation.bloomreach.com/discovery/docs/merchandising-capabilities)

**Cross-system comparison (all cells traceable to the findings above)**

| Capability | Akeneo | Pimcore | Adobe Commerce | SAP Commerce | Shopify |
|---|---|---|---|---|---|
| Attribute template | Family (1 per product) | Class (+ Object Bricks / Classification Store) | Attribute set | Product type + classification | Product type (weak) / metafields |
| Variant model | Family variant, 1–2 axes, 3 levels | Object variants (child, inherited) | Configurable (child simples) | baseProduct + variantType, multi-level | Variants (≤3 options, ≤2048) + combined listings |
| Link storage | Association type + quantified associations | Relation field (+ metadata columns) | `catalog_product_link` + `link_type` rows | ProductReference + enum qualifier | Metafield references |
| Direction | 1-way / 2-way | 1-way + Reverse field | 1-way (no inverse row) | 1-way (source→target) | 1-way only |
| Per-link data | quantity only | text/number/select/boolean | typed link attributes (only `position` seeded) | qualifier + custom attrs | whatever metafield type |
| Ordering | none (alphanumeric by ID) | list order in field | `position` link attribute | order in collection | list order |
| Inbound on delete | not documented | not documented | **DB `ON DELETE CASCADE`** on both FK columns | not documented | not applicable (metafield values die with the product) |
| Automatic | Rules engine + Product Compatibility | none built-in | Related product rules + Adobe AI | none built-in | auto "related" recommendations |
| Approval | Proposals (product-level) | Workflow engine (places/guards/permissions) | Staging + scheduled updates | Catalog version staged→online | none |
| Audit | Product version history (+restore) | Versions | Staging history | Catalog version + workflow audit | none native |
| Scale lever | search_after, 100/page, async bulk | object grid / custom | import/export CSV, async | ImpEx, sync jobs | JSONL bulk ops, 5 concurrent, 24h |

Table provenance caveats: Akeneo, Adobe, Shopify and Pimcore cells are directly documented in the findings above. Two SAP cells are weaker — "order in collection" is not documented (ProductReference is a collection, but no ordering guarantee was found), and "none built-in" for automatic relations reflects absence of evidence in the reviewed docs rather than a positive vendor statement. Pimcore "none built-in" likewise means no relation-generation engine is documented (it does ship a generic workflow engine and a data-quality scoring bundle).

### Inferences
- The reusable primitive is a **typed, directed edge** `(source, type, target, position/quantity, metadata, provenance, validity)`. Akeneo and SAP model it as a row with a type code; Adobe also stores rows in `catalog_product_link` with link types as rows and per-link typed attributes; Pimcore models it as a class field with optional metadata columns; Shopify delegates it to metafields/metaobjects.
- Mapping the requested relation types onto observed primitives: `accessory` ≈ Akeneo manual type / SAP `ACCESSORIES` / Shopify complementary; `upgrade` + `renewal` ≈ SAP `FOLLOWUP` (successor semantics) and Adobe up-sell; `alternative` ≈ SAP `SIMILAR` / Shopify "related"/substitute; `bundle` ≈ SAP `CONSISTS_OF`, Akeneo quantified association or Table+Product-Link, Shopify bundle app, Adobe bundle product type; `compatibility` ≈ Akeneo automatic association / SAP `MANDATORY`+attributes; `adjacent task` ≈ cross-sell.
- Only SAP's enum, Akeneo's free-form association types, and (at the DB level, not the admin UI) Adobe's `link_type` rows allow **arbitrary domain vocabularies**; what ships in Adobe's admin UI is three types, which is the weakest fit for a software catalog needing renewal/upgrade/compatibility — adding types means code/data work, not admin configuration.

### Gaps
- No primary source found describing **Akeneo association-level permissions or approval** (only product-level proposals).
- Pimcore has no built-in "related products" merchandising semantics; relation meaning is entirely project-defined — no vendor doc to cite for recommended retail relation taxonomy.
- SAP Commerce "Modeling Product Variants" page body could not be retrieved (repeated fetch returned empty); only the search abstract is used above.
- No public doc found for Salesforce B2B Commerce or commercetools relation modeling (search returned no results) — excluded rather than guessed.
- Adobe's **admin UI** documentation does not describe adding a fourth link type; only the schema shows types are rows. Whether a custom link type can be made usable in the admin without custom code was not documented — treat "Adobe is limited to 3 types" as true of the product, not of the schema.

## What is manual vs automatic, and how are suggestions reviewed, approved, rejected, versioned?

### Takeaway
The industry pattern is a **three-tier ladder**: stored manual links → rule-computed links (never stored, recomputed on read) → ML/behavioral recommendations. Review is a separate workflow layer that exists only at the *product/attribute* level (Akeneo proposals), not at the *relation* level; relation changes are audited through product version history instead.

### Cited Findings
- Akeneo **automatic associations (Product Compatibility)** are defined by a rule: source selection (family or filters) + target (products, product models, or **reference-entity records** such as vehicles/machines/brands) + attribute-value conditions; "The PIM resolves that rule dynamically, rather than storing a fixed, hand-picked list" — [Define Product Compatibility](https://help.akeneo.com/serenity-build-your-catalog/manage-product-compatibility)
- Compatibility rules have a **real-time Preview**: pick a primary product, see matching items, switch products freely — [same](https://help.akeneo.com/serenity-build-your-catalog/manage-product-compatibility)
- Curated hybrid flow: in the product's Associations tab the rule's matches are listed; "you can select one or more products and **send them to an existing Association Type**" (e.g. rule finds all iPhone 16 cases, merchandiser promotes the 5 best sellers into "You might also like") — [same](https://help.akeneo.com/serenity-build-your-catalog/manage-product-compatibility)
- Compatibility constraints: Premium feature, **100 rules per tenant**, unlimited matched pairs per rule, not supported in Apps, changes **do not emit a product-updated event**, several attribute types unusable in conditions (Identifier, Text area, Price, Image, Table, File, Asset collection, single Product link), product↔record links are always 1-way, records cannot be promoted into a manual association type — [same](https://help.akeneo.com/serenity-build-your-catalog/manage-product-compatibility)
- Akeneo **rules engine** (YML-defined, executed by cron daily 05:00 UTC, after bulk actions and after imports) can `add` or `set` associations, and the semantics are **partial by design**: `set` on `X_SELL.products` replaces only the product list, leaving associated product models/groups untouched; `add` appends without removing existing ones — [Get started with the rules engine](https://help.akeneo.com/v7-build-your-catalog/v7-get-started-with-the-rules-engine)
- Rules can be dry-run: "Calculate the affected products" populates an *Affected products* column before execution — [Get started with the rules engine](https://help.akeneo.com/v7-build-your-catalog/v7-get-started-with-the-rules-engine)
- Akeneo **proposals** (collaborative workflow) have four review states: *In progress* (not reviewable), *Waiting for approval*, *Can be partially reviewed* (permission-scoped), *Can't be reviewed*; approval can be **per change**, not only per proposal — [Review product proposals](https://help.akeneo.com/en_US/v5-collaborative-work/175-v5-review-product-proposals)
- Approving a change "adds the value to the product, which **creates a new product version**"; the approved change is removed from the proposal; mass approve/reject actions exist — [same](https://help.akeneo.com/en_US/v5-collaborative-work/175-v5-review-product-proposals)
- Akeneo version history is created for: attribute value changes, enabled/disabled status, family change, **association changes**, and category changes; each version records author/system, timestamp to the second, and old/new value — [Enrich your product (history)](https://help.akeneo.com/v4-take-the-power-over-your-products/174-v4-enrich-your-product)
- Version **restore** is package-gated (Advanced/Premium), restores one product at a time, clears values absent from the restored version, and History displays **up to 200 versions** — [Restore a previous product version](https://help.akeneo.com/serenity-take-the-power-over-your-products/serenity-restore-a-previous-product-version)
- Adobe Commerce has **related product rules** (Commerce only, not Open Source): conditions on *Products to Match*, results from *Products to Display*, `Apply To` = Related / Up-sells / Cross-sells, priority (1 = highest), date range, **Result Limit max 20**, optional customer segment and Real-Time CDP audience — [Create a related product rule](https://experienceleague.adobe.com/en/docs/commerce-admin/marketing/promotions/product-relationships/product-related-rule-create)
- Precedence rule: "Any up-sell, cross-sell, and related products that were **manually configured always appear before** any rule-based product promotions"; product sort order inside a rule result set is random; rule conditions always evaluate at **All Store Views** scope even if attributes are store-scoped; attributes must be flagged "Use for Promo Rule Conditions" to be usable — [same](https://experienceleague.adobe.com/en/docs/commerce-admin/marketing/promotions/product-relationships/product-related-rule-create)
- Adobe also offers **Product Recommendations powered by Adobe AI** as an alternative to manually configured recommendations/up-sells — [Product relationships](https://experienceleague.adobe.com/en/docs/commerce-admin/marketing/promotions/product-relationships/product-relationships)
- Adobe scheduled changes: all updates apply consecutively, an entity can have **only one scheduled update at a time**, and each applies to **all store views**; preview opens the storefront as it will look during the campaign and is shareable — [Schedule a content update](https://experienceleague.adobe.com/en/docs/commerce-admin/content-design/staging/content-staging-scheduled-update)
- Shopify: related recommendations are auto-generated from co-purchase/description/collection similarity and "become more accurate over time as more order and product information becomes available"; complementary must be manual; both are customized in the Search & Discovery app — [Adding a related products section](https://help.shopify.com/en/manual/online-store/themes/customizing-themes/common-customizations/add-product-recommendations); [Customizing product recommendations](https://help.shopify.com/en/manual/online-store/storefront-search/search-and-discovery-recommendations)
- Shopify recommendation eligibility is **filtered at render time**: not sold out (complementary requires stock > 0), not Unlisted, price > 0, not a gift card, published to Online Store, not already in cart; B2B recommendations are scoped to the buyer's company catalogs — [Customizing product recommendations](https://help.shopify.com/en/manual/online-store/storefront-search/search-and-discovery-recommendations)
- SAP has no rule-based relation generator in the docs reviewed; relations are curated records, and merchandising control lives in **catalog version staging + synchronization** and in the CMS component configuration ("up to five products and the Similar reference type" out of the box) — [Cross-Selling and Up-Selling Products](https://learning.sap.com/learning-journeys/managing-products-in-the-backoffice-product-cockpit/cross-selling-and-up-selling-products)
- Pimcore is the one reviewed system with a **generic state machine that can gate publishing**: workflows define *places*, *transitions* (with optional **guard** Symfony expressions that block the transition), and **per-place permission overrides** for `save / publish / unpublish / delete / rename / view / settings / versions / properties`, plus per-transition notifications and required comment/extra fields — [Workflow configuration](https://docs.pimcore.com/platform/Pimcore/Workflow_Management/Configuration/); [Workflow configuration details](https://docs.pimcore.com/platform/Pimcore/Workflow_Management/Configuration/Configuration_Details/)
- Bloomreach's model is rules-first with manual overrides: boost/bury/include/exclude, attribute rules, conditional slots, per-query/category/page scope, global vs widget layers — [Product grid editor](https://documentation.bloomreach.com/discovery/docs/product-grid-editor)

### Inferences
- **Nobody reviews relations as a first-class object.** The closest patterns are (a) Akeneo's "rule produces candidates → human promotes selected ones into a stored type" and (b) Adobe's "manual list renders before rule output". Both are effectively an *approve-to-store* pattern and are the cheapest thing to copy.
- Versioning of relations happens as a **side effect of product versioning** (Akeneo explicitly lists association changes as a version trigger). There is no vendor evidence of diffing a relation set across time, so a system that wants "who added this accessory link and when" must model the edge as its own versioned record.
- Adobe's "manual always before rules, rule results random order, max 20" is a concrete, citable precedence policy that is easy to reuse and explain to merchandisers.
- Dynamic (non-stored) compatibility is the correct choice for high-cardinality fitment (one product fits hundreds of models); stored links are the correct choice for anything needing order, quantity, curation or approval.

### Gaps
- No primary documentation found for **rejecting an automatically suggested relation** as a distinct state (Akeneo compatibility has no "reject/blacklist a match" concept in the reviewed docs; the workaround is to not promote it).
- No source describing relation-level approval in Adobe Commerce or Shopify (only product-level staging / no approval at all).
- No public data on how Akeneo's 100-rule tenant cap behaves at 136k-SKU scale, or on recomputation cost.

## Scale, bulk editing, import/export, localization, and consistency across merge/split/retire

### Takeaway
Scale is handled by (a) **hard UI caps with API escape hatches**, (b) **asynchronous bulk jobs with report artifacts**, (c) **cursor pagination**, and (d) **staged→online catalog versions** rather than per-record publishing. Merge/split is handled only at the *variant hierarchy* level (re-parenting) — no vendor documents a true product-identity merge that rewrites incoming relations.

### Cited Findings
- Akeneo product grid "can display a maximum of **10,000 results** across all pages"; beyond that you must narrow filters; lists/filters in the associations view also stop at 10,000 and "use the API to retrieve the full list" — [Get familiar with the Product Grid](https://help.akeneo.com/serenity-take-the-power-over-your-products/serenity-get-familiar-with-the-product-grid); [Associations of products](https://help.akeneo.com/serenity-take-the-power-over-your-products/serenity-associations-of-products)
- Akeneo REST: max **100 items per page** (422 above that); `search_after` cursor pagination is "strongly recommended" for products/product models/published products/assets/reference entities because offset paging slows down and can return **duplicates** — [REST API basics: pagination](https://api.akeneo.com/documentation/pagination.html)
- Akeneo bulk actions: edit attribute values, add attribute values (multi-valued only; Table attribute unsupported), change family, add to product model, **change the parent product model**, **convert to simple products**, associate to products, publish/unpublish; each operation has its own permission — [Bulk actions on products](https://help.akeneo.com/v7-boost-your-productivity/v7-bulk-actions-on-products)
- Bulk edits apply to the **scope and locale currently selected in the grid** — changing several locales/scopes requires several bulk actions — [same](https://help.akeneo.com/v7-boost-your-productivity/v7-bulk-actions-on-products)
- Mass delete/product-model delete runs as a **back-end task** with a notification and a report page; deleting a product model deletes all children — [same](https://help.akeneo.com/v7-boost-your-productivity/v7-bulk-actions-on-products)
- Merge/split is supported as **re-parenting**: "To allow more flexibility on variant products (such as merging or splitting product models), you can now change the parent product model"; the new parent must use the **same family variant**, otherwise the move is refused; common attributes then take the new parent's values. Documented use cases: merging two ERP beer models into one size range; splitting a t-shirt model into "solid colours" vs "floral" — [same](https://help.akeneo.com/v7-boost-your-productivity/v7-bulk-actions-on-products)
- Akeneo import of associations: products are created first and associations applied afterwards, so **row order does not matter**, but a product imported without its identifier cannot receive associations; for 2-way types **both sides must be declared**, otherwise previously created links are removed — [Associations of products](https://help.akeneo.com/serenity-take-the-power-over-your-products/serenity-associations-of-products)
- Adobe relation import pitfall: relations "should be comma-separated… only one row is required per SKU, and each product relation type must use its own column"; a row-per-link CSV (`sku, link_type, linked_sku, position`) **silently imports nothing** — [KCS ka-29955](https://experienceleague.adobe.com/en/docs/experience-cloud-kcs/kbarticles/ka-29955)
- Adobe staging: catalog/content changes are staged and previewed per campaign, but **one scheduled update per entity at a time**, applied to all store views — [Schedule a content update](https://experienceleague.adobe.com/en/docs/commerce-admin/content-design/staging/content-staging-scheduled-update)
- SAP: the customer-visible catalog is `online`, working copies are `staged`; synchronization is **unidirectional staged→online**, can target a whole catalog version **or selected categories/products**, and catalog *systems* chain multiple input catalogs (supplier A, supplier B) into a master catalog and then into language/country output catalogs; "there is no technical difference between catalogs and catalog versions… the online catalog differs only by access rights" — [Synchronizing Catalogs](https://help.sap.com/docs/SAP_COMMERCE/d0224eca81e249cb821f2cdf45a82ace/8c6a38118669101481bdf1303d70949e.html)
- SAP Product Cockpit: mass data editing in list view, copy/paste of data, runtime view customization (columns/sections/fields), role-based attribute/class/catalog-version permissions, validation rules for data formats, workflow tracking/commenting/status, product comparison, staged work without touching the live site — [Product Cockpit](https://help.sap.com/docs/SAP_COMMERCE/5c9ea0c629214e42b727bf08800d8dfa/8c325596866910148a15ee72de6fe321.html)
- Shopify bulk ops: JSONL input, `bulkOperationRunMutation`; since API **2026-01** each app can run **5 bulk mutations concurrently** per shop (previously 1); an operation must finish within **24 hours** or it is stopped and marked failed — [Bulk import data](https://shopify.dev/docs/api/usage/bulk-operations/imports)
- Shopify relation storage limits: metafield values capped at **2 MB** each; `metafieldsSet` accepts **25 metafields per request** (10 MB payload); `metafieldsDelete` 250 per request; definitions usable as admin filters are capped at 50 — [Metafield limits](https://shopify.dev/docs/apps/build/metafields/metafield-limits)
- Shopify variant upload rate limit: stores with ≥500,000 variants are limited to **10,000 new variants/day** via app or CSV (waived on Plus) — [Adding variants](https://help.shopify.com/en/manual/products/variants/add-variants)
- Localization/scope differences: Akeneo's published comparison credits "localizable and scopable" only to the **product link attribute** and to the **Table attribute with a product-link column**, not to manual associations, while ordinary attribute values are locale+scope keyed; Adobe rule conditions always evaluate at All Store Views scope even when the underlying attribute is store-scoped — [Define Product Compatibility](https://help.akeneo.com/serenity-build-your-catalog/manage-product-compatibility); [Create a related product rule](https://experienceleague.adobe.com/en/docs/commerce-admin/marketing/promotions/product-relationships/product-related-rule-create)
- Supersession modeling (vendor guide, spare-parts domain): a `REPLACED_BY` edge needs **direction, effective date, quantity ratio, reason, source, status**; chains must be resolved to a terminal node, cycles flagged, depth capped (~5–10 hops); splits are one-to-many with a ratio **per branch**, merges many-to-one with a ratio per incoming edge; a denormalized `current_successor_id` avoids traversal at query time and must be recomputed on every new link — [How to Model Supersession Chains](https://getclaro.ai/resources/guides/model-supersession-chains-in-a-catalog/) *(vendor guide, not platform documentation)*
- That guide also enumerates the failure mode of naive two-column old→new tables: multi-hop chains, splits, unknown effective dates, and "search for old SKU returns no results / returns the old part as current / returns only the immediate successor" — [same](https://getclaro.ai/resources/guides/model-supersession-chains-in-a-catalog/)

### Inferences
- For ~136k offers, the observed ceilings (Akeneo 10k grid, 100/page API, Shopify 24h bulk) imply: never rely on "select all in UI" as the bulk mechanism; the bulk editor must be **query-driven and asynchronous**, with a job report.
- The re-parenting guard in Akeneo (same family variant or refuse) is a good model for a **structural invariant check** on merge/split: refuse the operation rather than silently producing an inconsistent hierarchy.
- Deletion behaviour is a documented fork, not a universal: Adobe **cascades** (FK `ON DELETE CASCADE` on both `product_id` and `linked_product_id`), so inbound links vanish silently with no warning; Akeneo documents only that deleting a product model deletes its children. Neither offers "block deletion while inbound links exist". A catalog that must keep renewal/upgrade chains intact therefore cannot rely on platform behaviour and has to own the protocol: either block deletion while inbound edges exist, or rewrite edges transactionally and log it as a versioned event.
- The supersession field set (effective date, ratio, reason, source, status, confidence) maps almost 1:1 onto software-license realities (old SKU → renewal SKU, 1 seat → 5 seats, "vendor bulletin" → price-list/EDI feed), and the "old SKU resolves to terminal successor" rule is directly reusable for renewal and upgrade links.

### Gaps
- Inbound-relation integrity on delete is now answered for Adobe (DB cascade) but **not documented** for Akeneo, Pimcore or SAP Commerce; Akeneo documents only that model deletion cascades to children. No reviewed platform offers "block deletion while inbound links exist", and none documents what happens to an inbound link when two products are *merged* (as opposed to deleted).
- No public benchmark of any of these systems at 136k products with dense relations; no published numbers on association-count limits per product.
- Localization of relation *labels* is documented (Akeneo association type labels per locale), but localization of relation *targets* (e.g. a different accessory per country) is not documented in any reviewed system.

## What screens and workflows do merchandisers actually use?

### Takeaway
The convergent merchandiser toolkit is: **filterable data grid with configurable columns + saved views**, **inline/mass edit with permissions per operation**, **sequential edit**, **a picker modal with search & filters + selection basket**, **rule preview/dry-run**, **storefront preview of staged changes**, and **an audit/history tab**. Nobody does graph editing; relations are edited as lists inside a product form. Note the one thing that is *not* observed: a true side-by-side relation diff editor. Vendors ship product-level comparison (SAP), sequential edit (Akeneo) and staged preview (Adobe), but not a two-pane "current links vs proposed links" tool.

### Cited Findings
- Akeneo grid: list vs gallery view; configurable columns; saved **Views** and **Projects**; channel/locale switch; inline editing of categories, status, booleans, text, text area, simple/multi-select; a **Flat** mode that shows every record (models, sub-models, variants, simple products) ungrouped "ideal for task management"; completeness shown as `2/3` variants complete for a model — [Get familiar with the Product Grid](https://help.akeneo.com/serenity-take-the-power-over-your-products/serenity-get-familiar-with-the-product-grid)
- Akeneo selection model: individual checkboxes, "Select all" (all matching filters except manually deselected), "Unselect all"; Selection Toolbar appears at the bottom with the selected count — [same](https://help.akeneo.com/serenity-take-the-power-over-your-products/serenity-get-familiar-with-the-product-grid)
- Akeneo **Sequential Edit** opens each selected product in turn with previous/next controls — [same](https://help.akeneo.com/serenity-take-the-power-over-your-products/serenity-get-familiar-with-the-product-grid)
- Akeneo association picker: "Add associations" opens a selector with filters (category, label, identifier, custom filters), a grid with checkboxes, a **basket**, then Confirm; quantified types render as a **list** instead of a gallery — [Associations of products](https://help.akeneo.com/serenity-take-the-power-over-your-products/serenity-associations-of-products)
- Akeneo reverse lookup UX: an "Associated with" grid filter plus a button next to each manual association type that opens a filtered grid of everything associated; the filtered grid URL is shareable — [Associations of products](https://help.akeneo.com/serenity-take-the-power-over-your-products/serenity-associations-of-products)
- Akeneo proposal review is reachable from 4 places (dashboard widget, notification center, product form menu, proposals grid) and supports filters on family/author/proposed date/SKU plus attribute-value filters — [Review product proposals](https://help.akeneo.com/en_US/v5-collaborative-work/175-v5-review-product-proposals)
- Adobe product edit: "Related Products, Up-Sells, and Cross-Sells" collapsible section → *Add Related Products* → filter grid → checkbox selection → *Add Selected Products*; rows show thumbnail, name, status, attribute set, SKU, price, and a Remove action — [Product settings](https://experienceleague.adobe.com/en/docs/commerce-admin/catalog/products/settings/related-products-up-sells-cross-sells)
- Adobe rule authoring mirrors catalog price rules (conditions builder in a left panel), with an explicit *Products to Match* / *Products to Display* split — [Create a related product rule](https://experienceleague.adobe.com/en/docs/commerce-admin/marketing/promotions/product-relationships/product-related-rule-create)
- Adobe preview: staging preview opens a new tab showing the storefront during the campaign, always starting from the default store view, and the link can be **shared with colleagues** — [Schedule a content update](https://experienceleague.adobe.com/en/docs/commerce-admin/content-design/staging/content-staging-scheduled-update)
- SAP Product Cockpit: list view and grid view perspectives, mass editing **in list view**, copy/paste of data between records, favorites, switchable roles, runtime column/section customization, integrated DAM, product comparison, workflow actions (track/comment/status) — [Product Cockpit](https://help.sap.com/docs/SAP_COMMERCE/5c9ea0c629214e42b727bf08800d8dfa/8c325596866910148a15ee72de6fe321.html)
- SAP reference creation: in the Backoffice Product Cockpit you create a reference by **selecting the reference type first**, then the target product — [Cross-Selling and Up-Selling Products](https://learning.sap.com/learning-journeys/managing-products-in-the-backoffice-product-cockpit/cross-selling-and-up-selling-products)
- Pimcore: relations are edited as drag-and-drop fields in the object editor; the **object grid** can display and inline-edit relation metadata columns; reverse relations let you edit from the target side (with a warning if the owner is open) — [Relational Datatypes](https://docs.pimcore.com/platform/Pimcore/Objects/Object_Classes/Data_Types/Relation_Types); [Reverse Object Relation](https://docs.pimcore.com/platform/Pimcore/Objects/Object_Classes/Data_Types/Reverse_Object_Relation_Type)
- Pimcore data quality: a **score** computed from weighted rule definitions (mandatory/validation check, recommended fields, Symfony expressions), shown in editor, grid and tree, with auto-generated **improvement suggestions** in a "Data Quality Details" tab and a precondition to scope scoring — [Data Quality Management](https://docs.pimcore.com/platform/Data_Quality_Management)
- Shopify admin: relations are not a native screen; recommendations are configured in the **Search & Discovery app**, and theme sections (related / complementary) are added and configured in the theme editor — [Adding a related products section](https://help.shopify.com/en/manual/online-store/themes/customizing-themes/common-customizations/add-product-recommendations)
- Bloomreach: the primary tool is a **visual grid editor** with drag-in "Add product", boost/bury, include/exclude, attribute rules, slots, and immediate **preview** of the result set for a query/category/page; "Already in Recall" labeling prevents duplicates — [Product grid editor](https://documentation.bloomreach.com/discovery/docs/product-grid-editor)

### Inferences
- The highest-leverage screens to copy, in order: (1) grid with saved views + inline edit, (2) product-form relation tab with picker modal + basket + reverse "associated with" filter, (3) rule with dry-run count and preview, (4) staged preview link, (5) history/audit tab.
- A **shareable filtered "associated with" URL** is a cheap, high-value feature (Akeneo) — it turns relations into a reviewable queue without building a new app.
- Split view / side-by-side comparison is weakly documented: Adobe and SAP document product *comparison* (SAP explicitly), Akeneo documents sequential edit rather than split view. For a relation-curation tool, a two-pane "source product | candidate relations" layout is an inference, not an observed pattern.
- Pimcore's weighted data-quality score + suggestions is the most directly reusable "validation UX" pattern: it makes relation completeness (e.g. "no alternative linked", "no renewal SKU") a scored, actionable metric rather than a hard block.

### Gaps
- No documentation found of a true **split-view/diff editor for relations** in any of the reviewed systems (Akeneo has compare/translate for values, not for relation sets).
- No public screenshots/flows for SAP's newer (non-deprecated) Product Cockpit reference editing; the reviewed pages are marked deprecated.
- No evidence of merchandisers editing relations in bulk *with per-link metadata* in any system except via CSV/import.

## What are the strengths and failure modes of each approach?

### Takeaway
Typed-edge models (Akeneo, SAP, and Adobe at the schema level) are the most expressive and the most expensive to govern; fixed-type models (Adobe's *product surface*) are simple but cannot express renewal/upgrade/compatibility; field-based models (Pimcore) are maximally flexible but push all semantics and validation into custom code; metafield models (Shopify) are fast to start and structurally weak (no referential guarantees, no ordering, no inverse).

### Cited Findings
- Akeneo strength: one association type can carry direction, quantity and locale-aware labels, and is inherited by variants; weakness: types are **immutable after creation** (no converting a 1-way type to 2-way, no adding quantities later) and there are **no default types**, so every implementation starts from a blank taxonomy — [Manage your association types](https://help.akeneo.com/v7-manage-your-association-types)
- Akeneo weakness: **no user-defined order** for associated items (alphanumeric by internal ID, products before models) — merchandising order must be handled downstream — [Associations of products](https://help.akeneo.com/serenity-take-the-power-over-your-products/serenity-associations-of-products)
- Akeneo weakness: 2-way import is order-sensitive in a non-obvious way — omitting the reverse declaration **deletes** links created on earlier rows — [same](https://help.akeneo.com/serenity-take-the-power-over-your-products/serenity-associations-of-products)
- Akeneo automatic associations weakness: dynamic results are **not evented** ("changes to these compatibility links do not trigger a product updated event"), capped at 100 rules/tenant, and unusable in Apps — a real integration hazard — [Define Product Compatibility](https://help.akeneo.com/serenity-build-your-catalog/manage-product-compatibility)
- Adobe strength: three link types map cleanly to three storefront slots (PDP block, PDP up-sell, cart cross-sell) and are trivially explicable to business users; rules add targeting by segment/audience with explicit precedence — [Product relationships](https://experienceleague.adobe.com/en/docs/commerce-admin/marketing/promotions/product-relationships/product-relationships); [Create a related product rule](https://experienceleague.adobe.com/en/docs/commerce-admin/marketing/promotions/product-relationships/product-related-rule-create)
- Adobe weakness: only three relation semantics are exposed in the product surface; "accessory", "alternative", "renewal", "compatibility" have no native home and must be overloaded onto related/up-sell or custom attributes; rule results capped at 20 and randomly ordered within a set. The DB does allow extra `link_type` rows and extra per-link attributes (`_int`/`_decimal`/`_varchar` value tables), so the limitation is product/UI depth rather than data model — but exploiting it is developer work, not merchandiser configuration — [Create a related product rule](https://experienceleague.adobe.com/en/docs/commerce-admin/marketing/promotions/product-relationships/product-related-rule-create); [Catalog db_schema.xml](https://raw.githubusercontent.com/magento/magento2/2.4-develop/app/code/Magento/Catalog/etc/db_schema.xml)
- Adobe weakness: deletion is a silent cascade — `ON DELETE CASCADE` on both sides of `catalog_product_link` means retiring a SKU erases every related/up-sell/cross-sell edge pointing at it, with no referential error and no audit row — [Catalog db_schema.xml](https://raw.githubusercontent.com/magento/magento2/2.4-develop/app/code/Magento/Catalog/etc/db_schema.xml)
- Adobe weakness: CSV relation import fails **silently** with a plausible-looking row-per-link format — a documented support article exists precisely because of this — [KCS ka-29955](https://experienceleague.adobe.com/en/docs/experience-cloud-kcs/kbarticles/ka-29955)
- SAP strength: the richest built-in vocabulary (`FOLLOWUP`, `SPAREPART`, `CONSISTS_OF`, `DIFF_ORDERUNIT`, `MANDATORY`, `SELECT`, `ACCESSORIES`, `SIMILAR`, `UPSELLING`, `CROSSELLING`), plus catalog-version staging/sync for controlled rollout — [ProductReferenceTypeEnum](https://help.sap.com/doc/9fef7037b3304324b8891e84f19f2bf3/2205/en-US/de/hybris/platform/catalog/constants/GeneratedCatalogConstants.Enumerations.ProductReferenceTypeEnum.html); [Synchronizing Catalogs](https://help.sap.com/docs/SAP_COMMERCE/d0224eca81e249cb821f2cdf45a82ace/8c6a38118669101481bdf1303d70949e.html)
- SAP weakness: variant modeling is project-specific (multiple documented approaches) and the accelerator reference docs are marked **deprecated**; storefront rendering of non-Similar reference types needs developer work — [Modeling Product Variants](https://help.sap.com/docs/SAP_COMMERCE/917a3cf5902e4f7f9241ab456de71388/8c143a2d8669101485208999541c383b.html); [Cross-Selling and Up-Selling Products](https://learning.sap.com/learning-journeys/managing-products-in-the-backoffice-product-cockpit/cross-selling-and-up-selling-products)
- Pimcore strength: relations are class fields with **typed metadata per link**, reverse relations, and both sides editable; weakness: no retail semantics out of the box, and the Classification Store route **cannot hold relations at all**, forcing Object Bricks or custom code — [Relational Datatypes](https://docs.pimcore.com/platform/Pimcore/Objects/Object_Classes/Data_Types/Relation_Types); [Object Bricks vs Classification Store](https://docs.pimcore.com/platform/Pimcore/Objects/Object_Classes/Object_Bricks_vs_Classification_Store/)
- Shopify strength: reference-typed metafields/metaobjects give a real graph without a PIM, and 2,048 variants removed the historical modeling ceiling; weakness: nothing enforces inverse consistency or ordering, and the platform's own recommendations are opaque and availability-filtered — [Data modeling with metafields and metaobjects](https://shopify.dev/docs/apps/build/metaobjects/data-modeling-with-metafields-and-metaobjects); [Customizing product recommendations](https://help.shopify.com/en/manual/online-store/storefront-search/search-and-discovery-recommendations)
- Cross-cutting failure mode (consultancy, secondary source): PIM programmes fail on **governance and current-state data analysis**, not on tooling — "not developing data governance requirements and policies… defining business objects, constraints, attributes, taxonomy, product families, completeness, workflow processes" and "failing to adequately understand your product data" (one client's cost/time tripled) — [Bounteous: 10 Ways PIM Projects Fail](https://www.bounteous.com/insights/2021/08/24/ways-pim-projects-fail-and-how-to-ensure-success/) *(vendor consultancy blog, opinion)*
- Vendor blog on catalog schema (secondary): the recurring structural failures are attribute sets defined **per category instead of per product type**, flat category hierarchies, no variant model, and no governance layer; also "the database schema that works for 500 SKUs rarely works for 50,000" — [AtroPIM: product catalog database](https://www.atropim.com/en/blog/product-catalog-database) *(vendor blog)*
- Same source on master data: "Never flatten into one record. Category, Variant, Asset, Channel, Supplier, Price, and Unit of Measure are all distinct entities", and attribute scope (global / locale / channel) is "the highest-stakes design decision" — [AtroPIM: product master data model](https://www.atropim.com/en/blog/product-master-data-model) *(vendor blog)*

### Inferences
- Failure modes cluster into four buckets: **vocabulary** (fixed types that don't match the domain), **identity** (no merge/split/retire semantics), **inverse consistency** (1-way links with no backlink), and **silent import semantics** (replace-vs-append ambiguity).
- For a software catalog, the Adobe *product surface* fails on vocabulary (no renewal/upgrade/compatibility), the Shopify model fails on identity and inverse integrity, the Akeneo model fails on ordering and type mutability, and SAP's model is closest but historically expensive to operate. Adobe additionally fails on retirement safety (cascade deletes inbound edges), which matters most for exactly the renewal/upgrade chains this catalog depends on.
- A defensible design is: **Akeneo-style typed edge table** (type registry with direction + cardinality + quantity/metadata flags, immutable codes, per-type permission), **plus** SAP-style domain vocabulary seeded with the software relation types, **plus** Adobe-style "manual before rule, rule with dry-run + limit + priority", **plus** Pimcore-style per-link metadata and reverse-relation views, **plus** a supersession-style retire/merge protocol.

### Gaps
- No quantitative comparisons (cost, time-to-value, error rates) between approaches were found in primary sources; all comparative statements above are qualitative and derived from documented capability gaps.
- Contentsquare (named in the brief) publishes nothing on catalog relation modeling — no relevant source found, so it is excluded.

## What should we reuse for a ~136k-offer B2B/B2C software catalog?

### Takeaway
The evidence supports one relation table with a **type registry**, **directed edges**, **per-edge metadata**, **provenance + status + validity dates**, and **two materialization modes** (stored curated vs. rule-computed with promote-to-stored), fronted by a grid + product-form tab + picker + dry-run rule builder + audit tab.

### Cited Findings
- Relation "type" needs to be data, not code: Akeneo lets admins create types with direction and quantity flags and per-locale labels; SAP ships a fixed but broad enum; Adobe stores types as rows in `catalog_product_link_type` and per-link values as typed attribute rows — [Manage your association types](https://help.akeneo.com/v7-manage-your-association-types); [ProductReferenceTypeEnum](https://help.sap.com/doc/9fef7037b3304324b8891e84f19f2bf3/2205/en-US/de/hybris/platform/catalog/constants/GeneratedCatalogConstants.Enumerations.ProductReferenceTypeEnum.html); [Catalog db_schema.xml](https://raw.githubusercontent.com/magento/magento2/2.4-develop/app/code/Magento/Catalog/etc/db_schema.xml)
- Retiring an offer without a protocol is destructive, not merely lossy: Adobe's foreign keys use `ON DELETE CASCADE` on both `product_id` and `linked_product_id`, so a delete erases inbound edges with no error — which is precisely the evidence for owning merge/retire in application logic — [Catalog db_schema.xml](https://raw.githubusercontent.com/magento/magento2/2.4-develop/app/code/Magento/Catalog/etc/db_schema.xml)
- Per-edge payload is a real requirement in two systems: Akeneo quantified associations (quantity) and Table+Product-Link columns (measurement/text/date/boolean per row); Pimcore Advanced Many-To-Many metadata columns (text/number/selection/boolean) — [Associations of products](https://help.akeneo.com/serenity-take-the-power-over-your-products/serenity-associations-of-products); [Relational Datatypes](https://docs.pimcore.com/platform/Pimcore/Objects/Object_Classes/Data_Types/Relation_Types)
- Inverse visibility is a named feature in two systems: Akeneo backlinks (any locale/channel) and Pimcore Reverse Object Relation (editable, no own storage) — [Manage composable products](https://help.akeneo.com/serenity-build-your-catalog/manage-composable-products-in-the-pim); [Reverse Object Relation Datatype](https://docs.pimcore.com/platform/Pimcore/Objects/Object_Classes/Data_Types/Reverse_Object_Relation_Type)
- Curated-vs-computed promotion is a documented workflow (Akeneo: rule matches → select → send to a manual association type) — [Define Product Compatibility](https://help.akeneo.com/serenity-build-your-catalog/manage-product-compatibility)
- Precedence and caps are explicit in Adobe (manual before rules; result limit 20; priority 1 = top) — [Create a related product rule](https://experienceleague.adobe.com/en/docs/commerce-admin/marketing/promotions/product-relationships/product-related-rule-create)
- Successor/retirement semantics need effective date, quantity ratio, reason, source, status, cycle detection and terminal resolution — [Supersession guide](https://getclaro.ai/resources/guides/model-supersession-chains-in-a-catalog/) *(vendor guide)*
- Rule changes that don't emit events break downstream sync (Akeneo compatibility) — so computed relations must either be materialized before export or the export must resolve them on read — [Define Product Compatibility](https://help.akeneo.com/serenity-build-your-catalog/manage-product-compatibility)
- Bulk at scale must be asynchronous with a report (Akeneo bulk task + report page; Shopify 24h bulk job + JSONL) — [Bulk actions on products](https://help.akeneo.com/v7-boost-your-productivity/v7-bulk-actions-on-products); [Bulk import data](https://shopify.dev/docs/api/usage/bulk-operations/imports)
- Structural invariants should be enforced at write time (Akeneo refuses re-parenting when the family variant differs) — [Bulk actions on products](https://help.akeneo.com/v7-boost-your-productivity/v7-bulk-actions-on-products)

### Inferences (concrete blueprint)
- **Type registry**: `relation_type(code, label_i18n, direction[1way|2way], cardinality, allows_quantity, allows_metadata_schema, source_kind[manual|rule|import|system], is_symmetric, allowed_families[], permission_scope)`. Keep codes immutable; make direction/cardinality immutable after first use (Akeneo's mistake to avoid: it cannot be fixed later).
- **Seed vocabulary** for this domain: `accessory`, `upgrade` (successor, direction-aware), `renewal` (successor with validity/period metadata), `alternative` (substitute, often symmetric), `bundle_component` (quantity), `compatibility` (rule-computed, target may be non-sellable reference records), `adjacent_task` (cross-sell), `included_in`/`requires` (mandatory prerequisite).
- **Edge record**: `(source_offer_id, type, target_offer_id | target_ref_record, position, quantity, metadata_json, status[proposed|active|rejected|expired], source_kind, confidence, valid_from, valid_to, created_by, approved_by, evidence_url)`. This single shape covers Akeneo's quantity, Pimcore's metadata, and the supersession guide's provenance requirements.
- **Two materializations**: stored edges for curated/commercial links; rule definitions evaluated on read for compatibility. Provide an explicit "promote match → stored edge" action so merchandisers can curate the top-N (Akeneo's pattern), and make sure promotion records provenance (`source_kind=rule`, rule id, confidence).
- **Merge/split/retire protocol**: never hard-delete an offer with inbound edges. On merge, rewrite inbound edges to the survivor and write a `replaced_by` edge with effective date + reason; on split, create one `replaced_by` per branch with a quantity ratio; on retire, require either a successor edge or an explicit `no_successor` flag (both from the supersession checklist). Recompute any denormalized `current_successor_id` on every edge write.
- **Validation**: hard-block only structural invariants (self-link, duplicate edge, 2-way asymmetry, target not sellable where required, cycle in successor chains, depth > N); everything else as a weighted quality score with suggestions (Pimcore pattern) so 136k offers can be improved incrementally rather than blocked.
- **UX minimum**: grid with saved views + inline status/boolean edit; product-form "Relations" tab grouped by type with picker modal (search by SKU/name/family, basket, confirm); reverse "Referenced by" panel per type; bulk "add relation" from a filtered selection (append-only, never implicit replace); rule builder with affected-count dry-run and per-product preview; audit tab showing edge-level old/new with author and timestamp; CSV/API import with **explicit mode flag** (`append` vs `replace_type`) to avoid Akeneo's and Adobe's silent-replace/silent-noop failure modes.
- **Scale tactics**: cursor pagination for the relation export API; async bulk jobs with downloadable per-row error reports; cap interactive grids (10k, as Akeneo does) and route large operations to jobs; store `position` explicitly since no reviewed platform lets users order relations and that is a real merchandising need for "top 5 accessories".
- **Software-license specifics** (domain inference, not a cited finding): the reviewed vendor taxonomies assume physical goods, so the family/variant axes need remapping. A workable split for this catalog: *family* = vendor + product line (Microsoft 365, Kaspersky Endpoint Security, КриптоПро CSP, Adobe Creative Cloud, CorelDRAW Graphics Suite); *product model* = edition/tier (Business Standard vs Premium, CSP vs DSS); *variant* = term × seat band × region/language. That keeps edition-level marketing copy and cross-edition "upgrade" edges at model level (inherited, like Akeneo), while price/SKU-bearing combinations stay as variants.
- **License-specific edge semantics** (inference): `renewal` and `upgrade` both need a *from-edition → to-edition* mapping plus a quantity/seat ratio (1 seat → 5 seats, 1 year → 3 years), which is exactly the supersession `quantity_ratio` + `effective_date` shape; `compatibility` for software usually means platform/OS/version constraints, so it is better computed from attributes (Akeneo compatibility pattern) than curated per pair; `bundle` for software is frequently a *licence bundle* (e.g. suite = several products under one SKU) where component quantities are seats, not units.
- **Term-bound relations** (inference): a renewal link should carry `valid_from/valid_to` and the subscription term, otherwise a 2024 renewal SKU will keep pointing at a 2025 SKU after the vendor renames the line — the failure mode the supersession guide warns about when effective dates are missing.

### Gaps
- No public evidence on the practical cardinality limits of a relation table at 136k nodes × N edges per node; sizing must be derived from our own access patterns, not from vendor docs.
- No vendor-documented pattern for **time-boxed relations** (e.g. a renewal link valid only for a subscription term) beyond Adobe's scheduled updates and the supersession guide's `effective_date`; the `valid_from/valid_to` design above is an inference.
- Whether B2B customer-specific relation visibility (different accessory sets per segment) is supported natively anywhere was not found; Adobe's related-product rules support customer segments, which is the closest documented analogue — [Create a related product rule](https://experienceleague.adobe.com/en/docs/commerce-admin/marketing/promotions/product-relationships/product-related-rule-create)
