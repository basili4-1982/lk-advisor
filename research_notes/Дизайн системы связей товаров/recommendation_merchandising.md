# Recommendation & Merchandising Platforms: Algorithmic Item-to-Item Relations Combined with Human Curation

Scope: public vendor documentation, API references and help centers as of late 2026 (pages fetched 2026-11-26). Vendors covered: Amazon Personalize, Algolia Recommend, Recombee, Coveo, Bloomreach, Nosto, Constructor, Dynamic Yield, Rebuy. Context of use: B2B software licenses/subscriptions, sparse co-purchase, long tail, renewal/upgrade paths, human validation queue.

---

## 1. How platforms build item-to-item relations (co-purchase, co-view, content, embeddings)

### Takeaway
Every mature platform runs **two or more independent relation generators** — a behavioural one (co-view / co-purchase / co-occurrence in a session or basket) and a content/embedding one — and merges or fallbacks between them. Behavioural signals are almost always **normalised against item popularity** (demoting "hub" items that co-occur with everything), and the content model exists specifically to cover items that behaviour cannot reach.

### Cited Findings

**Vendor/algorithm matrix (documented relation sources)**

| Vendor | Behavioural relation | Content/embedding relation | Explicitly documented merge/fallback |
|---|---|---|---|
| Amazon Personalize (Similar-Items) | co-occurrence of the item in user histories | item metadata similarity (categorical + unstructured text) | single recipe blends both; returns popular items if item unknown | 
| Algolia Recommend | collaborative filtering on 30–90 days of click/conversion events | content-based filtering on titles/descriptions/attributes | merged set when both enabled |
| Recombee | interaction-based models per scenario/logic | item properties usable in filters/boosters | "logic" presets per domain |
| Coveo PR | historical interaction patterns aggregated across visitors/sessions | product embeddings/vectors (separate model family) | seeded strategies + "with/without fallback" variants |
| Bloomreach | behaviour pixels feed the model | BERT embeddings over product-feed features → top-200 candidates | primary + secondary (fallback) algorithm |
| Nosto | ML algorithms (bestseller, browsing-history, cross-sell) | attribute filters/weights | filters + merchandising rules layered on top |
| Constructor | item-item + user-user graph from search/browse/purchase | content embeddings used for "product inheritance" | backfilling with Bestsellers |
| Dynamic Yield | Viewed Together / Purchased Together (session, transaction) | Keyword Similarity, VisualML | algorithm + filters + pin rules |
| Rebuy | purchased/viewed/complementary-to-viewed data sources | similar-products endpoint | static list source available |

**Amazon Personalize — Similar-Items (`aws-similar-items`)**
- "Similar-Items calculates similarity based on interactions data and any item metadata you provide. It takes into account the co-occurrence of the item in user histories in your Interaction dataset, and any item metadata similarities." — [AWS docs, Similar-Items recipe](https://docs.aws.amazon.com/personalize/latest/dg/native-recipe-similar-items.html)
- Minimum data: "you must create an Item interactions dataset with at least 1000 unique historical and event interactions (combined)"; an Items dataset is recommended for accuracy but not required. — [same](https://docs.aws.amazon.com/personalize/latest/dg/native-recipe-similar-items.html)
- Popularity is a tunable, not a side effect: hyperparameter `popularity_discount_factor`, default `0.0`, range `[0.0, 1.0]`; "Specify a value closer to zero to include more popular items. Specify a value closer to one for less emphasis on popularity." — [same](https://docs.aws.amazon.com/personalize/latest/dg/native-recipe-similar-items.html)
- Cold-item definition is explicit: "You can get recommendations for items that are similar to a cold item (an item with fewer than five interactions)." If the item ID is unknown, "the recipe returns popular items as recommendations." — [same](https://docs.aws.amazon.com/personalize/latest/dg/native-recipe-similar-items.html)
- Personalize also ships a lower-level `SIMS` recipe for teams that want more hyperparameter control over the same item-similarity problem. — [same](https://docs.aws.amazon.com/personalize/latest/dg/native-recipe-similar-items.html)

**Algolia Recommend**
- "Collaborative filtering analyzes user events from the last 30 to 90 days. Recommend builds an interaction table between `userToken` and `objectID`. It then counts how often each user interacts with each record." Similar = same users interacted; Frequently bought together = same users bought. — [Algolia docs, Recommend overview](https://www.algolia.com/doc/guides/algolia-recommend/overview)
- Two FBT variants with different precision/coverage trade-off: **relaxed** (default) "uses collaborative filtering to infer relationships from past purchases… users often buy A with B, and B with C. Recommend can then suggest C for A. This can happen even if those two items weren't bought together. This increases catalog discovery but can introduce inferred pairings." **Strict** "recommends only items that appeared together in the conversion events you select for training." — [same](https://www.algolia.com/doc/guides/algolia-recommend/overview)
- Content-based filtering is positioned as the sparse-data remedy: it "can improve relevance compared to using only collaborative filtering. It lets you **show recommendations when you don't have enough click and conversion events.** With content-based filtering, you can increase catalog coverage." When both are used, "Recommend returns a merged set of recommendations from both models." — [same](https://www.algolia.com/doc/guides/algolia-recommend/overview)
- There is a per-request score cut-off: the Related query accepts a numeric `threshold` (float, e.g. `42.1`) alongside `indexName`, `objectID`, `model`. — [Algolia API, getRecommendations](https://www.algolia.com/doc/api-reference/api-methods/get-recommendations/)
- A fifth model, **Looking similar**, "recommends related items… based on the images in your index. It **doesn't require any events**" — a pure content relation with no behavioural floor at all. — [Algolia docs, Recommend overview](https://www.algolia.com/doc/guides/algolia-recommend/overview.md)
- Per-model minimum-data floors are published as a table: Frequently bought together **1,000** conversion events (with two or more items); Related items **10,000** click/conversion events; Related content **10** items with content-based attribute values; Trending items and Trending facets value **250** conversion events each. Maxima are 1.5M–3M; "Each model generates up to 30 recommendations." — [same](https://www.algolia.com/doc/guides/algolia-recommend/overview.md)
- Training cadence is fixed and not configurable: "After this initial training, models retrain **once every day**. You can't change how often a model retrains." — [same](https://www.algolia.com/doc/guides/algolia-recommend/overview.md)
- Event selection is a per-model curation lever: "By default, each model trains on all the events it receives… For example, users often add several similar items to their cart and buy only one of them. Training the Frequently bought together model only on purchase events keeps the model focused on items that users actually bought together." — [same](https://www.algolia.com/doc/guides/algolia-recommend/overview.md)

**Dynamic Yield — explicit popularity demotion in the co-occurrence score**
- Viewed Together: "scores items based on the number of occurrences they have been viewed together in the same session but **demotes items that are typically viewed with many other items, implying a weaker connection.** The scores are recalculated every 24 hours." — [Dynamic Yield KB, Recommendation Strategies](https://support.dynamicyield.com/hc/en-us/articles/360022554694-Recommendation-Strategies)
- Purchased Together: "scores items based on the number of times they have been purchased together in the same transaction while **demoting products that are typically purchased with many other items**. Consequently, it recommends products that are strongly linked to one another rather than products that have an arbitrary connection to a popular product. Recommendations are based on data from the past 6 months. The scores are recalculated every 24 hours." — [same](https://support.dynamicyield.com/hc/en-us/articles/360022554694-Recommendation-Strategies)
- Content relations: **Keyword Similarity** "uses categories and keywords from the data feed to score similarities between items, assigning higher scores to rare keywords shared between a pair of items and lower scores to more common terms… similarity scores are recalculated whenever the product feed is updated" (an IDF-style weighting, i.e. the same anti-popularity principle applied to text). **VisualML** is a deep-learning visual-similarity model for attributes "the marketers didn't tag into the metadata". — [same](https://support.dynamicyield.com/hc/en-us/articles/360022554694-Recommendation-Strategies)
- Offline purchase data can be blended: `Purchased Together Offline` and `Purchased Together Offline or Online` variants exist. — [same](https://support.dynamicyield.com/hc/en-us/articles/360022554694-Recommendation-Strategies)

**Constructor**
- "Constructor looks across all customer histories to identify common patterns, assembling a dense graph of connections based on **item-item and user-user relationships**." — [Constructor docs, Learn about Recommendations](https://docs.constructor.com/docs/products-recommendations-learn-about-recommendations.md)
- Strategy-level separation of relation types: **Alternative** = "collecting and analyzing co-occurrence data based on user behavior… products a user might consider as an alternative"; **Complementary** = "evaluates co-purchase behavior and other conversion signals… products a user would purchase in addition to a particular product"; **Bundles** = "items which are most frequently purchased in sets together… optimizes for products that are likely to be added to cart as a whole set with the primary product"; **Visually similar items** = visual attributes (color, style, pattern, shape). — [same](https://docs.constructor.com/docs/products-recommendations-learn-about-recommendations.md)
- Cold-start mechanism named "**product inheritance**": "For new or less popular products, Constructor marries behavioral signals with **content embeddings** by mapping new or less popular products to the most similar products with view and purchase information using titles, categories, descriptions, keywords and other product data." — [same](https://docs.constructor.com/docs/products-recommendations-learn-about-recommendations.md)

**Bloomreach**
- Similar Products pipeline is documented as a two-stage retrieve-then-rank: (1) "All the relevant product features are extracted from the product data"; (2) "We pass the collected product feature information through the pre-trained **BERT** model and compute **product similarity scores**. The algorithm then predicts the potential **top 200** similar product recommendations candidates." — [Bloomreach docs, Similar Products Widget](https://documentation.bloomreach.com/discovery/docs/similar-products-widget)
- Behaviour and content are both required inputs: "The Similar Product algorithm uses both user behavior and product information to build an intelligent model." — [same](https://documentation.bloomreach.com/discovery/docs/similar-products-widget)

**Coveo**
- "PR recommends catalog products, **learning product relationships from historical interaction patterns aggregated across visitors and sessions**." — [Coveo docs, About Product Recommendations](https://docs.coveo.com/en/3382/)
- Relation types are exposed as named strategies rather than one opaque model: "Viewed together", "Viewed together, same category", "Viewed together, different category", "Purchased together", "Purchased together without fallback", "Purchased together, same category", "Purchased together, different category". — [Coveo docs, Product recommendation strategies](https://docs.coveo.com/en/p85e0425/)
- Category-conditioned variants ("same category" / "different category") are first-class: i.e. the platform treats "alternative" and "complementary" as two directions of the same co-occurrence signal, conditioned on taxonomy. — [same](https://docs.coveo.com/en/p85e0425/)
- Coveo also sells separate embedding model families (Product embeddings and vectors; Catalog Semantic Encoder; Multi-Modal Catalog Encoder) as distinct ML models from the PR model. — [Coveo docs nav, Product Recommendations section](https://docs.coveo.com/en/3395/)

**Recombee**
- Item-to-item is a first-class endpoint: `Recommend Items to Item(itemId, targetUserId, count)` with optional `filter`, `booster`, `logic`, `minRelevance`, `rotationRate`, `rotationTime`. — [Recombee API, Recommendations](https://docs.recombee.com/api/recommendations)
- The `logic` parameter selects a domain-tuned model behaviour (e.g. `ecommerce:homepage`), distinct from `scenario` which selects the placement; "logic specifies mainly behavior, while scenario specifies the place where recommendations are shown to the users." — [Recombee docs, Recommendation Logics](https://docs.recombee.com/logics)
- "Composite Recommendations" return a *source* entity plus a related list — the documented pattern for "Because You Watched X" / "Because You Purchased X" — configured with templates or custom stage-by-stage endpoints, and "In the Admin UI, you can set distinct Filters and Boosters for each stage (Source and Result)." — [Recombee docs, Composite Recommendations](https://docs.recombee.com/scenarios/composite-recommendations)

**Nosto**
- Recommendation types are separate algorithms with per-type settings, e.g. Best Sellers "based on overall trend data and popularity" with "Scoring mode… 'most bought' or 'most viewed'", a time period, and toggles to "exclude products in cart" and "exclude currently viewed product"; Browsing History has "Option to show also related products to browsing history". — [Nosto Help, Recommendations Glossary](https://help.nosto.com/en/articles/586470-recommendations-glossary)

### Inferences
- The industry-standard architecture is: **behavioural candidate generator (co-occurrence, popularity-normalised) + content/embedding candidate generator + merge/fallback policy**, with the content side explicitly justified as coverage for items with insufficient events. This maps cleanly onto a B2B software catalog where co-purchase is sparse: the embedding model carries most of the recall and behaviour only re-ranks.
- "Demote items that co-occur with everything" is the single most transferable scoring idea for software catalogs, where platform/OS/runtime items (e.g. "Windows Server", "Azure", "SQL Server") would otherwise dominate every relation list. Dynamic Yield implements it inside the score; Personalize exposes it as `popularity_discount_factor`; Algolia exposes it as strict-vs-relaxed FBT.
- Coveo's split into "same category" vs "different category" strategies is the closest documented analogue to the distinction a software catalog needs between **upgrade/replacement relations** (same product family, different edition) and **complementary/add-on relations** (different family, same solution).
- Algolia's relaxed FBT (transitive A–B, B–C ⇒ A–C) is a documented way to increase coverage in sparse data, and the vendor itself warns it "can introduce inferred pairings" — i.e. it is a precision-for-coverage trade that should be a per-relation-type setting, not a global default.

### Gaps
- No vendor publishes the actual similarity formula, weighting between behavioural and content signals, or the minimum co-occurrence count used to emit an edge. All descriptions are qualitative.
- Rebuy's documentation is API/data-source oriented (Recommended, Top Sellers, Trending, Purchased, Collections, Viewed, Static, Similar Products, Complementary to Viewed — [Rebuy developer docs](https://developers.rebuyengine.com/reference/similar-products/)); I found no public page describing how its "similar products" score is computed.
- No public source describes how any of these platforms handles **negative** relations (explicit "do not recommend together") at the model level, as opposed to as a filter/blocklist.

## 2. Manual controls: pins, boosts, blacklists, exclusions, rules, merchandising zones, fallback lists, diversity constraints

### Takeaway
Manual control converges on a small, remarkably consistent vocabulary — **block/blacklist, include-only/allowlist, boost, bury, pin/slot, attribute-weighted boost, and diversity constraints** — applied at **layered scopes** (global → placement/widget/pod → query/item-conditioned). Three structural facts matter for design: (a) exclusion is universally stronger than ranking; (b) positional pinning is offered by most vendors (Algolia, Coveo, Nosto, Dynamic Yield) but not all — Bloomreach explicitly excludes Product Slotting from Recommendations; and (c) the platforms that document precedence (Algolia, Coveo) treat it as a first-class, deterministic algorithm rather than an implementation detail.

### Cited Findings

**Coveo Merchandising Hub — the cleanest scope model, and the only documented pin-conflict rule**
- Three rule families on a recommendation slot: "filter rules, ranking rules, and conditional rules"; merchandisers "fine-tune the content of recommendation slots using various ML strategies combined with filter rules, ranking rules, and conditional rules." — [Coveo docs, Recommendations manager](https://docs.coveo.com/en/o4nh0046/)
- Slots are the merchandising zone: the manager "offers merchandisers a comprehensive overview of all the recommendation slots that are associated with a specific storefront", with per-slot "key performance metrics". — [same](https://docs.coveo.com/en/o4nh0046/)
- Ranking rules are exactly three: "**Pin**: Products that meet the conditions will be pinned at a specific position within the recommendation slot. **Boost**: …ranking boosted. **Bury**: …ranking decreased." — [Coveo docs, Ranking rules for recommendations](https://beta.docs.coveo.com/coveo-platform/commerce/coveo-merchandising-hub-cmh/recommendations-manager/ranking-rules-for-recommendations/index.md)
- Scope is deliberately narrow: "Currently, recommendation ranking rules can only apply to **specific recommendation slots**", with per-rule **Locale** and **slot** scope, and "ranking rules can also be **scheduled for a specific time**". — [same](https://beta.docs.coveo.com/coveo-platform/commerce/coveo-merchandising-hub-cmh/recommendations-manager/ranking-rules-for-recommendations/index.md)
- **Pin conflict resolution is documented** (the only vendor found that specifies precedence): "Pin rules override the content that should otherwise appear at a specific position in a recommendation slot. This includes other pin rules that target the same position, so merchandisers must not create multiple pin rules that target the same position in the same slot. **If there's a conflict between pins, priority is given to the most recent pin rule.**" Worked example: a March 1 rule pinning "Safari Khakis" to position 2 and a March 10 rule pinning "Blue Jeans" to position 2 → "only the most recent rule applies". — [Coveo docs, Pin rules for slots](https://beta.docs.coveo.com/coveo-platform/commerce/coveo-merchandising-hub-cmh/recommendations-manager/ranking-rules-for-recommendations/pin-rules-for-slots.md)
- Boost rules are **attribute-based, not item-based**: "These criteria are based on product attributes that are available in the indexed metadata, such as brand, category, or price", selected via Attribute → Operator → Value (e.g. `ec_brand` = "Barca Sports"), with date operators for date attributes. Prerequisite: the metadata must be mapped to a field with "**Facet** or **Multi-value facet** option enabled". — [Coveo docs, Boost rules for slots](https://beta.docs.coveo.com/coveo-platform/commerce/coveo-merchandising-hub-cmh/recommendations-manager/ranking-rules-for-recommendations/boost-rules-for-slots.md)

**Constructor — rule types, and what is deliberately unsupported**
- "Recommendation rules support **boost, bury, slotting, ranged slotting, blocklist, allowlist, and variation slicing** rules. They do **not** support content rules, global rules, or faceted searchandising, and the preview does not show performance analytics in the header." — [Constructor docs, Searchandise a recommendation pod](https://docs.constructor.com/docs/using-the-constructor-dashboard-recommendations-searchandise-a-recommendation-pod.md)
- Rules are scoped by condition: "**By item:** the rule applies when the pod generates results for a specific item… **By attribute:** the rule applies when the pod generates results for…" — i.e. an edge-level override and a segment-level override. — [same](https://docs.constructor.com/docs/using-the-constructor-dashboard-recommendations-searchandise-a-recommendation-pod.md)
- One rule can target **multiple pods** at once ("Select the checkbox next to each pod that the rule should affect"), which is the documented mechanism for keeping "complementary" and "alternative" slots consistent. — [same](https://docs.constructor.com/docs/using-the-constructor-dashboard-recommendations-searchandise-a-recommendation-pod.md)

**Bloomreach — merchandising feature datasheet (the most explicit control inventory found)**
- **Block** — "Removes PIDs from a response set" (available for Recommendations). **Include/Exclude rules** — "Filters out or includes products from a response set based on attributes" (Recommendations: yes). **Hard boost (PID boost)** — "Includes PIDs from out-of-algo recall set into response" (Recommendations: "Yes (except for Personalized algo)"). **Soft boost/bury — description attribute-based** — "Boosts attribute match products to Top N (carousel size defined in configurator)". **Soft boost — numeric attribute** — "Boosts a set of products based on the condition set on the numeric attribute value". **Product Slotting** — "Pins particular products to certain positions in a grid" (**Recommendations: No**). — [Bloomreach docs, Merchandising Capabilities](https://documentation.bloomreach.com/discovery/docs/merchandising-capabilities)
- Scope layering is explicit: "Global-Recommendations rule scope only influences all the Recommendation type widgets like Frequently Viewed Together, Frequently bought Together, Similar Products"; plus a **Widget Global rule** ("rules that affect all responses tied to a particular widget ID") and a **Widget Query rule** ("affects responses tied to a widget ID and the query combination"). — [same](https://documentation.bloomreach.com/discovery/docs/merchandising-capabilities)
- Not all widget types support widget-level merchandising: "For Bestseller, Past Purchases and Experience-Driven Recommendation widget types, the widget level merchandising functionalities are not available yet. However, Global Ranking and Global Recommendations rules can be created to block the products." — [same](https://documentation.bloomreach.com/discovery/docs/merchandising-capabilities)

**Nosto**
- Merchandising rules act "as a weighting mechanism, based on both product attributes such as category, brand, size, and price—and performance metrics such as conversion rate, margin, and inventory turnover… the sequence of products in recommendations is reordered. This boosts the visibility of the items aligning with the merchandising rule, all the while **respecting the initial algorithm and any filters applied**." Scope: "a specific recommendation placement or across all placements", extendable "with just one click… to your search results and category pages". — [Nosto blog, Merchandising rules for Product Recommendations](https://www.nosto.com/blog/whats-new-in-nosto-merchandising-rules-for-product-recommendations/)
- Global rule builder supports: "Filter to include or exclude products and **pin specific items to designated positions**"; segment targeting; **scheduling** ("active during specific time periods or on recurring days and times every week… reducing the risk of human error"); and A/B testing of rules with "continuous optimization" to "automatically direct the most traffic toward the highest-performing variant". — [Nosto, Global Merchandising Rules](https://www.nosto.com/commerce-experience-platform/dynamic-targeting/global-merchandising-rules/)
- Filters vs dynamic filters: "**Basic Filters** are essentially inclusion and exclusion rules… **Advanced dynamic filters** support the creation of precisely paired recommendations based on product attributes… operate on the principle of 'if this, then that' conditions, requiring more manual input but providing a higher level of control." — [Nosto Help, Recommendation Filters](https://help.nosto.com/en/articles/586449-recommendation-filters)
- Exclusion scope hierarchy: "The scope of each filter is limited to the recommendations where the rules are applied. **Global exclusion rules allow the removal of products from all Nosto features.**" — [same](https://help.nosto.com/en/articles/586449-recommendation-filters)
- Rules compose additively by default: specific-query rules' "boosts are merged with the already existing global rules. If you don't want the rules to be merged, use the exclusion mechanism directly in the create/edit menu." Ranking is a separate score from relevance: "Every found product has its score that consists of relevance score and ranking score. In Merchandising, you can manipulate ranking scores." — [Nosto Help, Merchandising & Search Personalization Guide](https://help.nosto.com/en/articles/7168969-merchandising-search-personalization-guide)

**Recombee — filters, boosters, and the only well-documented diversity constraints**
- Filters: "Filters determine **which items can be recommended** in this scenario… An item can be recommended only if all filter rules assigned to the scenario are satisfied." API-level filter is combined with Admin-UI filters "using the `AND` operator". — [Recombee docs, Scenario Settings in the Admin UI](https://docs.recombee.com/scenarios/settings-in-admin-ui)
- Boosters: "Each booster rule produces a numeric score for each item. **The final boosting score is the product of the scores from all applied booster rules.**" API booster is combined with Admin-UI boosters "using the `*` operator". — [same](https://docs.recombee.com/scenarios/settings-in-admin-ui)
- **Constraints** (diversity): "Constraints define **how frequently items sharing certain conditions can appear** in recommendation results. Examples: At most 2 items per category; No more than 50% of items from a single genre; Only one product per parent product ID." Implemented via an Item Segmentation, with **Limit Type** Absolute ("max 3 per brand") or Percentage ("max 25% from one brand") and an optional **Window Size** ("with a max of 2 items per segment and a window size of 4, each consecutive group of 4 recommendations will contain at most 2 from the same segment"). — [same](https://docs.recombee.com/scenarios/settings-in-admin-ui)
- Global Settings apply a filter "to all scenarios — for example, to always exclude unavailable items". — [same](https://docs.recombee.com/scenarios/settings-in-admin-ui)

**Dynamic Yield**
- Custom filter rules are exactly three: "**Only include:** Recommend only products with a specific property… **Exclude:** Never recommend products with a specific property… **Pin:** Recommend only a specific product, regardless of any algorithm." — [Dynamic Yield KB, Recommendation Strategies](https://support.dynamicyield.com/hc/en-us/articles/360022554694-Recommendation-Strategies)
- Pin is absolute and overrides safety checks: "What happens if I pin an item that is out of stock? Or, if I pin 2 slots with SKUs from the same groupID? **We display the items even though they are out of stock, or have SKUs from the same groupID.**" Conversely "What if I create a filter that only includes items that are out of stock? **No items will be displayed.**" — [same](https://support.dynamicyield.com/hc/en-us/articles/360022554694-Recommendation-Strategies)
- Structural filters use taxonomy relations: "**With the same property**", "**With different properties**", "**With the same category**", "**With the same parent category**" (parent-category matching lets "men|tops|shirts" match "men|tops|jackets"). — [same](https://support.dynamicyield.com/hc/en-us/articles/360022554694-Recommendation-Strategies)
- Popularity-only **Shuffle Results**: "Retrieve more products than requested and then randomly select a subset from the top 100 most popular items. Selection is weighted by product score" — available for the popularity algorithm only. — [same](https://support.dynamicyield.com/hc/en-us/articles/360022554694-Recommendation-Strategies)

**Amazon Personalize — promotions as a quota-based override**
- "A *promotion* defines additional business rules that apply to a configurable subset of recommended items… you specify: The percentage of recommended items to apply the promotion filter to. A filter that specifies the promotion criteria." — [AWS docs, Promoting items](https://docs.aws.amazon.com/personalize/latest/dg/promoting-items.html)
- Ordering semantics: "promoted items are positioned randomly relative to other recommended items, but in sorted order relative to other promoted items." — [same](https://docs.aws.amazon.com/personalize/latest/dg/promoting-items.html)
- Graceful under-supply: "If there aren't enough items that meet the promotion criteria, the result will contain as many promoted items as possible." — [same](https://docs.aws.amazon.com/personalize/latest/dg/promoting-items.html)
- Filter scoping is split: "A promotion filter applies to only promoted items, while a request filter applies to only the remaining recommended items." — [same](https://docs.aws.amazon.com/personalize/latest/dg/promoting-items.html)
- Promotion is request-time, not model-time, and is supported for all use cases plus Similar-Items/SIMS/Trending-Now/Popularity-Count. — [same](https://docs.aws.amazon.com/personalize/latest/dg/promoting-items.html)
- Filter expressions support item attributes and, for related-item recipes, the **source item's** attributes via `CurrentItem.attribute`. — [AWS docs, Filter expressions](https://docs.aws.amazon.com/personalize/latest/dg/filter-expressions.html)

**Algolia — rules as an if-then curation layer, with per-source-item conditions and published precedence**
- Rules "are if-then statements that let you refine and curate your recommendations without editing code. When a **condition** (if) is met, the rule's **consequences** (then) are applied." Number of rules per scenario depends on the plan. — [Algolia docs, Refine recommendations with rules](https://www.algolia.com/doc/guides/algolia-recommend/how-to/rules.md)
- **Conditions are edge-scoped.** For FBT / Related items / Looking similar: "**Any item is a source item.**… **Specific item is viewed.** The consequences of this rule apply only when recommendations for a specific item are retrieved. **Subset of source items.** The consequences of this rule apply to items that match a filter." — [same](https://www.algolia.com/doc/guides/algolia-recommend/how-to/rules.md)
- **Five consequences**, mapping one-to-one onto the control vocabulary: "**Pin items**. Put one or more selected items at a specific position… (`1` is first). **Hide items**. Exclude one or more selected items. **Boost items**… show matching items before non-matching items. **Bury items**… after non-matching items. **Filter items**… only include matching items." — [same](https://www.algolia.com/doc/guides/algolia-recommend/how-to/rules.md)
- A relation-aware filter primitive exists: "To only show items with the same attribute value as the viewed item, set the value to `sameAsViewedItem`. This option isn't available for Trending items." — [same](https://www.algolia.com/doc/guides/algolia-recommend/how-to/rules.md)
- **Pin-vs-filter interaction is an explicit opt-in**, unlike Dynamic Yield's unconditional pin: "By default, pinned items appear in the recommendations, even if they don't match the filters applied to the request… To pin an item *only* when it matches the active filters, select the **Pinned items must match active filters to be displayed** checkbox… If it doesn't match, it's dropped from the recommendations instead of being promoted." — [same](https://www.algolia.com/doc/guides/algolia-recommend/how-to/rules.md)
- **Precedence is a published four-step algorithm**: "1. Rules for which you've specified a context. 2. Rules with **Filter items**, **Boost items**, or **Bury items** consequences. 3. Rules with a specified validity time frame. 4. If there are still tied rules, the one with the lowest object ID (alphabetically ordered) wins." — [same](https://www.algolia.com/doc/guides/algolia-recommend/how-to/rules.md)
- **Applied rules are inspectable at request time**: passing `getRankingInfo: true` in `queryParameters` returns an `appliedRules` array of rule object IDs — "useful for debugging and understanding why certain recommendations appear." — [same](https://www.algolia.com/doc/guides/algolia-recommend/how-to/rules.md)
- Rules support an optional validity timeframe ("select a timeframe, when the rule should be active") and contexts. — [same](https://www.algolia.com/doc/guides/algolia-recommend/how-to/rules.md)
- Separately, `optionalFilters` at query time "**don't exclude records**. Instead, they influence the record's ranking. Use them to promote or demote results without filtering them out." Syntax mirrors `facetFilters`; a leading `-` demotes (`"category:-Books"`). Requires the attribute to be in `attributesForFaceting`. — [Algolia API, optionalFilters](https://www.algolia.com/doc/api-reference/api-parameters/optionalFilters/)

**Bloomreach — turning rules off for experiments**
- Rule classes are individually switchable at the API level for A/B tests: `merchandising_rules.disable=all`, `=recall`, `=product_block`, `=product_add_to_recall`, `=attribute_include`, etc.; recall rules = "Product Block, Product Add to recall, Include Only, Exclude"; ranking rules = "Product Boost, Product Bury, Product Slot, Attribute Boost, Attribute Bury". — [Bloomreach docs, API controls to disable Merchandising rules](https://documentation.bloomreach.com/discovery/reference/api-controls-to-disable-merchandising-rules)

### Inferences
- The control vocabulary to implement is small and stable: `block`, `allowlist-only`, `boost(weight)`, `bury(weight)`, `pin(position)`, `attribute-weight`, `constraint(max per segment)`, plus `schedule` and `scope`. Everything else vendors offer is a UI convenience over these.
- **Pin precedence must be explicit and pins must never override validity.** Dynamic Yield demonstrates the failure mode: pinned items bypass stock and dedupe checks, so a pin can surface a dead product. For a software catalog, a pin that survives "end-of-sale"/"retired" flags would produce dead links. Model the pin as a *position* preference with a validity predicate (see the Algolia pattern below), and give pin-vs-pin conflicts a deterministic rule (Coveo: most recent wins).
- Recombee's **constraints** (absolute/percentage + window size) is the only vendor-documented diversity mechanism I found, and it is directly reusable: "max 1 relation per product family", "max 30% of a relation list from one vendor", computed over a sliding window of the rendered list.
- Nosto's separation of **relevance score vs ranking score** is the cleanest mental model for manual overrides: manual rules never re-order the candidate set, they only perturb a second score. That protects the algorithmic ranking as a baseline for measurement.
- Bloomreach's `merchandising_rules.disable` API is a strong argument for making **every manual rule individually addressable and disableable by ID** — otherwise the human layer contaminates every A/B test of the algorithmic layer.
- The "hard boost = inject a PID from outside the recall set" concept (Bloomreach) is distinct from "boost = reweight an item already in the candidate set". A human validation queue that can *add* a relation needs the former; a queue that only re-orders needs the latter.
- **Algolia's `appliedRules` array is the single most transferable idea for a human validation queue.** Returning the IDs of every rule that fired on a served list turns "why is this relation here?" from an interview question into an API call. A relation system should return, per served edge, the identifiers of the candidates/rules/manual overrides that produced it — which is also the only practical way to audit whether a human override is still doing anything.
- **Pin semantics should follow Algolia, not Dynamic Yield.** Dynamic Yield's pin ignores filters (out-of-stock items still show); Algolia makes filter-compliance an opt-in checkbox ("Pinned items must match active filters to be displayed") and *drops* rather than promotes a non-matching pin. For a software catalog where "retired / end-of-sale / not sold in region" are hard constraints, the Algolia default is the correct one: a pin is a *position* preference, never a *validity* override.
- Algolia's published four-step precedence (context → filter/boost/bury → validity timeframe → lowest object ID) is worth copying almost verbatim because step 4 gives a **deterministic, total order**. Determinism matters more than the specific ordering rule: without it, two rules that both apply produce non-reproducible renders and un-debuggable A/B results.

### Gaps
- **Cross-class precedence between pin, boost and diversity constraint remains undocumented.** Coveo specifies pin-vs-pin ("priority is given to the most recent pin rule") and Algolia publishes a four-step tie-break among rule *conditions*, but neither covers what happens when a **pin, a boost, and a diversity constraint** all apply (e.g. a pinned item violates a "max 1 per family" constraint). Whether the pin wins, the constraint wins, or the render errors is unstated. — [Coveo, Pin rules for slots](https://beta.docs.coveo.com/coveo-platform/commerce/coveo-merchandising-hub-cmh/recommendations-manager/ranking-rules-for-recommendations/pin-rules-for-slots.md); [Algolia, Refine recommendations with rules](https://www.algolia.com/doc/guides/algolia-recommend/how-to/rules.md)
- **Per-edge control exists but only as "rules conditioned on a source item", not as stored edges.** Algolia's "Specific item is viewed" condition and Constructor's "By item" condition both let a merchandiser say "when the source is A, do X to the list", which is functionally an edge-level override — but the override is a *rule evaluated at serve time*, not a persisted relation with its own identity, evidence, owner or expiry. No vendor lets you store and manage the edge itself ("A → B, type=complementary, confidence=0.7, approved by X on date"). This is the clearest structural difference between recsys merchandising and a relation catalogue.
- Coveo's boost rules are documented as **attribute-only** (Attribute → Operator → Value over faceted metadata), so it is unclear whether an arbitrary hand-picked item list can be boosted without also being pinned. Algolia, by contrast, separates "Pin items" (explicit item list) from "Boost items" (filter criteria). — [Coveo, Boost rules for slots](https://beta.docs.coveo.com/coveo-platform/commerce/coveo-merchandising-hub-cmh/recommendations-manager/ranking-rules-for-recommendations/boost-rules-for-slots.md); [Algolia, Refine recommendations with rules](https://www.algolia.com/doc/guides/algolia-recommend/how-to/rules.md)

## 3. Candidate generation → review → promotion to production

### Takeaway
Vendors separate two lifecycles that a relation system must also separate: the **model lifecycle** (train → build → shadow/A-B on a traffic slice → promote to 100%) and the **rule lifecycle** (draft → preview against a concrete item/profile → save → measure incremental gain). Human review is implemented as *preview-before-save* plus *post-hoc gain attribution*, not as a per-item approval queue.

### Cited Findings

**Model lifecycle: build is asynchronous, promotion is gated by A/B**
- Coveo: "A model can take anywhere from several minutes to several hours to build, depending on the size of the model dataset and the number of model build requests in the queue (system load)." Statuses are `Active`, `Build in progress`, `Inactive`; "The model can only return recommendations when its status is Active." — [Coveo docs, Create and manage a PR model](https://docs.coveo.com/en/3395/)
- Coveo promotion path: "Once you've created a Coveo ML CR model, the leading practice is to test the model performance by doing an A/B test. This allows you to test the model on a chosen proportion of the traffic passing through a given query pipeline… Once satisfied with the model efficiency, you can **stop the A/B test to make the model effective for all the traffic**." — [Coveo docs, Associate a CR model with a query pipeline](https://docs.coveo.com/en/l25f0432/)
- Model association is per query pipeline and per strategy, so a relation type can be rolled out independently: "In the Strategy selection section, you can view all the trained recommendation strategies and their associated query pipelines." — [Coveo docs, Create and manage a PR model](https://docs.coveo.com/en/3395/)
- Changing training data silently invalidates the model: "Updating the training dataset, building parameters, or strategy selection initiates an automatic model rebuild when you save the model." — [same](https://docs.coveo.com/en/3395/)

**Rule lifecycle: preview against a real entity, then save**
- Constructor: the recommendation-rule editor "preview[s] the results of one pod at a time… **Item-based strategies** (for example, *Alternative*, *Complementary*, or *Bundles*) generate results from an item that the shopper is viewing. Select an item in the **Search an item to preview** field. If the item has variations, you can select a variation. **User-based strategies**… Select a shopper profile." Plus "To preview the pod for a user segment, select **Impersonate**". — [Constructor docs, Searchandise a recommendation pod](https://docs.constructor.com/docs/using-the-constructor-dashboard-recommendations-searchandise-a-recommendation-pod.md)
- Bloomreach: "To preview the changes, you must enter the **Product ID (PID)**. The Preview shows products per the rule you have set." — [Bloomreach docs, Merchandising Capabilities](https://documentation.bloomreach.com/discovery/docs/merchandising-capabilities)
- Recombee: scenarios are configured in the Admin UI and "You can also see the performance of each scenario in the Admin UI separately, so you can check how well each application performs." — [Recombee API, Recommendations](https://docs.recombee.com/api/recommendations)

**Post-hoc attribution of manual rules (the "was this rule good?" loop)**
- Constructor computes **item-level gain** and **page-level gain** for slot/boost/bury rules: "comparing an item's performance before and after a rule change. An item's purchases, clicks, or add-to-carts are divided by the page traffic during each period, and the difference between the two values (before and after) is applied to the page's daily traffic… The daily estimates are summed over the last seven days." — [Constructor docs, Rule Performance Overview](https://docs.constructor.com/docs/analytics-rule-performance-overview.md)
- Crucially, it detects cannibalisation: "A **negative gain** means it performed worse, even if the merchandised items themselves improved. This can happen when promoted items **divert engagement from other items without improving the page's overall performance**." — [same](https://docs.constructor.com/docs/analytics-rule-performance-overview.md)
- Scope limits are stated: rule types included are "slot, boost, and bury rules"; "Global rules and other rule types (e.g., content, variation slicing, allowlist, etc.) are not included." — [same](https://docs.constructor.com/docs/analytics-rule-performance-overview.md)

**Feedback capture for training**
- Recombee returns a `recommId` per response "It can be used to: Let Recombee know that this recommendation was successful (e.g., user clicked one of the recommended items). See Reported metrics." — [Recombee API, Recommendations](https://docs.recombee.com/api/recommendations)
- Algolia: "Configure your app to send click and conversion events before you start a test. These events let you compare clicks and conversions for each variant." — [Algolia docs, What is A/B testing](https://www.algolia.com/doc/guides/ab-testing/what-is-ab-testing/)

### Inferences
- The pattern to copy is: **relation candidates are generated offline and versioned; the merchandiser reviews a *rendered slot for a specific source item*, not a raw edge list; saving publishes a new version; the old version stays measurable.** This matches the preview-against-a-PID/an-item pattern in Bloomreach and Constructor.
- A human validation queue for relations is genuinely different from what these vendors ship. Their "review" is a *preview of the effect* plus a rule that fires at serve time (Algolia's "Specific item is viewed", Constructor's "By item"), not an *approval of a proposed edge*. For a catalog with sparse co-purchase, a queue of proposed edges (with evidence and confidence) has no direct vendor precedent — it is closer to the knowledge-graph curation tools than to recsys merchandising UIs.
- Constructor's item-level vs page-level gain is the right two-level metric for a validation queue: approve an edge if it lifts the item, but roll it back if it cannibalises the slot.
- Because every vendor's preview is *stateful* (needs a source item, a profile, or a PID), a relation-adding system must decide early what the "preview key" is — source item, or source item + segment.
- The vendor workflow has **no notion of a relation "state"**. A rule is either saved or not; there is no draft/pending/approved/rejected lifecycle, no owner, no expiry, no evidence record. That entire state machine is the novel part of the system being designed, and it has to be built rather than adapted.

### Gaps
- No vendor publicly documents a **multi-step approval workflow** (draft → reviewer → approver → publish) for recommendation relations. The MACH Alliance listing for Coveo's Merchandising Agent asserts "Approved changes create, update, or replicate rules across search, listings, and recommendations for the brands, regions, and storefronts named" ([MACH Alliance listing](https://machalliance.org/agent-ecosystem/solutions/coveo-merchandising-agent)), but the page body did not render on fetch and no primary Coveo documentation was reachable to confirm the approval semantics — treat as unverified.
- No vendor documents a cap on how many manual rules a slot can carry before the algorithmic signal is considered drowned, nor any "manual override ratio" guardrail.
- I found no public description of how these platforms handle **concurrent editing** of the same rule/slot (locking, conflict resolution, audit of who changed what).

## 4. Cold start, sparse items, popular-item bias, catalog updates

### Takeaway
Four distinct mechanisms are used, and they are not interchangeable: (1) **content/embedding similarity** as the relation source for items without behaviour; (2) **inheritance/relaxation** — map an unknown item onto the nearest known item or relax a taxonomy constraint; (3) **popularity fallback** when nothing is known at all; (4) **scheduled retraining plus a separate "new item" fast path** so that new items do not wait for the next full rebuild. Popularity bias is treated as a tunable hyperparameter and as a metric, not as a bug to eliminate.

### Cited Findings

**Content as the cold-start relation source**
- Algolia: content-based filtering "lets you show recommendations when you don't have enough click and conversion events… you can increase catalog coverage. Users then get recommendations for items with little interaction data." — [Algolia docs, Recommend overview](https://www.algolia.com/doc/guides/algolia-recommend/overview)
- Constructor: "For new or less popular products, Constructor marries behavioral signals with content embeddings by mapping new or less popular products to the most similar products with view and purchase information using titles, categories, descriptions, keywords and other product data." — [Constructor docs, Learn about Recommendations](https://docs.constructor.com/docs/products-recommendations-learn-about-recommendations.md)

**Relaxation when the strict match fails**
- Bloomreach: "**Widget behavior when similar products matches cannot be found** — We relax the product type to match others when we do not find similar items." — [Bloomreach docs, Similar Products Widget](https://documentation.bloomreach.com/discovery/docs/similar-products-widget)

**Popularity fallback, explicitly bounded**
- Personalize: cold item = "an item with fewer than five interactions"; "If Amazon Personalize can't find the item ID that you specify in your recommendation request or batch input file, the recipe returns popular items as recommendations." — [AWS docs, Similar-Items recipe](https://docs.aws.amazon.com/personalize/latest/dg/native-recipe-similar-items.html)
- Constructor: "**Backfilling** — If there are not enough items that meet the criteria for a particular recommendation pod, Constructor will automatically plug in another strategy to fill the remaining spots. **By default, Constructor will use the Bestsellers strategy in this scenario.** This logic can be turned off by request." — [Constructor docs, Learn about Recommendations](https://docs.constructor.com/docs/products-recommendations-learn-about-recommendations.md)
- Bloomreach: the Similar Products widget takes a **Primary Algorithm** and a **Secondary Algorithm** ("Choose the fallback algorithm… from the following options: Best Seller, Trending Products, Recently Viewed"). — [Bloomreach docs, Similar Products Widget](https://documentation.bloomreach.com/discovery/docs/similar-products-widget)
- Coveo: "To avoid empty recommendation slots when there isn't enough data for a strategy, **use a strategy with a fallback when appropriate**", and it ships explicit pairs — `Purchased together` vs `Purchased together without fallback`, `Recently viewed` vs `Recently viewed without fallback`. — [Coveo docs, Product recommendation strategies](https://docs.coveo.com/en/p85e0425/)
- Recombee: `cascadeCreate` — "If an item of the given itemId or user of the given targetUserId doesn't exist in the database, it creates the missing entity/entities and returns some (non-personalized) recommendations." — [Recombee API, Recommendations](https://docs.recombee.com/api/recommendations)

**Minimum-data thresholds (the practical floor for behaviour)**
- Personalize Similar-Items: "at least 1000 unique historical and event interactions (combined)". — [AWS docs](https://docs.aws.amazon.com/personalize/latest/dg/native-recipe-similar-items.html)
- Coveo PR: "To serve relevant recommendations, a PR model needs **at least 10,000 view and/or purchase events** to learn from." — [Coveo docs, Create and manage a PR model](https://docs.coveo.com/en/3395/)
- Coveo ART (search, for comparison): "At least 100 search and click events"; "If fewer than 100 search and click events have been logged, ART models don't boost the ranking weight of any items. However, you can enable **Test configuration mode** to reduce the amount of analytics data required"; also "at least 55 visits per day". — [Coveo docs, Create and manage an ART model](https://docs.coveo.com/en/3397/)
- Algolia CF window is bounded: "user events from the last 30 to 90 days". — [Algolia docs](https://www.algolia.com/doc/guides/algolia-recommend/overview)
- Algolia publishes a **per-model** floor, and the spread is large: Frequently bought together **1,000** conversion events (with two or more items); Related items **10,000** click/conversion events; **Related content only 10 items with content-based attribute values**; Trending items / Trending facets value **250** each. — [Algolia docs, Recommend overview](https://www.algolia.com/doc/guides/algolia-recommend/overview.md)
- Algolia's **Looking similar** model "doesn't require any events" at all — it derives relations purely from images in the index. — [same](https://www.algolia.com/doc/guides/algolia-recommend/overview.md)
- Dynamic Yield recalculates: Viewed Together / Purchased Together "every 24 hours"; Purchased Together uses "data from the past 6 months"; Keyword Similarity "recalculated whenever the product feed is updated". — [Dynamic Yield KB](https://support.dynamicyield.com/hc/en-us/articles/360022554694-Recommendation-Strategies)

**Catalog updates / retraining**
- Personalize domain recommenders: "automatically retrains the models backing your recommenders **every 7 days**… For *Top picks for you* and *Recommended for you* use cases, Amazon Personalize updates your recommender to consider new items… **Automatic updates are not a full retraining**… they allow Amazon Personalize to feature your new items in recommendations before the recommender's next full retraining." *Trending now* "automatically evaluates your interactions data **every two hours**". While retraining, "you can still get recommendations… the recommender uses the previous configuration and models." — [AWS docs, Maintaining recommendation relevance](https://docs.aws.amazon.com/personalize/latest/dg/maintaining-relevance.html)
- Personalize custom recipes: "By default, all new solutions use automatic training to create a new solution version every 7 days… Without automatic training, you must manually create new solution versions for the solution to learn from your most recent data." — [same](https://docs.aws.amazon.com/personalize/latest/dg/maintaining-relevance.html)
- Coveo exposes the training window explicitly: `exportPeriod` "defining the age of the Coveo Analytics data used to build the model"; `exportOffset` (e.g. `P1D` "to ignore events that occur on the current day"); `intervalTime` 1–30 with `intervalUnit` DAY/WEEK/MONTH. — [Coveo docs, Create and manage a PR model](https://docs.coveo.com/en/3395/)

**Popularity bias as a measured, tunable property**
- Personalize: `popularity_discount_factor` (see §1). — [AWS docs](https://docs.aws.amazon.com/personalize/latest/dg/native-recipe-similar-items.html)
- Dynamic Yield: co-occurrence scores explicitly demote items that co-occur with many others (see §1). — [Dynamic Yield KB](https://support.dynamicyield.com/hc/en-us/articles/360022554694-Recommendation-Strategies)
- Offline evaluation literature proposes tracking "an average recommendation popularity metric to detect" popularity concentration alongside IPW-NDCG. — [Dzhoha et al., CEUR Vol-3924](https://ceur-ws.org/Vol-3924/short4.pdf); [arXiv 2412.08780](https://arxiv.org/html/2412.08780v1)

### Inferences
- For a B2B software catalog, the *documented minimums* are the decisive constraint — but they differ by orders of magnitude **by relation type**, not by vendor. Behavioural models need 1,000 events (Personalize Similar-Items, Algolia FBT), 10,000 events (Coveo PR, Algolia Related items); the content model needs **10 items with attribute values** (Algolia Related content) or **zero events** (Algolia Looking similar). A software catalog with hundreds of SKUs and tens of renewals per month cannot clear the behavioural floors, so the content/embedding + human-curation path must be primary and the behavioural path an enrichment signal. The practical rule: *pick the relation type whose data floor you can actually clear*, rather than picking the vendor and hoping.
- The "relax the constraint" pattern (Bloomreach: relax product type; Dynamic Yield: same-parent-category) is the right default for software: exact-edition matching will produce empty relation lists, so a ladder (same SKU → same edition family → same product family → same category → same solution area) is needed, with the relaxation level stored on the relation as provenance.
- "Popular items as fallback" is actively harmful for a long-tail software catalog (it would surface the same five flagship SKUs everywhere). Constructor's *configurable* backfill and Coveo's *explicit* "with/without fallback" strategy pairs show that fallback must be a per-slot, per-relation-type choice — and for software, curated fallback lists (e.g. "recommended alternatives for this family") are a better backfill than bestsellers.
- The two-speed update pattern (full retrain weekly + a fast path for new items + a 2-hour trending job) is a good template: relation *edges* can refresh on a different cadence from *scores*, and a newly added SKU should be able to get content-derived relations within minutes without waiting for a retrain. Algolia's fixed daily retrain (not configurable) is the counter-example: a hard cadence with no new-item fast path means a product launched today has no behavioural relations until tomorrow.

### Gaps
- No vendor documents how a *relation* (as opposed to a recommendation) is invalidated when a SKU is retired, superseded, or end-of-sale. All documented invalidation is at the item/filter level ("exclude unavailable items").
- No public data on how much of the long tail any of these systems actually covers in practice; coverage is asserted as a benefit of content-based filtering but never quantified.
- Coveo's product-group mechanism ("Products without a group ID will be excluded from the training dataset") is the only documented case of an entire class of items being silently dropped from training — a warning worth heeding when modelling edition families. — [Coveo docs, Create and manage a PR model](https://docs.coveo.com/en/3395/)

## 5. Metrics, experiments, feedback loops and position bias

### Takeaway
Live experimentation is universal and simple (A/B on a traffic slice, click/conversion as the outcome). Offline evaluation is where the sophistication sits: **inverse-propensity-weighted NDCG** to correct position bias, plus an explicit **popularity metric** to detect feedback-loop amplification. The industry consensus is that position bias must be corrected in *training/evaluation*, not merely observed, and that a closed loop will amplify whatever it is trained on unless something deliberately randomises or re-explores.

### Cited Findings

**What vendors measure**
- Constructor rule performance: metrics are **purchases, clicks, add-to-carts**, computed as item-level gain and page-level gain, with traffic normalisation and a 7-day summation window (see §3). — [Constructor docs, Rule Performance Overview](https://docs.constructor.com/docs/analytics-rule-performance-overview.md)
- Coveo: recommendation slots carry "in-depth performance metrics… tracking and analysis of recommendation slot performance"; merchandisers "monitor key performance metrics for each recommendation slot". — [Coveo docs, Recommendations manager](https://docs.coveo.com/en/o4nh0046/)
- Recombee: per-scenario performance "in the KPI section and the Insights"; `recommId` enables "Reported metrics" (clicks attributed back to the served recommendation). — [Recombee docs, Scenarios](https://docs.recombee.com/scenarios); [Recombee API](https://docs.recombee.com/api/recommendations)
- Dynamic Yield distinguishes two attribution models and warns they disagree: Recommendations reports "attribute revenue to a strategy only after the user clicks a recommended item" (direct/assisted revenue) whereas Experience reports use the configured attribution settings — so "strategy data in the Recommendations report" can legitimately "look different from variation data in Experience reports". — [Dynamic Yield KB](https://support.dynamicyield.com/hc/en-us/articles/360022554694-Recommendation-Strategies)

**How experiments are run**
- Algolia: control vs variants on live traffic; requires click and conversion events; frequentist (wait until planned end) or Bayesian; index-level tests need replicas which "increases your record count", parameter-level tests need no setup. — [Algolia docs, What is A/B testing](https://www.algolia.com/doc/guides/ab-testing/what-is-ab-testing/)
- Coveo: A/B the model on "a chosen proportion of the traffic passing through a given query pipeline", then promote to all traffic. — [Coveo docs, Associate a CR model](https://docs.coveo.com/en/l25f0432/)
- Nosto: A/B test merchandising rules "against one or more variations and choose 'continuous optimization' to automatically direct the most traffic toward the highest-performing variant." — [Nosto, Global Merchandising Rules](https://www.nosto.com/commerce-experience-platform/dynamic-targeting/global-merchandising-rules/)
- Bloomreach: rules must be disableable by API parameter during an A/B test, "in some cases, merchandising rules enabled in the background may influence the test results." — [Bloomreach docs, API controls to disable Merchandising rules](https://documentation.bloomreach.com/discovery/reference/api-controls-to-disable-merchandising-rules)

**Position bias: measurement and correction**
- Magnitude: "On Google Search, users click on the first position 10x more than the tenth position"; "Training our models on biased historical data perpetuates the bias via a self-reinforcing feedback loop. This can lead to suboptimal outcomes where items that are more relevant but are shown in lower positions continue to get lower engagement and thus don't improve their rank." — [Eugene Yan, How to Measure and Mitigate Position Bias](https://eugeneyan.com/writing/position-bias/)
- Measurement options: uniform random shuffling of top results (RandN/RandTopN — "adversely impacts the customer experience and is usually too costly"); exploiting inherent randomness from multiple production rankers or frequent ranker updates; and, specifically for item-to-item, "the same recommended item may be shown in different positions for different context items. However, as the context isn't constant, this app[roach is limited]". — [same](https://eugeneyan.com/writing/position-bias/)
- Correction: the Google approach "used inferred position bias to train models optimized on **inverse propensity weighted precision**". — [same](https://eugeneyan.com/writing/position-bias/)
- Applied e-commerce result: "All attributed items are considered as relevant and their relevance is weighted based on inverse propensity scores"; offline evaluation uses "inverse-propensity-weighted NDCG to measure relevance and an average recommendation popularity metric to detect" popularity concentration. — [arXiv 2412.08780, Reducing Popularity Influence by Addressing Position Bias](https://arxiv.org/html/2412.08780v1); [CEUR Vol-3924 short paper](https://ceur-ws.org/Vol-3924/short4.pdf)

**Feedback loops**
- Simulated evidence that loops amplify bias: Mansoury et al., "Feedback Loop and Bias Amplification in Recommender Systems" — proposes simulating user interaction with the recommender offline to study the loop's impact. — [arXiv 2007.13019 / alphaxiv](https://www.alphaxiv.org/abs/2007.13019)
- Production evidence and mitigation: Tong, Qiao, Lee, McInerney, Basilico, RecSys 2023, "Navigating the Feedback Loop in Recommender Systems: Insights and Strategies from Industry Practice" — "In a closed-loop recommender system on Netflix Homepage, we introduced a new ML agent to mitigate the feedback loop bias in the existing ML agent, and observed…" — [ACM DL, DOI 10.1145/3604915.3610246](https://dl.acm.org/doi/fullHtml/10.1145/3604915.3610246) (page is CAPTCHA-gated for automated fetches; bibliographic record confirmed via [Semantic Scholar, CorpusId 261824573](https://api.semanticscholar.org/graph/v1/paper/DOI:10.1145/3604915.3610246))
- Dynamic Yield's `Shuffle Results` is a production exploration mechanism: sample a subset "from the top 100 most popular items… weighted by product score, giving higher-ranked products a greater chance of being displayed" (popularity algorithm only). — [Dynamic Yield KB](https://support.dynamicyield.com/hc/en-us/articles/360022554694-Recommendation-Strategies)

### Inferences
- The minimum credible evaluation stack for a relation system is: (a) offline **IPW-NDCG / recall@k** on held-out interactions, (b) a **popularity-concentration metric** (share of edges pointing at the top-N items, or average target popularity) to catch loop amplification, (c) a **coverage metric** (share of catalog with ≥1 relation), and (d) an online A/B with click-through and downstream conversion. Vendors publicly do (d) and part of (a); the literature supplies (b).
- For a catalog with a human validation queue, the natural extra metric is **queue precision** — the share of approved candidate edges that survive 90 days without being reverted — because click data will be far too sparse to judge an individual edge.
- Item-to-item has a structural advantage for debiasing that vendors do not exploit explicitly: the same target appears in many different source-item lists, so position varies naturally across contexts. Recording `(source_item, target_item, position)` at serve time makes this usable as a weak randomisation for propensity estimation.
- Constructor's "page-level gain can be negative even when item-level gain is positive" is the correct guard against a merchandiser optimising a single relation at the expense of the whole slot — and it is the exact failure mode a human validation queue is prone to.

### Gaps
- No vendor publishes offline metric definitions, thresholds, or acceptance criteria for promoting a model/rule (e.g. "ship if NDCG@10 improves by X"). Everything public is directional.
- No vendor documents how it corrects for position bias inside its own product; IPW appears only in the academic literature. Whether Algolia/Coveo/Constructor internally debias is not publicly stated.
- No public data on the size of the feedback-loop effect in item-to-item recommendations specifically (as opposed to personalised ranking).

## 6. UX for merchandisers to inspect and edit relations

### Takeaway
The merchandising UI is organised around **slots/widgets/pods as the primary object**, not around items or edges: the merchandiser picks a placement, previews it against a concrete source item (or shopper profile/segment), and layers rules on top. Relation inspection is therefore *indirect* — you see the rendered list, not the graph. Editing is form-based (condition → action), with a preview pane; there is no public example of a graph-editing surface for recommendations.

### Cited Findings

**Slot/pod as the organising object**
- Constructor: "Every location you would want to serve recommendation results should be thought of as a **recommendations pod**. Pods represent a specific location on a page or set of pages (template)… A page may have one or more pods." — [Constructor docs, Learn about Recommendations](https://docs.constructor.com/docs/products-recommendations-learn-about-recommendations.md)
- Constructor: "Currently, a pod can be assigned a **single strategy**, but the capability is possible in the future to support multiple strategies in a single pod." — [same](https://docs.constructor.com/docs/products-recommendations-learn-about-recommendations.md)
- Coveo: the Recommendations manager "main page offers merchandisers a comprehensive overview of all the recommendation slots that are associated with a specific storefront", with a search bar "to search for specific slots or rules", navigation tabs, and property/locale selectors to scope which slots are shown. — [Coveo docs, Recommendations manager](https://docs.coveo.com/en/o4nh0046/)
- Bloomreach: the **Widget Configurator** is the entry point — "Go to Recommendations to view the Widget Configurator… Click + New widget", then choose Primary/Secondary algorithm, "Result size and FL list", and "Under the Product Grid tab, apply the merchandising rules for the Widget". — [Bloomreach docs, Similar Products Widget](https://documentation.bloomreach.com/discovery/docs/similar-products-widget)

**Preview is the core inspection affordance**
- Constructor preview: "The preview shows the results of one pod at a time. Select the pod to preview from the drop-down at the top of the preview. **The badge next to each pod shows its strategy.**" Preview needs an item (item-based strategies) or a profile (user-based); segments via **Impersonate**; "The preview is not yet available for pods with some strategies, such as *Filtered items*." — [Constructor docs, Searchandise a recommendation pod](https://docs.constructor.com/docs/using-the-constructor-dashboard-recommendations-searchandise-a-recommendation-pod.md)
- Bloomreach preview: "view the grid using the **Preview** option… To preview the changes, you must enter the **Product ID (PID)**. The Preview shows products per the rule you have set." — [Bloomreach docs, Merchandising Capabilities](https://documentation.bloomreach.com/discovery/docs/merchandising-capabilities)

**Editing is condition → action, in the same editor as search**
- Constructor: "You build it in the same editor that you use for search and browse searchandising, with the same preview and the same rule types"; conditions are "Refine with conditions" → "By item" / "By attribute". — [Constructor docs, Searchandise a recommendation pod](https://docs.constructor.com/docs/using-the-constructor-dashboard-recommendations-searchandise-a-recommendation-pod.md)
- Nosto: rules are built by choosing an attribute and a weight — "you must select an attribute and set a specific weight for it, adjusting the ranking score. **You can manually write anything more than 100% as weight** if you don't see your desired outcome." — [Nosto Help, Merchandising & Search Personalization Guide](https://help.nosto.com/en/articles/7168969-merchandising-search-personalization-guide)
- Nosto: rule scope is chosen at creation ("global" vs "specific query/category"), and merging behaviour is an explicit toggle ("If you don't want the rules to be merged, use the exclusion mechanism directly in the create/edit menu"). — [same](https://help.nosto.com/en/articles/7168969-merchandising-search-personalization-guide)
- Recombee: logic, filters and boosters are all settable in the Admin UI per scenario, and the UI shows the resulting configuration as a single screen ("Setting Logic & Filter in the Admin UI"). — [Recombee docs, Scenario Settings](https://docs.recombee.com/scenarios/settings-in-admin-ui)
- Algolia: the rule editor is model-scoped and built top-down — "use the **Model** selector at the top of the dashboard to select the index and model to which you want to apply rules", then "+ New rule" → pick condition → "Add consequence" → optional description and timeframe. Rules apply to "trained Frequently bought together, Related items, Looking similar, and Trending items models". — [Algolia docs, Refine recommendations with rules](https://www.algolia.com/doc/guides/algolia-recommend/how-to/rules.md)
- Algolia exposes a **debug affordance for the served list**, not just for the rule: `getRankingInfo: true` returns `appliedRules` with the object IDs of every rule that fired. — [same](https://www.algolia.com/doc/guides/algolia-recommend/how-to/rules.md)

**Guardrails and affordances visible in the UI**
- Coveo pin editing is direct-manipulation: you can "search for the product or use the preview to select the products to pin… When using the preview, **drag a product and drop it at a position** to pin it there." Pinning requires a **seed product** to preview: "If you selected a slot that requires a seed product to generate recommendations, you must select a seed product to preview the recommendations generated for th[at item]". — [Coveo docs, Pin rules for slots](https://beta.docs.coveo.com/coveo-platform/commerce/coveo-merchandising-hub-cmh/recommendations-manager/ranking-rules-for-recommendations/pin-rules-for-slots.md)
- Coveo warns about conflicts *in the rule-creation flow* rather than silently resolving them: "merchandisers must not create multiple pin rules that target the same position in the same slot. If there's a conflict between pins, priority is given to the most recent pin rule." — [same](https://beta.docs.coveo.com/coveo-platform/commerce/coveo-merchandising-hub-cmh/recommendations-manager/ranking-rules-for-recommendations/pin-rules-for-slots.md)
- Dynamic Yield surfaces precedence in the FAQ rather than the UI: pinning out-of-stock still shows the item; a filter that only matches out-of-stock shows nothing; Recently Viewed caps at 30 products. — [Dynamic Yield KB](https://support.dynamicyield.com/hc/en-us/articles/360022554694-Recommendation-Strategies)
- Bloomreach shows, in the datasheet, which controls are unavailable for which widget type and which algorithm (e.g. hard PID boost "except for Personalized algo"; Product Slotting not available for Recommendations) — capability gating is presented as part of the product surface. — [Bloomreach docs, Merchandising Capabilities](https://documentation.bloomreach.com/discovery/docs/merchandising-capabilities)

### Inferences
- The dominant UX metaphor is **"the slot with a preview, plus a rule list"** — not a graph, not a table of edges. For a relation-adding system with a human validation queue, this suggests a two-pane design: *left = proposed/rejected/accepted relations for the selected source item, with evidence; right = live preview of the resulting slot*. That combines the vendor's preview affordance with the edge-level review the vendors lack.
- Showing the **strategy badge next to each pod** (Constructor) is a small but important transparency cue: the merchandiser always knows which algorithm produced what they are looking at. An equivalent for relations is a **provenance badge per edge** (co-purchase / co-view / embedding / manual / inherited).
- Because previews are stateful (need an item, profile, or PID), the queue should be **source-item-centric**: pick an item, see its current relations, see candidates, preview the slot. A queue organised by "recently proposed edges" would force the reviewer to context-switch into a preview for every row.
- Nosto allowing weights "more than 100%" and exposing merge/exclude toggles indicates that merchandisers need an **escape hatch with visible precedence**; hiding precedence in an FAQ (as Dynamic Yield does) is the anti-pattern.
- Algolia's `appliedRules` is the closest existing precedent for **per-item explainability of a served list**, and it is a request-time flag rather than a separate admin screen. For a relation catalogue this argues for making provenance part of the read API (`GET relations?explain=true`) instead of building a separate "why" tool — the reviewer then sees the reason next to the edge in the same call that renders the preview.

### Gaps
- I found no public screenshots or documentation of any vendor offering a **graph visualisation** of item-to-item relations for merchandisers; all relation inspection is via rendered lists. (By contrast, the knowledge-graph tools covered in the companion note do provide graph views.)
- No vendor documents bulk operations on relations (CSV import/export of edges, bulk approve, bulk retire) in public docs — only bulk item/attribute rules.
- No vendor documents the reviewer experience for a *rejected* suggestion, i.e. whether rejections are remembered and suppress re-proposal. This is a real design question for a validation queue and is unanswered in public sources.

## 7. What transfers to a B2B software catalog with sparse co-purchase, long-tail items, renewal/upgrade paths and a human validation queue?

### Takeaway
The vendor stack transfers well as a **set of primitives** (relation generators, scoring normalisation, layered manual controls, deterministic precedence, preview-and-measure review) but not as an **architecture**: every platform assumes dense consumer behaviour and organises its UI around a rendered slot, whereas a software catalog must lead with content/embedding relations and needs a per-edge object with approval state that no vendor provides.

### Cited Findings
- Behavioural data floors are high and vendor-stated: 1,000 interactions (Personalize Similar-Items), 10,000 events (Coveo PR), 1,000 FBT / 10,000 Related-items events (Algolia); Algolia's CF window is 30–90 days. — [AWS, Similar-Items](https://docs.aws.amazon.com/personalize/latest/dg/native-recipe-similar-items.html); [Coveo, PR model](https://docs.coveo.com/en/3395/); [Algolia, Recommend overview](https://www.algolia.com/doc/guides/algolia-recommend/overview.md)
- Content floors are dramatically lower: "Related content" needs **10 items with content-based attribute values**, and "Looking similar" "**doesn't require any events**". — [Algolia, Recommend overview](https://www.algolia.com/doc/guides/algolia-recommend/overview.md)
- Content relations are explicitly the documented remedy for sparse behaviour: "show recommendations when you don't have enough click and conversion events… increase catalog coverage" (Algolia); "marries behavioral signals with content embeddings" for "new or less popular products" (Constructor); BERT-based "top 200 similar product candidates" from product-feed features (Bloomreach). — [Algolia](https://www.algolia.com/doc/guides/algolia-recommend/overview); [Constructor](https://docs.constructor.com/docs/products-recommendations-learn-about-recommendations.md); [Bloomreach](https://documentation.bloomreach.com/discovery/docs/similar-products-widget)
- Popularity is exposed as an explicit control: `popularity_discount_factor` (default 0.0, "closer to one for less emphasis on popularity"); Dynamic Yield "demotes products that are typically purchased with many other items". — [AWS, Similar-Items](https://docs.aws.amazon.com/personalize/latest/dg/native-recipe-similar-items.html); [Dynamic Yield KB](https://support.dynamicyield.com/hc/en-us/articles/360022554694-Recommendation-Strategies)
- Fallback is a per-placement choice, not a global default: Constructor backfill uses Bestsellers "by default" and "can be turned off by request"; Coveo ships `Purchased together` vs `Purchased together without fallback`; Bloomreach requires picking a Secondary Algorithm (Best Seller / Trending / Recently Viewed). — [Constructor](https://docs.constructor.com/docs/products-recommendations-learn-about-recommendations.md); [Coveo](https://docs.coveo.com/en/p85e0425/); [Bloomreach](https://documentation.bloomreach.com/discovery/docs/similar-products-widget)
- Relation types are already split along the axis a software catalog needs: Coveo's "same category" vs "different category" co-view/co-purchase strategies, and Constructor's Alternative (substitutable) vs Complementary (bought in addition) vs Bundles. — [Coveo](https://docs.coveo.com/en/p85e0425/); [Constructor](https://docs.constructor.com/docs/products-recommendations-learn-about-recommendations.md)
- Precedence can be made deterministic and auditable: Algolia's four-step tie-break ends with "the one with the lowest object ID (alphabetically ordered) wins", and `getRankingInfo: true` returns an `appliedRules` array. — [Algolia, rules](https://www.algolia.com/doc/guides/algolia-recommend/how-to/rules.md)
- Rule effects are measurable at two levels, including cannibalisation: Constructor's page-level gain can be negative "even if the merchandised items themselves improved… when promoted items divert engagement from other items". — [Constructor, Rule Performance](https://docs.constructor.com/docs/analytics-rule-performance-overview.md)
- Review is preview-based, not approval-based: previews require "a seed product" (Coveo), "an item… or a shopper profile" (Constructor), or "the Product ID (PID)" (Bloomreach). — [Coveo, Pin rules](https://beta.docs.coveo.com/coveo-platform/commerce/coveo-merchandising-hub-cmh/recommendations-manager/ranking-rules-for-recommendations/pin-rules-for-slots.md); [Constructor](https://docs.constructor.com/docs/using-the-constructor-dashboard-recommendations-searchandise-a-recommendation-pod.md); [Bloomreach](https://documentation.bloomreach.com/discovery/docs/merchandising-capabilities)

### Inferences
- **Invert the default relation source.** For a catalog that cannot clear 1,000–10,000 events, make embeddings/content the primary generator and treat co-purchase as a sparse, high-precision booster (Algolia's "strict" FBT is the right analogue, not "relaxed"). Expect behavioural edges to be a minority and to need human confirmation.
- **Model four relation types explicitly**, mirroring the vendor vocabulary but adapted: `upgrade/replacement` (Coveo "same category", Constructor "Alternative"), `complementary/add-on` (Constructor "Complementary"), `renewal/successor` (no vendor analogue — must be designed), and `bundle/solution` (Constructor "Bundles"). Coveo's same-vs-different-category split is the closest published precedent for separating substitution from complementarity.
- **Store the edge, not just the rule.** The decisive gap versus every vendor is that they persist *rules that fire at serve time*; a software relation catalogue should persist `(source, target, type, evidence[], confidence, provenance, status, owner, valid_from/valid_to)` and treat pins/boosts as annotations on edges. This is what makes a human validation queue possible at all.
- **Discount hub items hard and by default.** Platform/runtime/vendor items ("Azure", "SQL Server", a dominant vendor) will otherwise attach to everything. Use a popularity-discount factor plus a diversity constraint (Recombee-style: absolute/percentage cap per segment, optional window) as a first-class guard, not a tuning afterthought.
- **Replace bestseller fallback with curated fallback.** Bestsellers in a long-tail software catalog collapse to the same handful of flagships. Prefer per-family curated lists, then embeddings, then popularity — and make the order a per-slot setting (the Constructor/Coveo pattern).
- **Adopt deterministic precedence and per-response explainability** (Algolia's model): a total order over overrides, plus a `relations?explain=true` style response that names which candidate source and which manual override produced each served edge.
- **Keep the two-level metric.** Approve an edge on item-level lift, but gate it on slot-level (page-level) gain so a validated relation cannot quietly cannibalise the rest of the list.

### Gaps
- No public source addresses **renewal/upgrade relations** in a recommendation system; all vendor relation types are merchandising constructs (substitute/complement/bundle), not lifecycle constructs (supersede/renew/step-up). This type must be designed from the catalog side, using the companion notes on software licensing rather than the recsys literature.
- No vendor documents relation **expiry or succession** (what happens to edges pointing at a retired SKU), so there is no precedent to copy for TTL/supersession semantics.
- No public evidence on how these platforms perform on catalogs with **fewer than ~1,000 total interactions**; all documented behaviour assumes the floors are met, and cold-start handling is described per *item*, never per *catalog*.
- Whether any vendor supports **bulk import of curated edges** (as opposed to bulk item/attribute rules) is undocumented; a validation queue that cannot be seeded from an existing spreadsheet or catalogue export would be impractical at scale.
